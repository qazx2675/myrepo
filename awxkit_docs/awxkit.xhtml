본 도구 및 로그 분석 출력은 100% 신뢰하기보다 보조 도구로 사용하는 것을 권장합니다. 특히 [S3] DHCP 등록(dhcp.sh) 및 [S4] PXE 등록(pxe.sh)은 실제 인프라 설정을 변경하는 작업이므로, 실행 완료 후 반드시 무작위로 대상 서버 몇 대를 골라 실제 설정 변경 여부를 직접 확인하십시오.

1. Suite 전체 개요 및 단계별 전체 흐름

awxkit은 단일 모놀리식 바이너리가 아니라 단계별로 독립된 7개 Go 바이너리(awxkit-*)와 각 바이너리를 감싼 7개 Bash 래퍼 스크립트(*.sh)로 구성된 Suite입니다. 래퍼 스크립트는 해당 바이너리가 없으면 자동으로 setup.sh를 호출해 7개 바이너리를 일괄 빌드한 뒤 전달된 인자를 그대로 넘겨 실행합니다.

또한 상위 배시 파이프라인인 awx_script(.claude/HPC/awx_script)가 내부 awxkit/ 폴더를 직접 호출하여 NodeInfo 수집(nodeinfo.sh), YAML 동기화(invsync.sh), DHCP/PXE 등록(dhcp.sh, pxe.sh)을 일괄 자동화합니다.

text ──▶ s2_source_field(source_path) PATCH → 소스 동기화 → s2_inventory 호스트 조회 │ ▼ [S3] dhcp.sh -infra <번호|값> ──▶ s3_template 실행 → 최종 상태 + 실서버 검증 권고 출력 │ ▼ [S4] pxe.sh -infra ... -os ... -boot ... -splunk ... ──▶ s4_template 실행 → s4_inventory 총 등록 대수 리포트 │ ▼ [사후 검증] 무작위 대상 서버 몇 대에 직접 접속해 DHCP/PXE 반영 여부 확인]]>

awx_script와의 연계 구조

  • 01.AWX_nodeinfo_V2.sh [2]단계(download_txt): 사용자가 NodeInfo 수집(Y)을 선택하면 awxkit/nodeinfo.sh -hosts <절대경로>를 호출해 awxkit/output/${user}_nodeinfo.yaml을 생성하고 입력 파일에 반영합니다.
  • 02.source_dhcp_pxe.sh 일괄 등록: 01이 분할·Git 업로드를 마친 yml 목록을 넘기면 yml마다 awxkit/invsync.sh -user <user> -file <yml>을 먼저 실행한 뒤, awxkit/dhcp.sh와 awxkit/pxe.sh를 백그라운드로 동시 실행합니다(stdin을 /dev/null로 닫고 실행). 그룹 yml이 2개 이상이고 모두 성공하면 마지막에 전체(_all) yml로 invsync.sh를 1회 추가 실행해 인벤토리 호스트를 최신화합니다.

3. 일괄 오프라인 빌드 · 배치 및 공유 설정

3.1 폐쇄망 오프라인 빌드 (setup.sh 및 공유 vendor/)

awxkit은 vendor/ 폴더를 포함하고 있으며(현재 외부 의존성 없음), setup.sh가 cmd/*/ 아래 7개 진입점을 순회하며 GOFLAGS=-mod=vendor로 7개 바이너리를 일괄 빌드합니다.

bash

Windows 체크아웃 주의: .gitattributes에서 *.sh, *.go, go.mod를 LF 줄바꿈으로 강제합니다. 또한 awx_script와 연계해 사용할 때는 전역 복사 대신 awx_script/awxkit/ 경로에 폴더를 통째로 배치해야 01·02 스크립트가 정상 동작합니다.

3.2 사용자 식별자(${user}) 결정 및 설정/호스트 파일 탐색 순서

conf/sample_setting.conf를 복사해 conf/${user}_setting.conf를 작성하고, 평문 비밀번호 보호를 위해 권한을 600으로 설정합니다.

  • ${user} 결정 우선순위 (config/user.go의 ResolveUser 기준):
    1. config.CurrentUser() (소스 내 현장 판별 로직 훅 — 기본값 빈 문자열)
    2. -user <이름> CLI 플래그
    3. AWXKIT_USER 환경변수
    4. $USER (Linux) / %USERNAME% (Windows)
  • 설정 파일(${user}_setting.conf) 및 호스트 목록(${user}.txt) 탐색 순서: -conf(또는 -hosts)를 지정하지 않으면 아래 순서로 먼저 발견된 파일을 사용합니다.
    1. ./conf/${user}_setting.conf (또는 ./conf/${user}.txt)
    2. ~/.awxkit/${user}_setting.conf (또는 ~/.awxkit/${user}.txt)
    3. <바이너리 위치>/conf/${user}_setting.conf (또는 <바이너리 위치>/conf/${user}.txt)

5. 하위 도구별 핵심 옵션 · 입력 · 출력 상세

5.1 선택지 처리 공통 규칙 (dhcp.sh · pxe.sh)

  • 번호 지정: *_choices에 정의된 순서(1부터 시작)로 지정할 수 있습니다(예: -infra 1).
  • 값 직접 지정: *_choices와 대소문자까지 일치하는 값을 지정합니다. *_choices가 설정된 상태에서 목록에 없는 값을 넘기면 즉시 오류 종료됩니다.
  • 플래그 생략: *_choices가 있으면 대화형 번호 선택 메뉴가 뜨고, 비어 있으면 자유 입력 프롬프트가 뜹니다. (비대화형 파이프 실행 시 stdin이 닫혀 있으면 오류 종료).

5.2 도구별 세부 동작 및 특수 처리

  • nodeinfo.sh ([S1]): ${user}.txt(또는 -hosts)의 hostname 전체를 줄바꿈으로 합쳐 템플릿을 1회만 실행하고 s1_output_dir/${user}_nodeinfo.yaml로 저장합니다. 출력 YAML의 양식 변환은 수행하지 않으며, Job 실패 시 stdout 마지막 30줄을 출력하고 종료 코드 1로 끝납니다.
  • invsync.sh ([S2]) HTTP 404 대화형 복구: AWX 웹에서 인벤토리 소스 ID가 변경되어 HTTP 404가 반환되면, 곧바로 실패하지 않고 새 소스 ID(숫자, 최대 3회 입력)를 받아 s2_inventory_source를 사용자 ${user}_setting.conf 파일에 y/n 확인 후 제자리 갱신(백업 없음, 주석/다른 줄 유지)하고 1회 재시도합니다. 변경 시 history_file에 action=invsync status=source_updated old=.. new=..가 기록됩니다.
  • pxe.sh ([S4]) 허용 값 및 리포트: -boot는 legacy 또는 uefi, -splunk는 On-premise / Cloud / no를 사용합니다(s4_bootmode_choices / s4_splunk_choices로 강제 가능). s4_inventory가 설정되어 있으면 완료 후 총 N대의 호스트가 등록 완료되었습니다.를 출력합니다.

6. 통합 주의사항 · 실서버 검증 및 제한사항

  • ask_variables_on_launch 미설정 시 무음 무시: AWX 템플릿에서 ask_variables_on_launch가 꺼져 있으면 extra_vars를 보내도 조용히 무시됩니다. 최초 실행 전 반드시 doctor.sh로 [!] 또는 [X] 경고가 없는지 확인하십시오.
  • s2_source_field 확인: 기본값은 source_path이나 AWX 환경에 따라 다를 수 있으므로 최초 1회는 AWX 웹 UI에서 실제 인벤토리 소스 파일 경로가 갱신되었는지 직접 확인해야 합니다.
  • invsync 404 자동 수정 주의: 404 복구 시 y를 입력하면 백업 없이 ${user}_setting.conf의 s2_inventory_source 줄을 직접 수정합니다.
  • 자격 증명 보안: conf/${user}_setting.conf에는 AWX 평문 비밀번호가 들어가므로 chmod 600 설정을 유지하고 Git 저장소에 절대 커밋하지 마십시오.
  • 변경 후 실서버 검증 필수: DHCP/PXE 등록 완료 후 무작위로 서버 몇 대를 선정해 실제 PXE 부팅/DHCP 리스/인벤토리 반영 상태를 직접 확인하십시오.
