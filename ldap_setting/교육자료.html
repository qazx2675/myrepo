ldap-automation 을 만든 과정

어떤 지시를 어떤 순서로 주었고, 그것이 어떤 설계 결정과 명령으로 이어졌는지에 대한 기록. 2026-09-07 · Rocky Linux 8.10 (192.168.0.58) 에서 작업

이 문서는 완성된 코드를 설명하지 않습니다. 코드에 도달하기까지의 판단을 설명합니다. 같은 방식으로 다른 도구를 만들 때 참고하시라고 남깁니다.

01출발점: 계획서와 그 결함

시작은 이미 작성된 설계 계획서(ldap_automation_system_design.md)와, appl 사이트 판별 방식을 안내하는 참고 스크립트(ntp_dns_app.txt) 두 개였습니다. 지시는 계획서다. 누락된 항목이나 설계 단계에서 애매한 것이 있으면 나한테 질문해줘 였습니다.

여기서 바로 코드를 쓰지 않은 것이 이 프로젝트의 첫 갈림길입니다. 계획서를 읽고 나온 것은 동작하지 않을 결함 6개와 결정이 필요한 질문 22개였습니다. 대표적인 것:

결함내용
a2/a3 판별 불가두 사이트의 uri_order 가 uri2,uri1,uri3 로 완전히 동일. URI 순서로는 절대 구분할 수 없는데 계획서의 판별 로직은 URI 순서에 의존
uri3=NONE 시 재충돌uri3 를 빼면 a1 과 a4 의 패턴이 uri1 uri2 로 같아짐
INFRA 개념 부재계획서 스키마는 단일 인프라 전제인데, 요구사항은 인프라가 여러 개
죽은 코드CURRENT_MP(auto.appl 파싱)와 OS_VERSION 을 구해놓고 한 번도 쓰지 않음
배포 흐름 단절래퍼가 로컬에서 엔진을 돌리고 원격에는 체크만 보냄. 원격 설정 적용 단계가 없음
서비스 재시작 누락파일만 고치고 sssd/nslcd/autofs 재시작 언급이 한 줄도 없음. 그러면 실제로 적용되지 않음
배울 점. 계획서가 있다고 해서 그 계획서가 맞는 것은 아닙니다. a2/a3 문제는 표를 한 번만 세로로 읽어보면 보이지만, 코드를 먼저 쓰기 시작하면 "일단 계획대로" 구현하고 나중에 통합 테스트에서 발견하게 됩니다.

02질문을 객관식으로 바꾼 지점

질문 22개를 던졌지만 답이 오지 않았습니다. 대신 다른 스킬이 세 번 연속 호출됐습니다 (git-upload-sk, home-test, andrej-karpathy-skills). 목록이 길어 답하기 부담스러운 상태라고 판단하고, 객관식으로 답할 수 있는 4개를 선택지로 재구성했습니다.

이때 답이 나왔습니다.

질문선택된 답
판별 기준DNS+NTP / LDAP / auto.appl 셋 다 교차 검증
엔진 실행 위치관리 노드에서 원격 제어, 사용자가 만든 gossh 사용
설정 파일 형식대상 노드에 jq 가 없음 → flat key=value
대상 OSRHEL 7 포함 → CGO_ENABLED=0 정적 빌드

이어진 답변에서 판별 모델이 더 정확해졌습니다. URI DNS+NTP binddn binpw 모든 집합을 기준으로 해야 한다, DNS + NTP를 세트로 1차 인프라 분류를 진행하고 mountpoint는 site별 설정값이 고유하다.

배울 점. 답이 안 온다고 추측해서 진행하지 마십시오. 대신 질문의 형태를 바꾸십시오. 서술형 22개보다 객관식 4개가 훨씬 빨리 답을 받습니다. 그리고 답할 수 없는 것(자산 파일 실제 포맷 같은)은 끝까지 물어야 합니다 — 추측하면 100% 다시 씁니다.

03환경을 물어보지 않고 직접 확인한 것들

빌드 환경이 root@192.168.0.58 로 정해지자, 물어볼 필요 없는 것은 직접 조사했습니다.

ssh root@192.168.0.58 'cat /etc/redhat-release; go version'
# → Rocky Linux 8.10 / go1.26.5

# 인터넷 연결 확인 (go mod vendor 가능 여부)
curl -sI https://proxy.golang.org/     # → HTTP/2 200

# 도구 존재 확인
for t in jq git gossh shellcheck sssd nslcd chronyd ntpd autofs; do
    command -v $t >/dev/null && echo "$t yes" || echo "$t no"
done
# → jq/git/gossh/sssd/chronyd 있음, shellcheck/nslcd/ntpd/autofs 없음

이 한 번의 조사로 세 가지가 결정됐습니다.

  • shellcheck 미설치 → CI 는 bash -n 만 사용
  • nslcd/ntpd/autofs 미설치 → RHEL 7 경로를 실장비로 검증 불가 → --root 플래그를 설계에 추가해 가짜 /etc 트리로 테스트
  • 인터넷 연결됨 → vendor/ 를 만들 수 있음 (다만 이 프로젝트는 표준 라이브러리만 써서 결국 불필요)

gossh 소스를 읽은 것이 설계를 바꿨습니다

ssh root@192.168.0.58 'cd "/root/myrepo/.claude/공통/gossh/v2" && \
  grep -n "flag\.\|Sprintf\|Session\|CombinedOutput" main.go'
소스에서 발견한 것설계에 미친 영향
파일 전송 옵션이 없음scp 대신 base64 파이프 주입 채택. base64 는 [A-Za-z0-9+/=] 뿐이라 따옴표·개행·특수문자로 명령이 깨지지 않음
명령에 /user/ 가 있으면 병렬 350 강제autofs 보호 장치. -cf 로 뚫지 않고 그대로 존중
위험어 = reboot/poweroff/shutdown/halt/init 0/init 6/ddc우리 명령은 해당 없음 → -dnlgjawkrdjqghkrdls 미사용 확정
출력이 <host>: <내용> 고정결과 파서를 이 형식에 맞춰 작성
구버전의 따옴표 절단 버그가 v2 에서 수정됨README 에 "v2 를 쓰라" 를 명시
배울 점. 의존하는 도구의 --help 만 보지 말고 소스를 읽으십시오. --help 에는 "/user/ 경로면 병렬을 350으로 줄인다" 같은 내용이 없습니다. 이걸 모르고 -c 1000 을 믿었다면 실제 동작과 다른 가정 위에 설계했을 것입니다.

04구현 중 내린 설계 결정

결정 A6

파일 전체 교체가 아니라 키 단위 수술적 갱신

autofs.conf 와 sssd.conf 에는 우리가 건드리지 않는 운영 설정이 함께 있습니다. 템플릿으로 통째 생성하면 그게 전부 날아갑니다. 해당 키만 바꾸고 없으면 추가하는 방식으로 갔습니다.

검증: fixture 적용 후 BASE, TLS_CACERTDIR, timeout, browse_mode, id_provider, cache_credentials, driftfile 이 모두 그대로 남아 있는지 확인.

결정 A7

노드별이 아니라 사이트별로 스크립트를 만든다

RHEL 버전과 hostname(s4) 판정을 노드 현장에서 하게 만들면, 같은 사이트의 노드는 전부 동일한 스크립트를 받으면 됩니다. gossh 호출이 노드 수가 아니라 사이트 수(보통 4회)로 끝납니다.

결정

-infra 에 기본값을 두지 않는다

자산현황 파일이 hostname<TAB>site 두 컬럼이라 인프라 정보가 없습니다. 기본값을 두면 다른 인프라의 LDAP 값을 통째로 밀어넣는 사고가 가능합니다. 그래서 필수 인자로 만들었습니다.

결정

사이트 판별은 auto.appl storage 로만 한다

01 에서 발견한 a2/a3 문제의 해법입니다. URI 순서는 사이트끼리 겹칠 수 있으므로 판별 키가 될 수 없고, 사이트가 정해진 뒤 "그 기대 순서와 맞는가"를 보는 검증에만 씁니다.

05테스트가 잡아낸 실제 버그 3개

이것들은 코드 리뷰로는 안 잡히고 돌려봐야 나오는 종류입니다.

버그 1 — awk -v 가 정규식을 먹어치움

awk -v secre="^[ \t]*\[domain/" ...
# awk: warning: escape sequence `\[' treated as plain `['
# → 정규식이 ^[ TAB]*[domain/ 로 깨져 문자클래스가 열린 채 끝남
# → awk 가 빈 출력을 내고, 그게 sssd.conf 에 그대로 쓰여 파일이 날아감

수정은 두 갈래였습니다.

  1. 원인 제거 — 데이터를 -v 로 넘기지 않고 환경변수 + ENVIRON[] 사용. 섹션 판정도 정규식을 버리고 문자열 접두사 비교로 변경.
  2. 방어선 추가 — commit_file 에 "원본에 내용이 있었는데 결과가 비면 반영하지 않는다" 가드 추가. 다음에 다른 곳에서 비슷한 사고가 나도 설정 파일이 날아가지 않습니다.

버그 2 — 테스트 모드인데 진짜 서비스를 재시작

ROOT=/tmp/fx8 로 fixture 에 쓰면서 systemctl restart sssd 가 실제 .58 의 sssd 를 재시작했습니다. 운영 노드에서 이런 테스트를 했다면 사고입니다.

if [ -n "$ROOT" ]; then
    log SKIP-RESTART "$svc (ROOT=$ROOT 테스트 모드)"
    return 0
fi

버그 3 — chrony 의 pool 줄을 안 지움

apply 는 server 줄만 교체했는데, 체크 스크립트는 ntp_dns_app.txt 를 따라 server 와 pool 을 둘 다 NTP 소스로 셉니다. 결과적으로 "적용은 성공했는데 검증은 FAIL" 이 나왔습니다.

흥미로운 점은 체크 스크립트가 apply 스크립트의 버그를 잡아냈다는 것입니다. 두 스크립트를 독립적으로 만들고 왕복(round-trip) 테스트를 한 덕분입니다.

배울 점. "설정하는 쪽"과 "검사하는 쪽"을 한 코드에서 공유하지 마십시오. 따로 만들어서 A로 적용한 뒤 B로 검사하면, 둘 중 하나가 틀렸을 때 드러납니다. 같은 로직을 공유했다면 이 버그는 조용히 통과했을 것입니다.

덤 — 테스트 하니스 자체의 버그

첫 회귀 테스트 실행에서 7개가 FAIL 로 떴는데, 출력을 보니 도구는 전부 정확했습니다. grep '<TAB>FAIL<TAB>' 로 찾고 있었지만 실제 출력은 FAIL 이 줄 맨 앞이었습니다. 실패를 봤을 때 코드가 아니라 테스트를 먼저 의심해야 하는 경우가 있습니다.

07정리 — 다음에 비슷한 걸 만든다면

  1. 계획서를 먼저 반증하십시오. 표를 세로로 읽고, 값이 겹치는 곳을 찾고, 데이터 흐름이 끊긴 곳을 찾으십시오.
  2. 추측할 수 없는 것은 끝까지 물으십시오. 다만 답이 안 오면 질문의 형태를 바꾸십시오.
  3. 의존 도구의 소스를 읽으십시오. --help 는 절반만 알려줍니다.
  4. 테스트 가능성을 설계에 넣으십시오. --root 하나로 실장비 없이 전 분기를 검증할 수 있게 됐습니다.
  5. 적용과 검사를 분리하십시오. 서로가 서로의 버그를 잡습니다.
  6. 파괴적 동작에는 방어선을 두 겹 치십시오. 원인 제거 + 최후 가드.
  7. 테스트 실패를 봤을 때 테스트를 먼저 의심하십시오.
그래도 남는 것. 이 도구는 인증과 이름해석에 직결되는 파일을 고칩니다. 14개 테스트가 통과했다는 사실이 "운영에서 안전하다"를 뜻하지 않습니다. -dry-run → 소수 노드 → 전체 순서를 지키고, 적용 후에는 무작위 서버 몇 대를 직접 확인하십시오.
