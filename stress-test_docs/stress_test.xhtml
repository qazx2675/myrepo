도구명: stress-test (stress-test + stress_run.sh) — AWX 부하테스트 자동 실행 및 1분 로드 감시 도구

양식 유형: T2 (부하판정 · 실행형)

주요 파일: stress-test (사전 빌드 정적 바이너리), stress_run.sh, setup.sh (설정 생성 마법사), conf/sample_setting.conf

연계 도구: setup_check (new_setup -run / -run -auto 비대화형 호출), gossh (접속체크·벤더 확인·1분 로드 감시), AWX 서버, repohost (custom_inventory.sh)

한 줄 요약: AWX 인벤토리 등록 후 a) cpu 및 b) stress-ng 부하테스트 템플릿을 실행하고, gossh로 대상 서버의 /proc/loadavg 1분 로드를 감시해 실제 부하 인가 여부(실행/미실행)를 판정하는 CLI/래퍼 도구입니다.

AWX 인벤토리 임시 변경/복원 및 실서버 부하 확인 필수:

  • 이 도구는 대상 서버에 실제 CPU/stress-ng 부하를 인가하며, cpu 단계 실행 시 AWX CPU 템플릿의 인벤토리를 DEFAULT → conf username 인벤토리로 바꿨다가 launch 직후 DEFAULT로 되돌립니다(stress-ng 템플릿은 개인 인벤토리를 그대로 사용).
  • 만약 복원(PATCH)에 실패하면 화면에 ✗✗✗ 경고, 이력에 action=restore status=fail, 결과표 비고에 인벤토리 복원 실패 — 수동으로 DEFAULT 로가 남으므로 즉시 AWX UI/API에서 해당 템플릿의 인벤토리를 수동으로 DEFAULT로 복구해야 합니다.
  • 실행/미실행 판정은 1분 로드(load_threshold)에 기반한 추정이므로, 작업 후 무작위로 몇 대의 서버에 직접 접속해 uptime, top, stress-ng/부하 프로세스 동작 여부를 반드시 확인하세요.

1. 개요 및 전체 판정 · 실행 흐름

stress-test는 HPC 장비 개통 후 부하테스트(a) cpu, b) stress-ng)를 AWX Job Template으로 실행하고, 대상 서버에 실제로 부하가 올라왔는지 gossh로 /proc/loadavg를 주기적으로 감시해 판정하는 도구입니다.

text 1회 실행 및 삭제 확인 ├─ 등록: yaml 생성 → scp → ssh custom_inventory.sh → svr_dir 새 *.yml 1개 확인 │ → (업로드 연동 설정 시) 인벤토리 YAML 업로드(동기화) → invsync → 대상 호스트 완전일치 검증 ├─ (cpu 만) 템플릿 인벤토리가 default_inventory 인지 확인(사용 중이면 질문) │ → username 인벤토리로 PATCH → 확인 GET → launch → 즉시 DEFAULT 복원 PATCH ├─ AWX job 완료(successful) 대기 (부하 프로세스를 백그라운드로 띄운 뒤 job 종료) └─ 부하 감시: monitor_interval 마다 gossh 'cat /proc/loadavg' 1분 로드 >= load_threshold 면 '실행' 확정(목록 제거, 비면 조기 완료) monitor_sec 만료 시 남은 호스트 = '미실행' (재실행 y/N 또는 -retry N) ↓ [3] 결과표 출력 및 /${user}_stress_result.txt 저장 (hostname|CPU벤더|cpu|stress-ng|비고)]]>

1.1 setup_check -run 과의 통합 연계

setup_check(new_setup -run 및 -run -auto)는 내부적으로 stress-test -batch와 -yaml-state를 호출하여 부하테스트 단계를 자동 조율합니다(stress-test 소스를 수정하지 않고 표준입출력 프로토콜로 연계).

연계 인터페이스 동작 및 프로토콜
-batch 비대화형 호출 setup_check가 stress-test -user <u> -hosts <목록> -steps a|b -batch [-end y,m,d,h,min] [-conf <파일>] [-ignore-offline]를 호출. 감시 화면 대신 회차별 [감시] ... 한 줄 요약을 출력하며, setup_check는 이 [감시] 줄을 등록·launch 완료 신호로 인식합니다.
[인벤토리사용중] stdin 프로토콜 CPU 템플릿의 현재 인벤토리가 default_inventory가 아니면 stress-test가 [인벤토리사용중] ... 한 줄을 출력하고 stdin 한 줄을 대기합니다. setup_check TUI가 이를 감지해 사용자에게 질문(r 다시 확인 / x 묶음 중단)을 띄워 입력값을 stdin으로 전달하며, 대기 중에는 STRESS_TIMEOUT을 일시정지합니다.
-yaml-state 및 이벤트 줄 new_setup -run -auto는 launch 직전 -yaml-state를 호출해 [yaml상태] yml=... / hosts=...로 다른 사용자의 yml 덮어쓰기 여부를 검사하며, -batch 실행 중 출력되는 [제외], [job], [결과], [삭제확인], [등록] 줄을 파싱해 시도 횟수와 O/미실행 상태를 정밀 추적합니다.

2. 사전 준비 및 바이너리 배치 / 대화형 설정

2.1 사전 빌드 바이너리 사용 (빌드 불필요)

사전 빌드된 stress-test 정적 바이너리(Rocky 8 / RHEL 8+ x86_64용)가 포함되어 있으므로 별도의 빌드 과정 없이 권한 부여 및 설정 생성 후 바로 실행합니다(RHEL 6 관리 서버용 바이너리는 제공되지 않음).

사전 필수 요건:

  • gossh 설치 (PATH, stress_run.sh의 GOSSH, 또는 conf gossh 키)
  • 실행 서버에서 repohost(custom_inventory.sh 위치) 및 설정 시 inventory_delete_host로 비밀번호 없이 SSH/SCP 접속 가능해야 함 (BatchMode=yes)
  • AWX 서버에 cpu_template(단일 템플릿 — Intel/AMD는 템플릿 내부에서 구분), stress_template, default_inventory(기본 DEFAULT), 그리고 conf username(또는 이름에 username이 포함된 단일) 인벤토리 존재
  • 인벤토리 YAML 업로드(동기화) 연동 사용 시 해당 업로드 경로 및 스크립트가 사전에 구성되어 있어야 함

2.2 대화형 설정 생성(setup.sh) 및 -inspect 검증

bash ] [--conf <설정파일>] # 3) 읽기 전용 AWX survey/인벤토리 점검 (conf 키 검증 및 추천 값 제안) ./stress-test -inspect [-user | -conf <설정파일>] [템플릿 ID/이름 ...]]]>

구버전 설정 키 주의: 예전 cpu_intel_* / cpu_amd_* 키가 설정 파일에 남아 있으면 stress-test가 종료코드 2로 실행을 거부합니다. bash setup.sh를 실행하면 기존 값을 단일 cpu_template / cpu_hostname_key / cpu_extra_vars로 자동 이전해 줍니다.

3. 입력 파일 및 설정 파일 규격

3.1 호스트 입력 파일 (user.txt)

줄 단위로 형식을 판정하므로 혼합 작성이 가능하며, 빈 줄·# 주석 무시 및 대소문자 무관 중복 제거(첫 줄 유지)가 적용됩니다.

필드 수 형식 처리 방식
1개 hostname 한 줄 DNS 첫 IPv4 조회(실패 시 DNS실패로 제외) + 줄 번호 순번 MAC(02:00:00:xx:xx:xx) 생성해 tmp tmp tmp <host> <IP> <MAC> eth0 sda sda5 100 8.10 uefi 변환
12개 AWX 설치양식 레코드 4번째 필드를 hostname으로 사용하고 12필드 그대로 yaml에 기록
13개 설치양식 + 13번째 분류 필드 4번째 필드를 hostname으로 사용하고 yaml에는 앞 12필드만 기록
그 외 형식 오류 오류 줄 번호 목록 출력 후 종료코드 2

3.2 장애 목록 (-er <파일> / error_list.txt)

줄마다 hostname<TAB>장애사유 형식으로 작성합니다(탭으로만 구분, 사유 내 |는 /로 치환). -er 생략 시 현재 경로에 error_list.txt가 있으면 자동 적용되며, 장애 호스트도 실행 대상에 포함되어 결과표 마지막 비고 열에 사유가 추가됩니다.

3.3 주요 설정 키 (conf/${user}_setting.conf)

탐색 순서: -conf 지정 경로 → ./conf/${user}_setting.conf → ~/.stress-test/${user}_setting.conf → <바이너리 위치>/conf/${user}_setting.conf.

키 기본값 설명
awx_url, username, password, insecure_tls (필수) / false AWX 접속 정보. username과 일치(또는 포함)하는 AWX 인벤토리 필수
gossh 빈 값 gossh 경로 (비우면 환경변수 GOSSH → PATH)
repohost, repo_dir, svr_dir (필수) / /root/Inventory / (필수) custom_inventory.sh 서버·경로 및 새 *.yml 감시 폴더(${user} 치환, 인벤토리 YAML 업로드 경로 설정은 setup.sh 안내 참고)
inventory_delete_host, inventory_match_exclude 빈 값 첫 등록 전 delhost_${user} 실행 대상 서버(삭제 전후 호스트 동일 시 최대 30초 재확인 후 exit 2) 및 완전일치 검증 제외 호스트(a|b)
inventory_source, inventory, source_field 빈 값 / 빈 값 / source_path 인벤토리 소스 ID(미지정 시 inventory의 첫 소스) 및 yml 저장 필드명
cpu_template, cpu_hostname_key, cpu_extra_vars 빈 값 a 단계 템플릿 ID/이름, hostname 목록 survey 변수명(비우면 미전달), 추가 k=v
stress_template, stress_hostname_key, stress_extra_vars, stress_end_keys end_year,end_month,end_day,end_hour,end_min b 단계 템플릿·변수명 및 종료 시각 5개 survey 키(정확히 5개 필수)
default_inventory DEFAULT CPU 템플릿의 평상시 인벤토리 이름 (launch 직전 확인 및 launch 후 복원 대상)
monitor_sec, monitor_interval, load_threshold 120 / 10 / 3 job 완료 후 최대 감시 초, 1분 로드 확인 주기 초, 부하 실행 판정 임계값(이상)
output_dir, poll_interval, history_file ./output / 3 / ./stress-test_history.log 결과표·gossh 로그 저장 폴더, AWX 조회 주기 초, 이력 파일 경로

4. 실행 방법 및 CLI 옵션

bash
CLI 플래그 설명
-user <u> 사용자 식별자 (생략 시 STRESS_USER → $USER)
-hosts <파일> (실행 시 필수) 입력 호스트/설치양식 파일
-steps <ab> (실행 시 필수) 실행할 단계 및 순서 (a, b, ab, ba만 허용)
-end <연,월,일,시,분> stress-ng 종료 시각. b 단계 포함 시 비대화형에서 필수(현재 시각 이후의 유효한 날짜여야 함)
-retry N 비대화형에서 미실행 호스트 자동 재실행 횟수 (기본 0)
-er <파일> 장애 목록 파일 경로 (생략 시 현재 경로 error_list.txt 자동 사용)
-conf <파일> 설정 파일 직접 지정
-batch 비대화형 모드 강제 (한 줄 요약, 템플릿 사용 중 시 [인벤토리사용중] + stdin 1줄 응답)
-ignore-offline gossh 접속체크에 응답 없는 접속불가 호스트도 제외하지 않고 launch (결과 실행(감시불가); DNS실패는 계속 제외)
-inspect [템플릿 ...] AWX 템플릿 survey·인벤토리·소스를 읽기 전용으로 점검 (exit 0/1/2)
-yaml-state 인벤토리 소스의 현재 yml 및 호스트 목록 읽기 전용 조회 ([yaml상태] 출력)

6. 해석상 한계 · 미검증 항목 및 주의사항

  • 가상(모의) 환경 기반 검증 (실 AWX·AMD 실장비 미검증): 현재 stress-test의 일부 동작은 모의 응답 서버 및 랩 테스트 위주로 검증되었으며, 실제 운영 AWX의 survey_spec 필드 구조, 템플릿 인벤토리 PATCH 권한 및 launch 직후 복원 경합, custom_inventory.sh 실파일명 규칙, AMD 장비의 실제 vendor_id 응답은 현장에서 확인이 필요합니다.
  • 부하 지연 오판 가능성: 1분 로드는 서서히 상승하므로 실제 템플릿이 부하를 늦게 띄울 경우 monitor_sec(기본 120초) 안에 기준에 못 미쳐 미실행으로 분류될 수 있습니다. 장비 특성에 맞게 load_threshold와 monitor_sec를 조정하세요.
  • 부하 종료 및 인벤토리 소스 경합 미지원: 실행 중인 부하 프로세스 강제 종료·정리 기능은 범위 밖이며, 여러 사용자가 동일 인벤토리 소스를 동시에 PATCH할 경우 마지막 값으로 덮어써질 수 있습니다.
