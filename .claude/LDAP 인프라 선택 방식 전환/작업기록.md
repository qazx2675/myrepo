# LDAP 인프라 선택 방식 전환 — 작업기록

## 변경 요청

- 대상 저장소: `qazx2675/myrepo`
- 대상 경로: `.claude/VM/Network_Change_Integration_Script`
- 참고 문서: `README.md`, `Network_Change_Integration_Plan.md`, `CHANGELOG.md`,
  그리고 원본 `.claude/HPC/ldap_setting/scripts/deploy_ldap.sh`

### 요청 내용

`integration.conf`의 `ldap_infra = ` 값이 통합 스크립트에서 정적으로(매번
같은 값으로) 읽혀 사용되고 있었음. 원본 단일 LDAP 프로젝트는 `-infra`를
여러 인프라 중 매 실행 필수로 지정하는 값으로 다뤘는데, 통합판에서는 이 값을
`integration.conf`에 한 번 저장해두고 재사용하는 구조라 "다른 인프라 작업을
할 때 conf 파일 수정을 잊으면 조용히 이전 인프라에 적용되는" 사고 위험이
있다는 점을 질문받음. 원본처럼 `change.sh`가 실행 시점에 "어떤 인프라를
실행할지" 물어보도록(또는 플래그로 받도록) 바꿔달라는 요청.

### 제약/유지할 것

- 원본 `ldap_setting`/`ldap-config-engine`, `ip_change`, `vm-network-migration`
  등 하위 프로젝트의 핵심 로직은 건드리지 않음 (통합 스크립트 레이어만 수정)
- 오프라인 빌드/실행 유지 (외부 의존성 추가 없음, 순수 bash)
- 기존 동작(`-y`/`--dry-run`/인시던트 저장·재개/롤백 흐름)은 그대로 유지하고
  인프라 선택 로직만 추가

### 완료 기준

- `bash -n` 전체 스크립트 통과
- 기존 `tests/test_preprocess.sh` 회귀 없이 통과
- `select_ldap_infra` 단위 검증: `--infra` 지정 시 그대로 사용, 미지정 +
  비대화형일 때 사용 가능한 인프라 목록과 함께 명확한 오류로 중단
- `CHANGELOG.md`에 날짜순 항목 추가, `README.md`/계획서 관련 설명 갱신

## 변경 내용 요약

1. **`change.sh`**: `--infra <이름>` 옵션 추가. usage 헤더에 설명 추가(추출
   범위도 함께 수정).
2. **`lib/stages.sh`**:
   - `_ldap_infra_names()` — `ldap_config.conf`에서 `infra.<이름>.` 패턴으로
     인프라 이름 목록을 뽑음.
   - `select_ldap_infra()` — `--infra`가 있으면 그대로 사용, 없으면 대화형
     `select`로 고르게 하고, 비대화형이면 오류(D2)로 중단하며 사용 가능한
     이름을 함께 보여줌.
   - `stage_ldap()`이 매번 `select_ldap_infra`를 호출하고, 선택된 인프라를
     로그로 남기며, (`--dry-run`이 아니면) "이 인프라에 적용합니다, 계속?"
     확인을 추가. `_run_ldap`은 `conf_get ldap_infra` 대신 전역 `$INFRA` 사용.
3. **`lib/incident.sh`**: 인시던트 저장 시 선택된 `$INFRA`를 `meta`에 기록,
   재개/롤백 시 복원. `rollback_incident`는 저장된 `$INFRA`로 롤백해 항상
   원래 적용된 인프라로 정확히 되돌아가게 함(저장값이 없는 구버전 인시던트는
   자동 롤백을 건너뛰고 수동 명령 안내).
4. **`integration.conf.sample`**: `ldap_infra` 키 제거, 이유를 주석으로 설명.
5. **문서**: `README.md`(설정 표/옵션 표/에러코드 D2/흐름 다이어그램),
   `Network_Change_Integration_Plan.md`(§11.4에 배경 추가), `CHANGELOG.md`.

## 근거

원본 `ldap_setting`의 `deploy_ldap.sh`는 `-infra`를 **매 실행 필수 CLI
인자**로 요구하고 기본값을 두지 않는다(ARCHITECTURE 규칙 5: "`-infra`에
기본값을 두지 말라"). 통합 스크립트가 이 값을 `integration.conf`의 정적
값으로 바꿔버리면서 원본이 막으려던 "이전 작업 인프라가 남아 다음 실행에
잘못 적용되는" 사고 경로가 다시 열려 있었음. 이번 변경으로 원본과 동일한
안전장치(매 실행 명시적 지정, 기본값 없음)를 복원했다.

## 변경 요청 2 — LDAP 설정 참조를 `conf/` 자체 보관으로 전환

- 대상 저장소: `qazx2675/myrepo`
- 대상 경로: `.claude/VM/Network_Change_Integration_Script`
- 참고 문서: `README.md`, `CHANGELOG.md`, `integration.conf.sample`

### 요청 내용

`Network_Change_Integration_Script` 폴더가 조만간 **다른 부서로 단독
이관**될 예정. 기존 `ldap_conf`/`ldap_assets` 기본값이
`../../HPC/ldap_setting/conf/...` 상대경로로 원본 `ldap_setting` 프로젝트를
참조하고 있었는데, 이 폴더만 떼어 이관하면 그 상대경로가 깨짐. 사용자가
"경로를 `./conf/...`로 바꾸고 그 안에 파일을 넣어두면 되는지" 질문 →
확인 결과 기능적으로는 맞지만 원본과 별개 사본이 생기는 트레이드오프가
있음을 설명 → 이관 목적 확인 후 `conf/` 자체 보관으로 전환 결정.

### 제약/유지할 것

- 이번 이관 범위는 **이 폴더 자체(LDAP 설정 참조)만** — 사용자가
  `AskUserQuestion`으로 명확히 확인: 바이너리는 이미 빌드된 채로 가져가거나
  받는 부서가 직접 빌드하므로 `setup.sh`의 `../../HPC/*` 빌드 소스 의존,
  포트그룹(E) 단계의 `nm_dir = ../vm-network-migration` 런타임 위임은
  **이번에 손대지 않음**. 단, 포트그룹 단계까지 함께 이관하면 `nm_dir`도
  같은 종류의 문제가 생긴다는 점은 README/CHANGELOG에 안내만 남김.
- LDAP 엔진(`ldap-config-engine`) 자체 로직은 건드리지 않음

### 완료 기준

- `integration.conf.sample`의 `ldap_conf`/`ldap_assets` 기본값이
  `./conf/ldap_config.conf` / `./conf/assets.txt`로 바뀌고, 원본과 별개
  사본이라 자동 동기화되지 않는다는 점이 주석으로 명시됨
- `conf/ldap_config.conf.sample`, `conf/assets.txt.sample`이 이 프로젝트
  안에 자체 보관되어, `HPC/ldap_setting` 없이도 값만 채우면 바로 동작
- `README.md`/`setup.sh` 안내에 `conf/` 사본 복사 단계 반영
- `bash -n` 통과, 샘플 파일이 `.gitignore`에 걸리지 않고 정상 추적됨

## 변경 요청 4 — `go.mod` 과도한 버전 요구로 인한 폐쇄망 빌드 실패 수정

- 대상 저장소: `qazx2675/myrepo`
- 대상 경로: `.claude/VM/Network_Change_Integration_Script/projects/*`
- 참고 문서: `CHANGELOG.md`, `README.md`

### 요청 내용

사용자가 `./setup.sh` 를 직접 실행했더니 `vm-network-migration` 단계에서
오류가 발생, "vendor 문제인 것 같다"고 보고. 이어서 "기존과 동일하게
vendor 파일이 폴더 안에 있어야 한다, 폐쇄망에서 setup.sh 를 실행하면
오류 없이 정상적으로 빌드되는 상태로 있어야 한다, 지금 그걸 못 만드는
상태이니 가능하게 해달라"고 명확히 요구.

### 진단 (원인 확인 후 진행)

1. `vendor/`·`go.mod`·`go.sum` 을 원본과 `diff -rq` — 바이트 단위 완전 동일.
   `.gitattributes` 의 `vendor/** -text` 도 `git check-attr` 로 정상 적용
   확인. → vendoring(변경 요청 3) 자체는 원인이 아님.
2. 세 프로젝트 `go.mod` 가 전부 `go 1.26.5` 를 요구하는데, vendor 안
   `govmomi v0.55.1` 의 실제 최소 요구는 `go 1.25.0` 뿐(과도하게 높게
   박혀 있었음). 폐쇄망 호스트에 정확히 그 버전이 없으면 `GOTOOLCHAIN` 이
   자동 다운로드를 시도하다 네트워크 없이 실패 — `-mod=vendor` 와 맞물려
   vendor 문제처럼 보이는 증상으로 나타날 수 있음.
3. 네트워크가 되는 이 세션에서 실제 `go1.26.5` 를 내려받아
   `go mod tidy && go mod vendor` 로 재생성 → 기존 커밋된 `vendor/`·
   `go.sum` 과 완전히 동일(diff 없음). **vendor 트리 자체는 100% 정상**임을
   확정.

### 조치

- `projects/ip_change/go.mod`, `projects/ldap_setting/go.mod`,
  `projects/vm-network-migration/go.mod` 의 `go 1.26.5` → `go 1.25.0` (실제
  최소 요구치에 맞춤, 코드/vendor 변경 없음)
- `README.md` 1.1 절 "랩 기준 go1.26.5" → "Go 1.25.0 이상이면 됨"

### 제약/유지할 것

- `vendor/` 디렉터리와 그 안 파일들은 그대로 유지(사용자 요구: "vendor
  파일이 폴더 안에 있어야 한다") — 삭제·재구성 없이 `go.mod` 의 버전
  지시자만 조정
- 코드 변경 없음, 세 프로젝트의 실제 동작 로직은 그대로

### 완료 기준 / 검증

- `go1.25.1`(로컬 확보)로 세 프로젝트 각각 `go vet ./...`, `go test ./...`
  전부 통과
- `GOMODCACHE=$(mktemp -d) GOPROXY=off ./setup.sh` 를 `go1.25.1` 로 **처음부터
  끝까지 실행해 9개 바이너리(`ip-change-engine`, `ldap-config-engine`,
  `nm-backup`/`nm-pgcreate`/`nm-disconnect`/`nm-connect`/`nm-verify`/
  `nm-rollback`/`nm-inventory`) 전부 정상 생성 확인** — 변경 요청 3에서
  "환경 제약으로 끝까지 못 돌렸다"고 남긴 재검증이 이번에 완료됨

## 변경 요청 5 — OS6(RHEL/CentOS 6) 대상용 사전 빌드 바이너리 추가

- 대상 저장소: `qazx2675/myrepo`
- 대상 경로: `.claude/VM/Network_Change_Integration_Script`
- 참고 문서: `README.md`, `integration.conf.sample`, `CHANGELOG.md`,
  그리고 선례로 `.claude/공통/gossh/README.md` §5.8 (`gossh_os6`)

### 요청 내용

사용자 Go 버전은 1.26.5. "해당 폴더에는 6버전에서도 사용 가능한 1.20
이하 버전에서 빌드해서 사용한 바이너리 파일도 만들어야 한다"는 요청 —
`integration.conf.sample`에 이미 존재하던 `os6_hostgroup`/`os6_gossh`/
`os6_bin_dir` 설정 자리(§8.1, RHEL 6 전용 바이너리 분기)에 실제로 쓸
바이너리가 없었던 상태를 채워달라는 것.

### 배경 조사

`.claude/공통/gossh`(이 저장소의 다른 프로젝트)에 이미 동일한 문제와
해법이 문서화돼 있었음(README §5.8): RHEL/CentOS 6은 커널·glibc가 오래돼
최신 Go 툴체인 산출물이 못 도는 경우가 있어, Go 1.20 툴체인으로 별도
정적 빌드한 `gossh_os6`를 저장소에 미리 빌드해 커밋해 둠. `lib/stages.sh`
의 `os6_bin_dir` 처리 로직(`bin_os6="$os6dir/$(basename "$bin_std")"`)을
보면 `ip-change-engine`/`ldap-config-engine` 도 같은 패턴을 쓰도록
설계돼 있었으나 실제 바이너리가 만들어진 적은 없었음.

### 제약/유지할 것

- 세 엔진(`ip-change-engine`/`ldap-config-engine`/`vm-network-migration`)의
  코드·로직은 건드리지 않음 — 빌드 산출물과 `go.mod`의 버전 지시자만 조정
- `os6_hostgroup`이 비어 있으면(기본값) 전혀 쓰이지 않아야 함 — 기존
  동작(OS6 대상 없는 배포에는 영향 없음) 유지

### 조치

1. `go1.20`을 실제로 확보(`GOTOOLCHAIN=go1.20`, 네트워크로 다운로드)해
   `ip_change`/`ldap_setting`이 그 버전으로 문제없이 빌드·`vet`·`test`
   통과하는지 먼저 검증
2. `projects/ip_change/go.mod`, `projects/ldap_setting/go.mod`의 `go`
   지시자를 `1.25.0`(직전 변경 요청 4) → `1.20`으로 낮춤 — 두 프로젝트
   모두 서드파티 의존성이 없어 제약이 없고, 이렇게 하면 일반 빌드와 OS6
   빌드가 완전히 같은 `go.mod`를 공유(별도 관리 불필요, `gossh` v2와
   같은 전략)
3. `bin_os6/ip-change-engine`, `bin_os6/ldap-config-engine`을 실제 Go
   1.20 툴체인으로 `CGO_ENABLED=0 GOPROXY=off` 정적 빌드해 커밋
4. `integration.conf.sample`의 `os6_bin_dir` 기본값을 `./bin_os6`로 설정
5. `README.md`(1.1 절 재빌드 방법 포함, 3.4 절), `setup.sh`(완료 안내)
   갱신

### 완료 기준 / 검증

- 클린 `GOPATH`/`GOCACHE`로 실제 Go 1.20 빌드 성공, `file`로 정적 링크
  확인, `-h`로 정상 동작 확인
- `go vet ./...`, `go test ./...`를 Go 1.20에서 두 프로젝트 모두 통과
- `go.mod`를 1.20으로 낮춘 뒤에도 `GOMODCACHE=$(mktemp -d) GOPROXY=off
  ./setup.sh`가 Go 1.25.1로 처음부터 끝까지(9개 바이너리) 정상 재확인 —
  회귀 없음
- `git check-ignore`로 `bin_os6/*`가 `.gitignore`의 `bin/` 패턴에 걸리지
  않고 정상 추적됨을 확인
