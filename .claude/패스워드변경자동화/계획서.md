# RHEL 서버 Current Password 자동 대응 스크립트 — 계획서

작성일: 2026-09-29
작성자: Claude (요청자: aisoki2675@gmail.com)
대상 환경: 록키 리눅스(Rocky Linux) VM (192.168.0.58), ESXi(192.168.0.59), vCenter(192.168.0.50) 등 홈랩 VM
목적: SSH 접속 시 계정 잠금/정책으로 인해 `Current password` 프롬프트가 뜨는 상황을 자동으로 처리하여,
보유 중인 과거 비밀번호 이력(`old_password.txt`) 중 현재 유효한 것을 자동으로 찾아내고, 지정한 새 비밀번호로
일괄 변경하는 자동화 도구. 기존에는 `expect`로 처리하던 것을 Go로 재작성.

> ⚠️ 전제: 이 스크립트는 **본인이 관리/소유한 홈랩 서버**의 계정 비밀번호 이력을 본인이 알고 있는 상태에서,
> 분실된 현재 비밀번호를 되찾기 위한 용도로만 사용합니다. 제3자 시스템이나 권한 없는 계정에는 사용하지 않습니다.

## 1. 요구사항 정리 (제가 이해한 내용)

1. **실행 위치**: Go 코드는 이미 Go가 설치된 록키 리눅스(192.168.0.58)에서 빌드/실행.
2. **셸 환경 다양성**: 접속 대상 서버의 로그인 셸이 `csh`(대부분) 또는 `bash`(일부)로 다를 수 있음 → 프롬프트 패턴이 셸마다 다를 수 있으므로 이를 모두 흡수해야 함.
3. **비밀번호 변경 플로우 2가지 패턴**:
   - **패턴 A (3단계)**: `Current password` → `New password` → `Retype new password`
   - **패턴 B (2단계)**: (Current 단계 없이) `New password` → `Retype new password` 바로 진행되는 경우
   - → 스크립트가 매 단계 프롬프트를 보고 **동적으로 분기**해야 함 (고정 스텝 수로 가정하면 안 됨).
4. **변경 후 세션 동작 차이**: 비밀번호 변경 완료 직후
   - 세션이 즉시 종료되는 경우
   - 세션이 그대로 유지되는 경우
   - → 두 경우 모두 정상 종료로 판단할 수 있어야 함 (연결 종료를 실패로 오판하면 안 됨).
5. **old_password.txt**:
   - 과거 사용했던 비밀번호 이력을 줄 단위로 기록, **최신 비밀번호가 맨 위**.
   - 맨 위(최신)부터 순서대로 시도, 접속 실패 시 다음 줄로 넘어감.
   - 모두 실패하면 "접속불가"로 기록.
6. **새 비밀번호 적용**:
   - 적용할 새 비밀번호는 평문으로 코드/설정에 두지 않고 **암호화된 파일**로 저장해 두고, 실행 시 이를 복호화해서 사용.
   - 예: `asdf`를 암호화한 파일을 만들어두면, 이 파일을 이용해 실제 계정 비밀번호가 `asdf`로 바뀌어야 함.
7. **우선순위**: 1순위 속도, 2순위 모든 케이스(위 2·3·4번)에서 안정적으로 current password 탐색 성공.
8. **대상 인원**: 다수 서버/다수 계정을 대상으로 반복 수행 가능해야 함 (본인 소유 홈랩 기준으로 이해 — 아래 질문 참고).

## 2. 전체 아키텍처

```
run.sh  (실행 편의용 bash 래퍼)
  └─ go build → ./pwreset
  └─ ./pwreset -targets targets.csv -oldpw old_password.txt -newpw newpass.enc -out result.csv

pwreset (Go 바이너리)
  ├─ 대상 목록 로딩 (host, user)
  ├─ 새 비밀번호 파일 복호화 (1회, 메모리에만 보관)
  ├─ old_password.txt 로딩 (순서 유지)
  ├─ 대상별 goroutine (동시 실행, 속도 우선)
  │    └─ SSH 접속 시도 (최신 비번부터 순차)
  │         ├─ 로그인 성공 + 비번 즉시 변경 요구 없음 → 그대로 "현재 비번 확인됨" 기록, 필요시 비번 변경 절차 수행
  │         ├─ 로그인 중 Current/New password 프롬프트 감지 → 상태머신으로 변경 절차 처리
  │         ├─ 인증 실패(Permission denied) → 다음 비번으로 재시도
  │         └─ 모든 비번 실패 → "접속불가" 기록
  └─ 결과를 result.csv / old_password.txt 갱신본으로 저장
```

### 핵심 설계 포인트

- **SSH 라이브러리**: `expect`(pty 기반 텍스트 매칭) 대신 `golang.org/x/crypto/ssh` + 커스텀 pty 유사 셸 세션을 쓰되,
  비밀번호 변경 프롬프트(PAM `Current password:` / `New password:` 등)는 SSH 인증 단계의 `KeyboardInteractiveChallenge`
  콜백에서 대부분 처리 가능합니다 (OpenSSH가 `password expired` 상태일 때 keyboard-interactive로 체인지 플로우를 태우는 경우가 많음).
  다만 서버 설정에 따라 인증 성공 후 셸에서 `passwd`류 프롬프트가 뜨는 케이스도 있어, **두 가지 경로를 모두 지원**하는 설계로 갑니다.
- **상태머신 기반 프롬프트 매칭** (고정 스텝 대신):
  ```
  상태: WAIT_CURRENT_OR_NEW
    "Current password" 매치 → 이전 비번 입력 → 상태: WAIT_NEW
    "New password" 매치      → 새 비번 입력   → 상태: WAIT_RETYPE   (패턴 B로 전환)
  상태: WAIT_NEW
    "New password" 매치 → 새 비번 입력 → 상태: WAIT_RETYPE
  상태: WAIT_RETYPE
    "Retype new password" / "Retype" 매치 → 새 비번 재입력 → 상태: DONE_OR_CLOSED
  상태: DONE_OR_CLOSED
    셸 프롬프트($/#) 감지 → 성공(세션유지)
    EOF/커넥션 종료 감지 → 성공(세션종료형)
    "passwd: all authentication tokens updated" 등 문구 → 성공 마킹 후 위 둘 중 하나 대기
  ```
  csh/bash 프롬프트 정규식은 별도 목록으로 관리(`% `, `# `, `\$ `, 커스텀 PS1 등 확장 가능).
- **타임아웃 + 재시도**: 각 read 단계마다 짧은 타임아웃(예: 5~8초)을 두어 "세션 종료 vs 응답 없음"을 구분하고,
  전체 세션 타임아웃(예: 30초)으로 행(hang) 방지.
- **동시성**: 서버 수가 많다면 `errgroup` + worker pool로 병렬 처리(속도 우선 요구사항). 단, 계정 잠금 정책이 있는 서버는
  동시 시도 횟수 제한(예: 동일 host 순차, host 간에만 병렬)이 필요할 수 있음 — 정책 확인 필요(아래 질문 참고).
- **비밀번호 암호화 파일**:
  - 대칭키 암호화(AES-256-GCM) 사용, 키는 환경변수 또는 별도 키파일(`key.bin`, 0600 권한)로 분리.
  - `pwreset -encrypt -in plain.txt -out newpass.enc` 서브커맨드로 사전에 새 비번을 암호화해서 저장.
  - 실행 바이너리는 이 파일 + 키를 읽어 메모리에서만 평문으로 복호화, 로그/디스크에 평문 비번이 남지 않도록 처리.

## 3. 파일 구성 (제안)

```
.claude/패스워드변경자동화/
  계획서.md                 (본 문서)
cmd/pwreset/
  main.go                   실행 진입점, 플래그 파싱
  sshclient.go               ssh 접속 + keyboard-interactive 처리
  promptfsm.go                Current/New/Retype 상태머신
  cryptutil.go                 AES-GCM 암복호화
  targets.go                   대상 서버/계정 로딩
  report.go                     결과 기록(old_password.txt 갱신, result.csv)
run.sh                        (사용자 편의) 빌드+실행 래퍼, 인자 검증, 사용법 출력
old_password.txt              [입력] 과거 비번 이력 (최신이 맨 위)
targets.csv                   [입력] host,user 목록 (예: 192.168.0.58,root)
newpass.enc / key.bin         [입력] 새 비번 암호화 파일 + 키
result.csv                     [출력] host,user,found_password_index,status,새비번적용여부
```

`run.sh`는 요청하신 대로 "실행 편의용 bash 스크립트"이며, `go build`, 인자 유효성 검사, `pwreset` 호출만 담당하고
실제 로직은 전부 Go 쪽(`pwreset`)에 둡니다.

## 4. 검증 가능한 성공 기준

1. csh 로그인 셸 + 패턴 A(3단계) 서버에서 정상적으로 current password를 찾아내고 비번 변경 성공.
2. bash 로그인 셸 + 패턴 B(2단계) 서버에서도 동일하게 성공.
3. 변경 직후 세션이 즉시 끊기는 서버 / 유지되는 서버 둘 다 "성공"으로 정확히 분류.
4. `old_password.txt`의 모든 항목이 실패하는 서버는 결과 파일에 "접속불가"로 명확히 기록.
5. `newpass.enc`에 `asdf`를 암호화해 넣고 실행하면, 실제 서버 비밀번호가 `asdf`로 바뀌는 것을 재로그인으로 확인 가능.
6. 동일 old_password.txt로 재실행 시(비번이 이미 바뀐 상태) 새 비번(맨 위 항목이 최신으로 갱신됐다고 가정)으로 즉시 로그인 성공 — 즉, 실행 후 `old_password.txt`에 새로 적용된 비번을 맨 위에 자동 추가하는 것도 옵션으로 고려(질문 4번 참고).

## 5. 확인이 필요한 부분 (애매해서 질문드립니다)

1. **대상 범위**: 이번 스크립트는 록키 리눅스 서버(192.168.0.58) 한 대만 대상인가요, 아니면 홈랩 내 다수의 RHEL 계열 서버를 대상으로 확장해야 하나요? (targets.csv로 다중 서버 지원을 기본으로 넣을지 결정)
2. **계정**: root 계정만 대상인가요, 아니면 일반 계정도 포함되나요? (root면 `PermitRootLogin`, PAM 정책이 계정별로 다를 수 있어 프롬프트 패턴에 영향)
3. **비밀번호 변경이 트리거되는 조건**: `chage`로 강제 만료시킨 계정이라 로그인 시 무조건 변경 프롬프트가 뜨는 상황인가요, 아니면 특정 조건(예: 90일 경과)에서만 뜨나요? 이에 따라 "로그인만 성공하고 변경 프롬프트가 없는 경우"도 처리해야 하는지 결정됩니다.
4. **비번 변경 후 old_password.txt 갱신 여부**: 성공적으로 바꾼 새 비밀번호를 `old_password.txt` 맨 위에 자동으로 추가해서 이력을 계속 쌓을까요, 아니면 이 파일은 읽기 전용 이력이고 갱신은 수동으로 하실 건가요?
5. **암호화 키 관리**: 새 비밀번호 암호화에 쓸 키를 어디에 둘지(같은 서버의 파일 / 환경변수 / 매 실행시 프롬프트 입력) 선호가 있으신가요? 록키 리눅스 로컬 파일로 두는 걸 기본안으로 생각 중입니다.
6. **동시 실행 정책**: 계정 잠금(lockout) 정책이 걸려있는 서버가 있나요? 있다면 old_password.txt를 위에서부터 하나씩 시도할 때 실패 횟수 제한에 걸리지 않도록 시도 간격(딜레이)을 둬야 합니다 — 필요하면 반영하겠습니다.
7. **`Current password` 프롬프트가 뜨는 경로**: SSH 인증 단계(keyboard-interactive)에서 뜨는지, 아니면 로그인 성공 후 셸에서 `passwd` 명령이 자동 실행되어 뜨는 것인지 확인 부탁드립니다(실제 서버에서 `ssh -v`로 한번 확인해주시면 상태머신을 더 정확히 만들 수 있습니다). 두 경로 모두 있을 수 있다고 하셨으니 우선 둘 다 지원하는 걸로 설계했습니다.

## 6. 더 나은 대안 제안

- **expect 대신 Go**: 요청대로 진행하되, Go의 `golang.org/x/crypto/ssh`는 pty 없이도 keyboard-interactive 콜백으로
  비번 변경 프롬프트를 처리할 수 있어 expect보다 안정적이고 병렬 처리가 쉽습니다. 다만 셸에서 `passwd`가 실행되는
  케이스가 섞여 있다면 pty 세션(`golang.org/x/crypto/ssh` + `session.RequestPty` + stdin/stdout 파이프)도 함께 써야 하므로,
  질문 7번 답변에 따라 최종 구현 방식을 확정하는 게 안전합니다.
- **결과 파일 분리**: "접속불가" 기록을 old_password.txt에 직접 쓰기보다, 별도의 `result.csv`에 성공/실패/시도한 비번 인덱스를
  남기는 걸 추천드립니다 — old_password.txt는 순수 이력 파일로 유지하는 게 재사용성이 좋습니다.
- **드라이런 모드**: `-dry-run` 플래그로 실제 비번 변경 없이 "어떤 비번으로 로그인되는지"만 확인하는 모드를 추가하면
  운영 중 실수 방지에 도움이 됩니다.
