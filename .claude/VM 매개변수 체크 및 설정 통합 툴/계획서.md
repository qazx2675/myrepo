## 0. 사전 확인 결과 (요청하신 검증)

### 0-1. "설정체크 스크립트에 정상값을 입력하는 부분이 있다" → **맞습니다**

`VM 매개변수설정체크/main.go` 의 CLI 플래그가 곧 정상값(기대값) 입력부입니다.

| 구분 | 플래그 | 필수 여부 |
|---|---|---|
| 공통(ev01·미분류) | `-cpu` `-cores` `-numa` `-mem` `-disk` `-shares-ev01` `-ht` | **필수** |
| ev02 전용 | `-cpu-ev02` `-cores-ev02` `-numa-ev02` `-mem-ev02` `-disk-ev02` `-shares-ev02` | 옵션(없으면 해당 체크 스킵) |
| ev03 전용 | `-cpu-ev03` `-cores-ev03` `-numa-ev03` `-mem-ev03` `-disk-ev03` `-shares-ev03` | 옵션 |
| affinity | `-affinity-ev01`(미지정 시 `-ht`+vCPU로 자동계산) `-affinity-ev02` `-affinity-ev03` | 옵션 |

고정 기대값(입력 불필요)은 `checker/fixed.go` 에 하드코딩되어 있습니다:
`sched.mem.lpage.enable1GPage=TRUE`, `sched.mem.prealloc=TRUE`, `sched.mem.prealloc.pinnedMainMem=TRUE`, `sched.swap.vmxSwapEnabled=FALSE`.
(`sched.mem.pin` 은 vCenter Advanced Config에 기록되지 않아 **체크 대상에서 의도적으로 제외**되어 있습니다 — 반면 `main_lpage.go` 는 이 키를 씁니다. 3-4 참고)

### 0-2. "main_lpage.go에 ev03가 없다" → **맞습니다**

`main_lpage.go` 는 `-ev01*` / `-ev02*` 플래그만 있고 대상 VM도 `cleanHost+"ev01"`, `cleanHost+"ev02"` 두 개만 만듭니다. ev03 추가 필요.
반면 **`main_affinity.go` 는 이미 ev03을 지원**합니다 (`-affinityFile03`, `-vm_cnt=3`, `maxVMCount=3`). 즉 ev03 추가 작업은 **lpage 쪽만** 해당됩니다.

### 0-3. ⚠️ 이게 "새로 만들어야 하는" 진짜 이유 (중요)

`main_lpage.go` 의 값 의미와 `vm-param-check` 의 기대값 의미가 **서로 다릅니다.** 기존 스크립트를 그대로 재활용하면 교정 직후 재검증이 FAIL로 뜹니다.

| 항목 | main_lpage.go 가 쓰는 값 | vm-param-check 가 기대하는 값 | 결과 |
|---|---|---|---|
| `cpuid.coresPerSocket` | `ev01Cores / ev01Sockets` | `-cores` | 우연히 같을 때만 OK |
| `numa.vcpu.maxPerVirtualNode` | **`coresPerSocket` 값을 그대로 씀** | `-numa` (NUMA 노드당 최대 vCPU) | `-cores ≠ -numa` 면 **FAIL** |
| `numaInfo.coresPerNumaNode` | `ev01Cores / ev01Numa` (`-ev01Numa`=노드 **개수**) | `-numa` | 의미 자체가 다름 → **FAIL** |
| 입력 단위 | `Cores`=총 vCPU, `Sockets`=소켓 수 | `-cpu`=vCPU, `-cores`=소켓당 코어 | 사용자가 매번 환산해야 함 |

→ **결론: 신규 교정기는 "체크에 입력한 정상값을 그대로 쓴다".** 환산·재해석 없이 `-cpu → NumCPUs`, `-cores → NumCoresPerSocket & cpuid.coresPerSocket`, `-numa → numa.vcpu.maxPerVirtualNode & numaInfo.coresPerNumaNode` 로 1:1 기록. 이러면 체크 → 교정 → 재검증이 논리적으로 항상 닫힙니다.

### 0-4. 캡처(Edit Settings → VM Options → CPU Topology) 반영

캡처의 `Cores per Socket = "Assigned at power on"` 은 `NumCoresPerSocket` 이 **미설정** 상태라는 뜻입니다. ExtraConfig(`cpuid.coresPerSocket`)만 넣으면 이 UI는 계속 "Assigned at power on" 으로 남습니다.
→ 교정기는 **반드시 하드웨어 필드까지** 씁니다: `ConfigSpec.NumCPUs`, `ConfigSpec.NumCoresPerSocket`, `ConfigSpec.VirtualNuma.CoresPerNumaNode`.
→ 검증 단계에서 API 재조회(`hardware.numCoresPerSocket`, `config.numaInfo.coresPerNumaNode`)로 확인하고, **vSphere Client UI에서 눈으로도 한 번 확인**합니다(캡처와 동일 화면에 숫자가 찍히는지).

## 1. 목표

기존 3단계(체크 실행 → CSV 생성 → 별도 수정 스크립트 실행)를 **바이너리 1개 / 명령 1줄**로 통합한다.

```
[정상값 입력] → 설정체크 → CSV 생성(_user) → "수정할까요? (y/N)" → 교정 → 재검증 CSV
```

**포함**: 통합 CLI, `-user` 옵션, 신규 교정기(govmomi 직접 Reconfigure, ev01/ev02/ev03), 안전 게이트, 재검증, 실환경 테스트, git 업로드.
**제외**: 호스트 고성능 전원정책 변경(`power_setting`) — 요청대로 이번 범위 밖. FAIL이 있으면 "수동조치 필요"로만 출력.
**제외**: 메모리/디스크/Shares/네트워크 — 자동교정 대상 아님(수동조치 안내).

## 2. 산출물 구조

기존 `VM 매개변수설정체크/` 를 그대로 확장합니다. (별도 폴더 신설 X, `FAIL기반 매개변수 수정/` 은 유지하되 이번 통합본이 대체)

```
VM 매개변수설정체크/
├── main.go              (수정) 통합 파이프라인 + -fix / -user / -yes 플래그
├── checker/             (그대로) 체크 로직
├── model/  report/  config/  vcenter/   (그대로)
├── fixer/               ★ 신규
│   ├── plan.go          FAIL/설정없음 → 교정 계획(VM별 ConfigSpec) 산출
│   ├── apply.go         govmomi Reconfigure 실행(워커풀 병렬)
│   ├── gates.go         동질성 검증 + 전원 OFF 검증 (기존 gates.go 이식)
│   └── affinity.go      ev01 자동계산 / ev02·ev03 파일 기반
├── vendor/              (그대로, 오프라인 빌드용)
└── README.md            (갱신) 통합 사용법 + 폐쇄망 빌드 절차
```

**단일 바이너리 방식을 택한 이유**: 외부 도구를 `exec` 로 부르면 ① 인증방식이 갈리고(`VC_USER/VC_PASS` vs `VC_PASSWORD`) ② 값 의미가 어긋나며(0-3) ③ 사용자가 설치 시 값을 또 입력해야 합니다(사용감 문제 — 요청하신 그 지점). 인프로세스로 합치면 정상값이 한 번만 입력되고 그대로 흘러갑니다.

## 3. 상세 설계

### 3-1. CLI (신규/변경 플래그만)

| 플래그 | 의미 |
|---|---|
| `-user <이름>` | CSV 파일명에 접미사. `-out=result.csv -user=kdh` → `result_kdh.csv` / `result_kdh_summary.csv`. `-out` 미지정 시 `vm-param-check_20260816_153000_kdh.csv` |
| `-fix` | 교정 단계까지 진행(미지정 시 체크+CSV까지만, 기존 동작 그대로) |
| `-yes` | 확인 프롬프트 생략(자동화용). 미지정 시 dry-run 출력 후 `y/N` 질문 |
| `-fixOut <경로>` | 재검증 CSV 경로(미지정 시 `<원본>_recheck_<타임스탬프>.csv`, `-user` 동일 적용) |
| `-concurrency <N>` | 교정 동시 처리 수(기본 20, `main_affinity.go` 관례 계승) |

기존 플래그는 **전부 그대로 유지**합니다(하위 호환).

### 3-2. 파이프라인

```
1. 정상값 파싱 + vCenter 접속            (기존 코드 재사용)
2. 체크 실행 → findings
3. CSV 2종 생성 (상세 / 요약, _user 접미사)
4. -fix 없으면 종료  ────────────────────  (= 기존 동작)
5. FAIL/설정없음 → 태그 분류 (lpage / affinity / manual)
6. [게이트] 그룹 동질성 + 전원 OFF  (병렬, 하나라도 실패 시 즉시 중단·무변경)
7. dry-run 출력: VM별로 "무슨 키를 무슨 값으로 바꿀지" 전부 표시
8. "위 내용대로 실제 설정을 변경하시겠습니까? (y/N)"
9. 교정 실행 (워커풀, VM 단위 Reconfigure 1회로 묶음)
10. 재조회 검증 + 재검증 CSV 2종 생성 + 최종 요약
```

**9번의 핵심**: VM 1대당 `Reconfigure` **한 번**에 ExtraConfig + 하드웨어 필드 + affinity 를 모두 담습니다(기존처럼 도구별로 따로 부르면 같은 VM을 2~3번 리컨피그하게 됨).

### 3-3. 교정 대상 매핑 (정상값 → 실제 기록 위치)

| 체크 항목Key | 그룹별 기대값 | 교정 시 기록 위치 |
|---|---|---|
| `sched.mem.lpage.enable1GPage` | TRUE(고정) | ExtraConfig |
| `sched.mem.prealloc` | TRUE(고정) | ExtraConfig |
| `sched.mem.prealloc.pinnedMainMem` | TRUE(고정) | ExtraConfig |
| `sched.swap.vmxSwapEnabled` | FALSE(고정) | ExtraConfig |
| `cpuid.coresPerSocket` | `-cores[-evNN]` | ExtraConfig |
| `hardware.numCoresPerSocket (CPU 토폴로지 UI)` | `-cores[-evNN]` | **`ConfigSpec.NumCoresPerSocket`** ← 캡처 화면 |
| `config.hardware.numCPU` | `-cpu[-evNN]` | **`ConfigSpec.NumCPUs`** ← 캡처 화면 CPU |
| `numa.vcpu.maxPerVirtualNode` | `-numa[-evNN]` | ExtraConfig |
| `config.numaInfo.coresPerNumaNode (CPU 토폴로지 UI)` | `-numa[-evNN]` | **`ConfigSpec.VirtualNuma.CoresPerNumaNode`** |
| `sched.vcpuN.affinity` | ev01=자동계산 / ev02·ev03=파일 | ExtraConfig |
| 메모리 / 디스크 / Shares / 네트워크 / host power policy | — | **교정 안 함, 수동조치 목록에 출력** |

### 3-4. 결정이 필요한 세부사항 (제 제안 + 근거)

1. **`sched.mem.pin`**: 체크는 제외, `main_lpage.go` 는 기록. → **기록은 하되 체크는 그대로 제외** 제안. 기존 설정 스크립트와 실제 VMX 상태를 맞추기 위함이고, 체크에 넣으면 vCenter가 값을 안 돌려줘서 영구 FAIL이 됩니다.
2. **ev03 규칙**: 요청대로 **ev02와 완전 동일**. VM명 `<host>ev03`, 플래그 `-cpu-ev03/-cores-ev03/-numa-ev03/-affinity-ev03`, 해당 옵션이 없으면 ev03 교정 스킵.
3. **ev02/ev03 옵션 미지정 + 해당 그룹 FAIL 존재** 시: 조용히 건너뛰지 않고 **경고 후 해당 VM만 스킵**(ev01 값을 대신 쓰지 않음 — 스펙이 다를 수 있음).
4. **VM 1대뿐인 경우**: 기존 3-0 규칙(ev02/ev03 체크 스킵)이 그대로 적용되므로 교정 대상도 자동으로 ev01/공통 항목만 남습니다.

### 3-5. 안전장치 (기존 `FAIL기반 매개변수 수정/gates.go` 이식)

- **그룹 동질성**: ev01끼리 / ev02끼리 / ev03끼리 vCPU·코어·메모리·디스크·Shares·NUMA·HT 동일 + 그룹 간 대수 동일
- **전원 OFF**: 대상 VM 중 하나라도 켜져 있으면 중단 (하드웨어 토폴로지 변경이라 필수)
- **dry-run 우선**: 무조건 변경 내역을 먼저 다 출력한 뒤 확인
- 게이트 실패 시 **아무것도 변경하지 않고 종료**

| 8 | **실환경 테스트** (vCenter 192.168.0.50 / ESXi 192.168.0.59) | ev01·ev02·ev03 각 1대 대상, 교정→재검증 전부 OK |
| 9 | **UI 확인** | vSphere Client → Edit Settings → VM Options → CPU Topology 에서 `CPU`, `Cores per Socket` 이 "Assigned at power on"이 아니라 **입력한 숫자로 표시**됨 (캡처와 동일 화면 캡처로 증빙) |
| 10 | README 갱신 + git push | 폐쇄망 다운로드→빌드 절차 포함, `master` 반영 |

> 8·9번은 실제 vCenter의 VM 설정을 변경합니다. **전원 OFF 상태의 테스트 VM에만** 수행하며, 실행 전 대상 목록을 확인받고 진행하겠습니다.
