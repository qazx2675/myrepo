# BM 전원 고성능 설정(power_setting) + vm_setup.sh MAC 수집 — 계획서 / 작업 기록

작업일: 2026-09-25 · 브랜치: `claude/determined-rubin-yw9r2d` · 대상: `.claude/VM/V2/VMsetup`

## 1. 요청

1. `power_setting`이 없다 → **VM이 아닌 BM(ESXi 호스트)에 전원 정책 "고성능"** 을 설정하는 도구를 만든다.
   - 기존 `VMsetup/<이름>-source/` 양식(main.go, go.mod/go.sum, setup.sh, README.md)을 따른다.
   - 입력: vCenter + 작업 대상 파일(`{user}.txt`)만 있으면 실행.
   - `{user}.txt`에는 도메인 없이 **hostname만** 적어도 동작해야 한다.
   - 다른 도구처럼 병렬 실행, 기본 계정 `lscsystems@vsphere.local`.
2. `vm_setup.sh`에 MAC 주소 수집(mac_info)이 없다 → 추가. 수집 결과는 `awx_route=""` 경로에 `{user}.txt`로 복사.
3. FQDN(짧은 이름 매칭) 기능이 수천 대에서 느려지지 않는지 검토.

## 2. 아키텍처 — power_setting

```
{user}.txt (hostname 또는 FQDN, 첫 칸만)
      │ readLines + 중복 제거
      ▼
vCenter 접속 (-vcTargetIP, -id=lscsystems@vsphere.local, VC_PASSWORD)
      │
      ▼
ContainerView(RootFolder, HostSystem) ── Retrieve 1회 ──▶ 모든 호스트의
      name / configManager.powerSystem / config.powerSystemInfo / config.powerSystemCapability
      │
      ▼
이름 맵 2개: hostByName[정확한 이름], hostByShort[첫 '.' 앞]
lookupHost(bm): 정확한 이름 → 짧은 이름(1대일 때만, 2대 이상이면 에러)   ← vswitch_setting / vm_create 와 같은 규칙
      │
      ▼
워커풀 (-concurrency, 기본 20) — 호스트마다:
   고성능 key 찾기: availablePolicy 중 shortName "static" 또는 name "High Performance" (없으면 1)
   현재 정책 == key → 스킵
   아니면 HostPowerSystem.ConfigurePowerPolicy(key)
      │
      ▼
요약: 성공 / 스킵 / 실패  (실패 ≥1 → 종료코드 1)
```

| 결정 | 이유 |
|---|---|
| 호스트 정보는 Retrieve 1번 | 호스트 수천 대여도 왕복 1회. 호스트별 조회 없음 |
| 이름 규칙은 `vswitch_setting`의 `lookupHost` 복사 | 도구들끼리 같은 규칙 유지(요청: hostname만으로 동작) |
| 정책 key를 호스트가 준 목록에서 찾음 | ESXi 버전별 key 차이 대비. 이름 `High Performance`는 vm-param-check `host power policy` 기대값과 동일 |
| 이미 고성능이면 스킵 | 재실행 안전 |
| `vm_setup.sh`에는 넣지 않음 | 요청이 "vCenter와 작업대상파일만 받으면 실행" — 단독 실행 도구 |

## 3. vm_setup.sh — MAC 수집 단계

- 위쪽 변수: `awx_route=""`, `MAC_ARG1`/`MAC_ARGINT`/`MAC_ARGSTR`(환경변수로도 가능).
  `mac_info`는 `-arg1`/`-argStr`이 필수라 값을 받을 자리를 만들었다. **비어 있으면 경고 후 건너뜀.**
- 순서: … lpage_setting → 스펙 체크 → **7. mac_info** → [완료]
- `mac_info`는 실행 폴더(`run_<user>/`)에 `Provisioning_List_<vCenter의 . → _>.txt` 생성 → `awx_route`가 있으면 `awx_route/<user>.txt`로 복사(폴더 없으면 생성, 복사 실패는 중단).
- 실행 계획 출력에 MAC 수집 줄 추가, 실행파일 확인 목록에 `mac_info` 추가.

## 4. FQDN(짧은 이름 매칭) 속도 검토 — 수천 대

**결론: 이름 매칭 자체는 수천 대여도 느려지지 않는다.**

- 매칭은 DNS 조회가 아니라 **문자열 비교**다(`net.Lookup*` 사용 없음). 네트워크 비용 0.
- 호스트 목록을 한 번 받아 맵 2개를 만들고(O(호스트 수)), BM마다 맵 조회(O(1)). 5,000대 기준 수 ms 수준.
- 실제 시간은 vCenter 호출 횟수가 정한다:

| 도구 | 조회 방식 | 수천 대에서 |
|---|---|---|
| `power_setting`, `vswitch_setting`, `vm_create`, `license_assign` | ContainerView Retrieve 1회 | 문제 없음 |
| `lpage_setting`, `nic_assign`, `tag_setting` | VM 이름 Retrieve 1회 | 문제 없음 |
| **`mac_info`** | `VirtualMachineList("*")` 후 **매칭 VM마다 `vm.Properties` 순차 호출** | **VM 수만큼 왕복(순차)** — VM 수천 대면 수 분 걸릴 수 있음 (FQDN과는 무관) |
| `affinity_setting`, `numa_preferht_setting` | 데이터센터별 `VirtualMachineList` + 일괄 Retrieve | 보통 |

- 주의할 점(속도 아님): 짧은 이름이 같은 호스트가 2대 이상이면(예: 다른 도메인에 같은 hostname) 어느 쪽인지 정하지 않고 **에러**로 멈춘다 → 그 호스트만 FQDN으로 적으면 된다.
- 개선 제안(이번 작업 범위 밖, 요청 시 진행): `mac_info`를 ContainerView로 `name`+`config.hardware.device`를 한 번에 Retrieve 하도록 바꾸면 호출 1회로 줄어든다. 데이터 양이 크면 `vm_setup.sh`가 넘기는 BM 목록에 해당하는 VM 참조만 골라 Retrieve.
