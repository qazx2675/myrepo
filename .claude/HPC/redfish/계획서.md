## 1. 목표

관리망 BMC 에 Redfish 로 접속해 BIOS 표준값(프로파일별)을 **점검**하고, 사용자가 승인(Y)한 FAIL 항목만 **Pending 으로 설정**한다.

- 재부팅은 **절대 하지 않는다.** 설정은 BMC 의 Pending(다음 재부팅 시 반영)까지만. OS 설치 과정의 재부팅에서 반영된다.
- 테스트 장비가 없으므로 **실제 OS 설치 요청 장비에서 모델별로 하나씩** 검증해 나간다. 한 번에 완성하지 않는다.
- 운영자는 Redfish 를 처음 사용 → 도구가 위험한 동작을 코드 레벨에서 막아야 한다.

## 2. 확정 사항 (인터뷰 결과)

| 항목 | 결정 |
|---|---|
| 언어/구조 | Go(실제 작업) + bash(실행 편의) 쌍. Go 는 **표준 라이브러리만** 사용 (폐쇄망, vendor 불필요) |
| 대상 | 5개 벤더(Dell, HPE, Cisco, Lenovo, Supermicro) 전 모델. 엑셀 표는 예시일 뿐 |
| Cisco UCSM 관리형 / Supermicro X11 이하 | 1차는 **점검만**(Redfish 로 읽히면), 설정 제외. 못 읽으면 `UNSUPPORTED` — **구현 반영:** 쓰기는 Dell·HPE·Lenovo 만 하고 그 밖의 벤더는 접속 없이 `SET_NOT_SUPPORTED_VENDOR` |
| 사전조사(`xml.sh`) | Redfish 응답 **JSON 덤프** + 사람이 읽고 옮겨 적을 수 있는 **짧은 요약**. 폐쇄망이라 반출 불가 → 사용자가 요약을 보고 전달 |
| 입력 | `user.txt` 한 줄에 대상 하나: `hostname` / `hostname-m` / `IP` |
| 이름 해석 | `hostname` → `/etc/hosts` 에서 `hostname-m` 의 IP 조회. `hostname-m` → `/etc/hosts` 조회. IP → 그대로 |
| 프로파일 | VM, BM … 실행 시 **메뉴로 선택**. 프로파일 = 표준값 파일 1개. BM 추가 시 파일만 추가하면 동작 |
| 계정 | ID 는 conf, 비밀번호는 **AES-256-GCM 암호화 파일**(`pass.enc` + `key.bin`, 0600) — `패스워드변경자동화` 방식 재사용 |
| TLS | conf 기본값 `insecure=true`(자체서명 BMC 전제), 필요 시 false |
| 규모 | 한 번에 **수천 대**. 동시 접속 기본 100, 자동 재시도, 실패 목록 재실행 — **구현 반영:** 재시도는 GET·세션 연결 실패만, 실패 목록 재실행은 `-retry-from`(병합 `merged_*`), 계정 잠금 방지용 AUTH_FAIL 차단기 `auth_fail_stop` 추가 |
| 결과 파일 | **TSV**. 열: `hostname ip profile vendor model bios_version std_name attribute expected current pending result` |
| 터미널 출력 | 리포트 형식: OK 호스트 목록 → FAIL 상세(호스트·항목) → `설정하시겠습니까? (Y/N)` |
| Y 동작 | FAIL 전체 일괄 Pending 설정 → 재조회로 Pending 반영 확인 → **적용된 hostname 목록 출력**. 재부팅 없음 — **구현 반영:** 비대화형(파이프·파일) 표준입력의 Y 는 N 으로 처리하고 `-stdin-ok` 로만 예외(경고 출력), 설정 직전에 다시 읽어 점검 이후 변화를 확인 |
| 미검증 모델 | 프로파일 행에 `verified=Y` 인 모델만 Y 적용. 아니면 dry-run(보낼 PATCH 본문 출력)만 — **구현 반영:** `verified=Y` 는 **모델을 지정한 행에만** 가능, `*` 행에 쓰면 프로파일 로드 오류 |
| 기존 Pending/Job 존재 | 건드리지 않고 `PENDING_EXISTS` 로 보고, 설정 제외. **남의 Job/Pending 절대 삭제 안 함** |
| 새 모델(매핑 없음) | 이름 후보 자동 탐색 → 실패 시 `MAPPING_MISSING` + 해당 호스트 덤프·요약 자동 저장, Y 대상 제외 — **구현 반영:** 후보 탐색은 판정하지 않고 `후보:` 로 **보여 주기만** 하며, 프로파일에 모델 행도 `*` 행도 없으면 `MAPPING_MISSING`(모델당 1대 덤프·요약을 `results/<일시>/mapping_missing/` 에 저장) |
| 실행 OS | RHEL6, RHEL8 둘 다. 빌드 완료 바이너리를 저장소에 커밋 (회사엔 Go 없음) |

### 설계 변경 이력 (구현 중 인터뷰 결정에서 바뀐 것)

| 항목 | 인터뷰 때 | 구현 |
|---|---|---|
| `*`(벤더 공통) 프로파일 행의 `verified` | 규정 없음 | `verified=Y` 불가(로드 오류). `*` 행은 점검 비교용, 설정은 모델 지정 행만 (단계 6 보안 리뷰) |
| Y/N 입력 | 터미널 입력 | 표준입력이 터미널이 아니면 N 처리, `-stdin-ok` 로만 읽음. `-no-prompt`·`-dry-run`·`-from-dump` 는 묻지 않음 |
| AUTH_FAIL | 즉시 중단·재시도 금지 | + 차단기 `auth_fail_stop`(기본 3, 0 이면 끔): 처음 N 대 직렬 웜업 → 로그인 성공 시 병렬, 누적되면 새 호스트 중단 + `SKIPPED_AUTH_STOP`(재시도 대상). check·dump·allcheck·set 공통 |
| Dell 설정 | PATCH 후 Job 생성 | PATCH 가 Job 을 자동 생성했는지 엄격히 판정(HTTP 202 또는 `JobType=BIOSConfiguration`·실행 전 상태 Job 확인)하고, 아닐 때만 `TargetSettingsURI` 하나만 담은 Job 을 최대 1회 POST. Pending 은 기대값인데 BIOS 설정 Job 이 없으면 `PENDING_NO_JOB`(verified=Y 이고 남의 Pending 이 없을 때만 같은 값 재PATCH + Job), Job 존재를 확인하지 못하면 쓰지 않음 |
| 시스템 프로파일 종속 | 레지스트리로 검사, 프로파일 항목 먼저 | 목표 프로파일이 `Custom` 이 아니면(또는 레지스트리를 못 읽으면) 프로파일 항목만 보내고 나머지는 `DEPENDS_ON_PROFILE` — 재부팅 후 재점검해 다시 설정 |
| `diff.txt` 의 모델 칸 | 모델 자동 조회 | 적어도 **확인용**일 뿐, 분류는 항상 BMC 가 보고한 모델. 다르면 `DIFF_TXT_MODEL_MISMATCH` 경고 |
| 쓰기 결과 | 적용 목록 출력 | `apply_result.tsv`·`applied.txt`·`apply_failed.txt`·`apply_requests.txt` 저장. 설정은 **자동 재시도하지 않음**(비멱등), 결과 불명은 `SET_ERROR`·`APPLY_UNCONFIRMED` 로 재점검 요구 |
| 같은 BMC 중복 | 규정 없음 | `host`·`host-m`·IP 가 같은 BMC 를 가리키면 설정은 첫 대상 1회만(`DUPLICATE_TARGET`) |
| 속성값 비교 | 문자열 | 문자열(대소문자 정확)이되, 둘 다 10진 정수면 정수로 비교(`05` = `5`) |
| 소스 구조 | `vendor_*.go` 로 벤더 분리 | 벤더 차이는 `inspect.go`(판별·정규화)·`set.go`(Dell Job 등)에 두고 `vendor_*.go` 는 만들지 않음. 4장 구조도 갱신 |
| 이름 후보 자동 매핑 | 후보 이름으로 레지스트리 탐색해 판정 | 판정은 프로파일의 후보 행(`std_name` 별 여러 줄, 파일 순서가 우선순위)으로만, 키워드 탐색(`stdKeywords`)은 `MAPPING_MISSING` 때 후보를 **보여 주는** 용도 |

## 3. 로그 안전장치 (요구사항 3)

Dell iDRAC Lifecycle Log, HPE iLO Event Log 등은 **로그인/설정 변경을 기록**한다. 도구가 남기는 흔적을 최소화하고, 기존 로그는 절대 건드리지 않는다.

1. **세션 1회**: 호스트당 `POST /redfish/v1/SessionService/Sessions` 1회 → X-Auth-Token 으로 모든 요청 → 끝나면 자기 세션만 DELETE. (요청마다 Basic 인증을 하면 로그인 기록이 요청 수만큼 쌓일 수 있음)
2. **호출 허용목록(allowlist)** — 전송 직전 코드에서 검사, 목록 외 요청은 보내지 않고 에러:

   | 메서드 | 허용 경로 | 모드 |
   |---|---|---|
   | GET | 아래 순회 대상만 (LogServices 하위 **제외**) — **구현 반영:** `/redfish/v1` 아래 GET 은 허용하되 로그·Actions·SSE 세그먼트(`LogServices`·`SEL`·`Entries`·`*Log`·`*Logs`·`Actions`·`sse` 등)는 거부 | 전 모드 |
   | POST | `SessionService/Sessions` | 전 모드 |
   | POST | Dell `Managers/*/Jobs` (BIOS 설정 Job 생성) | set + verified |
   | PATCH | `Systems/*/Bios/Settings` (Lenovo 등은 `Bios/Pending` 등 레지스트리에서 확인한 SettingsObject) | set + verified |
   | DELETE | **자기가 만든 세션 URI 1개** | 전 모드 |

   → `ClearLog`, LogService/Job 삭제, 리셋(`ComputerSystem.Reset`) 등은 경로 자체가 목록에 없어 **구조적으로 불가능**.
3. **호출 수 최소화**: ServiceRoot → Systems → Bios → Bios/Settings → (레지스트리는 `벤더|모델|BIOS버전` 키로 캐시, 같은 기종은 1회만).
4. **AUTH_FAIL(401) 즉시 중단·재시도 금지** — 공통 계정 잠금 및 로그인 실패 로그 누적 방지. **구현 반영:** 401 뒤에는 그 호스트로 더 이상 요청을 보내지 않고, 호스트 전체로는 `auth_fail_stop` 차단기가 새 호스트 접속을 멈춥니다.
5. 남는 흔적(불가피): 호스트당 로그인/로그아웃 기록 1쌍, set 시 설정 변경/Job 기록. README 에 명시하고, 짧은 간격 반복 실행을 피하도록 안내. **구현 반영:** 세션 미지원 BMC 는 Basic 폴백(`auth=basic`)이라 요청마다 인증 기록이 남을 수 있고, 같은 BMC 로 가는 연속 요청은 100ms 이상 간격을 둡니다.

### 프로파일 파일 형식 (`profiles/VM.tsv`)

엑셀 표를 그대로 옮길 수 있도록 탭 구분, 1행 = 벤더·모델·항목 1개.

```
vendor	model	std_name	attribute	value	verified
DELL	R660	system_profile	SysProfile	PerfOptimized	N
DELL	R660	hyper_threading	LogicalProc	Enabled	N
DELL	*	llc_prefetch	LlcPrefetch	Enabled	N
HPE	DL360 Gen11	hyper_threading	ProcHyperthreading	Enabled	N
```

- `model` 은 정확히 일치 우선, 없으면 `*`(벤더 공통) 사용.
- `*` 행은 **점검 비교용**이며 `verified=Y` 를 쓸 수 없다 (프로파일 로드 오류). 설정(Y)은 모델을 지정한 `verified=Y` 행에만 허용된다 (단계 6 보안 리뷰 W).
- `verified=Y` 는 실장비에서 dry-run 결과를 사람이 확인한 뒤에만 표시. **구현 반영:** `A|B` 로 허용값 여러 개(설정 시 첫 값 전송), 값 비교는 대소문자까지 정확, 같은 `std_name` 의 여러 행은 속성 이름 후보(파일 순서가 우선순위), 표준 4항목은 행이 없어도 항상 점검(→ `MAPPING_MISSING`), 그 밖의 `std_name` 행은 추가 항목.
- 매핑 없는 모델: 내장 후보 이름 목록(예: hyper_threading → `LogicalProc`, `ProcHyperthreading`, `Hyperthreading`, …)으로 레지스트리 탐색, 기대값은 같은 벤더 `*` 행 값 사용. 그래도 없으면 `MAPPING_MISSING`. **구현 반영:** 모델 행이 없으면 같은 벤더 `*` 행을 쓰고, 둘 다 없거나 후보 속성이 BMC 에 없으면 `MAPPING_MISSING` — 이때 키워드(`stdKeywords`)로 찾은 후보 속성(현재값·허용값·ReadOnly)을 보여 주고 덤프·요약을 저장할 뿐 자동으로 판정·설정하지 않습니다.
- 엑셀 검증 필요 값(Dell `Performance` vs `PerfOptimized`, HPE `ProHyperthreading` 오타, `HighPerformanceCompute(HPC)` 표기)은 첫 실장비 덤프로 확정.

### 결과 상태

소스의 실제 상수 기준입니다(`check.go`·`redfish.go`·`resolve.go`·`sweep.go`·`set.go`·`allcheck.go`).

#### 점검 — 항목 단위 (`result.tsv` 의 `result`)

| 상태 | 의미 | 자동 재시도 | Y 대상 |
|---|---|---|---|
| OK | 현재값 = 기대값 | - | - |
| PENDING_OK | 현재값은 다르나 Pending 이 기대값 (재부팅 대기). Dell 은 예약된 BIOS 설정 Job 확인 | - | - |
| FAIL | 현재값 ≠ 기대값 (`verified=Y` 행) | - | ○ |
| UNVERIFIED | FAIL 이지만 미검증 모델(`verified=N`) → dry-run 시험 출력만 | - | × |
| PENDING_EXISTS | 다른 Pending(우리 항목이 아니거나 기대값도 현재값도 아닌 값)이 이미 있음 — 건드리지 않음 | - | × |
| **PENDING_NO_JOB** | Dell: Pending 은 기대값이나 예약된 BIOS 설정 Job 이 없음(재부팅해도 반영 안 될 수 있음) | - | ○ (`verified=Y`·남의 Pending 없음일 때만) |
| MAPPING_MISSING | 프로파일에 이 모델 행이 없거나 후보 속성이 BMC 에 없음 → 덤프 자동 저장 | × | × |

#### 점검 — 호스트 단위 (`std_name` 이 `-` 인 한 행)

| 상태 | 의미 | 자동 재시도 | `retry.txt` |
|---|---|---|---|
| UNREACHABLE | 연결 거부 / no route / DNS / TLS 실패 | ○ (지수 백오프, conf `retries`) | ○ |
| TIMEOUT | 응답 시간 초과 | ○ | ○ |
| BMC_ERROR | 5xx | ○ | ○ |
| AUTH_FAIL | 401(로그인 403 포함) | **금지** | × |
| **SKIPPED_AUTH_STOP** | AUTH_FAIL 차단기가 작동해 접속하지 않음 | - | ○ |
| UNSUPPORTED | Redfish BIOS 미지원 (`/redfish/v1` 404, Bios 리소스 없음·Attributes 비어 있음 — UCSM 관리형, Supermicro X11 등) | × | × |
| HTTP_ERROR | 그 밖의 4xx·3xx·응답 해석 실패 (계획서 초안에 없던 보조 상태) | × | × |
| NO_HOSTS_ENTRY | `/etc/hosts` 에 `hostname-m` 없음 | × | × |
| **NO_DUMP** | `-from-dump` 폴더에 그 호스트 덤프가 없음 | × | × |

#### 설정(Y) — 항목 단위 (`apply_result.tsv` 의 `status`, 설정은 **자동 재시도 없음**)

| 상태 | 의미 | `apply_failed.txt` |
|---|---|---|
| **APPLIED** | PATCH 후 Settings 재조회로 Pending 반영 확인 | |
| **APPLY_UNCONFIRMED** | PATCH 는 받아들여졌으나 반영 확인 불가(재조회 실패·불일치·Dell Job 생성 실패) | ○ |
| **ALREADY_OK** | 재조회해 보니 현재값 또는 Pending 이 이미 기대값 → 쓰지 않음 | |
| **CHANGED** | 점검 이후 모델·Settings 경로·속성이 바뀜 → 쓰지 않음 | |
| PENDING_EXISTS | 점검 이후 남의 Pending 이 생김 → 쓰지 않음 | |
| UNVERIFIED | 프로파일 재검증 실패(모델 지정 `verified=Y` 행 없음·모델명 비어 있음) | |
| **SKIPPED_READONLY** | 레지스트리에서 ReadOnly → 보내지 않음 | |
| **INVALID_VALUE** | 허용값 밖·형식 불일치·위험 속성명 등 안전 검사 거부 → 보내지 않음 | |
| **DEPENDS_ON_PROFILE** | 시스템 프로파일 변경이 먼저 → 재부팅 후 재점검해 다시 설정 | |
| **SET_NOT_SUPPORTED_VENDOR** | Dell·HPE·Lenovo 외 → 쓰지 않음(접속도 안 함) | |
| **DUPLICATE_TARGET** | 같은 BMC 를 가리키는 앞의 대상에서 처리 → 두 번 쓰지 않음 | |
| **REJECTED** | BMC 가 400 등으로 거부 | ○ |
| **SET_UNSUPPORTED** | 404/405/501, Settings·Job 경로를 만들 수 없음(허용목록 밖 포함) | ○ |
| **SET_ERROR** | 5xx·타임아웃·연결 끊김: 쓰기 결과 불명(재시도하지 않음, 재점검 필요) | ○ |
| AUTH_FAIL · SKIPPED_AUTH_STOP · UNREACHABLE · TIMEOUT · BMC_ERROR · HTTP_ERROR · UNSUPPORTED | 쓰기 전 로그인·조회 단계의 호스트 오류 | ○ |

#### 전체 비교(all_bios_check, 8장)

| 상태 | 의미 | `retry.txt` |
|---|---|---|
| **SAME** / **DIFF** | 제외 속성을 뺀 모든 속성이 같음 / 차이 있음(속성 단위: `DIFF`·`ONLY_REF`·`ONLY_HOST`) | |
| **REFERENCE** | 기준 호스트 자신이라 같은 모델의 다른 기준이 없어 비교하지 않음 | |
| **NO_REFERENCE** | 이 모델의 기준 호스트가 `diff.txt` 에 없음 | |
| **REF_UNREACHABLE** | 이 모델의 기준일 수 있는 호스트를 모두 읽지 못함 | ○ |
| 호스트 오류 | 점검의 호스트 단위 오류와 같음(재시도 대상도 같음) | |
| 특이사항 | `BIOS_VER_DIFF`·`MULTI_REF`·`DIFF_TXT_MODEL_MISMATCH` | |

### 반복 절차: 새 모델 장비가 올 때마다 (요구사항 4)

1. `bash xml.sh <대상>` → 덤프 + 요약 출력
2. 사용자가 요약(AttributeName / 현재값 / 허용값 / ReadOnly / SettingsObject 경로)을 확인해 전달
3. `profiles/VM.tsv` 에 해당 모델 행 추가/수정 (`verified=N`)
4. `bash bios_check.sh` → FAIL 이면 dry-run 으로 PATCH 본문 확인
5. 사람이 확인 후 `verified=Y` → 다음부터 Y 설정 가능
6. OS 설치 재부팅 후 재점검으로 OK 확인

## 6. 가정 (틀리면 알려줄 것)

- `/etc/hosts` 형식은 `IP  hostname-m` (한 줄에 별칭이 여러 개여도 `-m` 이름으로 찾음).
- 공통 계정 1개가 전 벤더 BMC 에 동일하게 존재.
- Dell 은 `Bios/Settings` PATCH 후 BIOS 설정 Job 을 생성해야 다음 재부팅에 반영 (iDRAC 펌웨어에 따라 `@Redfish.SettingsApplyTime` 지원 여부 다름 → 첫 장비 덤프로 확인).
- 프로파일 의존성(Dell SysProfile, HPE WorkloadProfile 이 하위 항목을 덮어쓰거나 ReadOnly 로 만듦)은 레지스트리 `ReadOnly`/`Dependencies` 로 검사하고, 설정 순서는 프로파일 항목 먼저.
- 결과/덤프 디렉터리는 실행 위치 기준 `results/`, `dumps/`. (**구현 반영:** 래퍼는 스크립트 폴더로 이동한 뒤 실행하므로 기본값은 프로젝트 폴더 아래입니다.)

## 8. 추가 기능: 모델별 BIOS 전체 비교 (`all_bios_check.sh`)

표준 4개 항목 점검(`bios_check.sh`)과 별개로, **같은 모델 안에서 정상 호스트(기준) 대비 BIOS Attribute 전체의 값 차이**를 찾는다. **읽기 전용**이며 설정은 하지 않는다(ModeReadOnly 고정).

### 입력
- `diff.txt` — 기준(정상 설정) 호스트. **한 줄에 hostname 만** 적는다 (`#` 주석 허용). 모델은 BMC 에서 자동 조회해 할당하므로 적지 않아도 된다. 예: `checkhostname1`. 뒤에 모델을 적은 줄(`checkhostname1 DL360Gen11`)도 허용하되 확인용으로만 쓴다.
- `user.txt` — 조사 대상 호스트(기존과 동일 형식·`/etc/hosts` 해석 규칙 동일)

### 모델 자동 분류
1. **기준 호스트와 대상 호스트 모두** BMC 에서 Manufacturer/Model(`Systems/*`)을 읽어 모델을 자동 할당한다 (hostname 만 입력).
2. 모델명은 **정규화**해서 비교한다 (소문자, 공백·하이픈 제거, `ProLiant`/`PowerEdge`/벤더명 접두 제거 → `DL360 Gen11`, `DL360Gen11`, `ProLiant DL360 Gen11` 이 같은 키).
3. 분류 기준은 항상 **BMC 가 보고한 실제 모델**이다. `diff.txt` 에 모델을 적었다면 확인용으로만 쓰며, 실제 모델과 다르면 경고(`DIFF_TXT_MODEL_MISMATCH`)하고 실제 모델 기준으로 분류한다.
4. 대상의 모델에 대응하는 기준 호스트가 없으면 `NO_REFERENCE` 로 목록화(비교하지 않음). 같은 모델 기준이 2개 이상이면 BIOS 버전이 같은 쪽 우선, 없으면 첫 번째를 사용한다.
5. 기준 호스트가 `user.txt` 에도 있으면 자기 자신과는 비교하지 않는다. 기준 호스트에 접속 실패하면 그 모델 그룹 전체를 `REF_UNREACHABLE` 로 처리.

### 비교 규칙
- `Bios.Attributes` 의 모든 키/값을 비교 (현재값 기준). 상태: `SAME`, `DIFF`(값 다름), `ONLY_REF`(기준에만 존재), `ONLY_HOST`(대상에만 존재; BIOS 버전이 다르면 흔함).
- 호스트마다 달라야 정상인 속성은 비교 제외: `ignore_attrs.txt`(기본값 예: `ServiceTag`, `AssetTag`, `SerialNumber`, `UefiBootSeq`, `BootSeq*`, `*Uuid*`, `*Mac*`, 시간/날짜). 대소문자 무시, `*` 와일드카드. 제외 항목은 개수만 출력.
- **BIOS 버전이 달라도 조사·비교는 그대로 진행**하고, 차단하거나 건너뛰지 않는다. 버전 차이는 **특이사항**으로 따로 기록·출력한다 (`BIOS_VER_DIFF`: 대상 버전 ≠ 기준 버전; 속성 목록 자체가 달라 `ONLY_REF`/`ONLY_HOST` 가 늘어날 수 있다는 안내 포함).
- 벤더 공통으로 `Bios` 리소스를 읽으며(호출 수 최소), Cisco UCSM 관리형·Supermicro SUM 대상은 `UNSUPPORTED`.

### 출력
- 파일: `results/<일시>_all/all_diff.tsv` — 열: `model ref_host host bios_version ref_bios_version attribute ref_value host_value status` (DIFF/ONLY_* 만 행으로 기록, 동일 호스트는 `summary.tsv` 에 개수만; **구현 반영:** 없는 쪽 값은 `<없음>`, 빈 문자열은 `""`)
- `results/<일시>_all/summary.tsv` — 열: `host ip model ref_host bios_version ref_bios_version compared ignored diff only_ref only_host status notes` (호스트별: 모델, 기준호스트, 기준/대상 BIOS 버전, 비교 속성 수, DIFF/ONLY 개수, 상태, **특이사항**(`BIOS_VER_DIFF`·`MULTI_REF`·`DIFF_TXT_MODEL_MISMATCH`))
- 터미널 리포트: 모델 그룹별로 `기준 호스트 / 대상 N대 / 완전 일치 M대 / 차이 있음 K대` → 차이 있는 호스트의 속성 목록(많으면 상위 N개 + 파일 안내) → 마지막에 **속성별 집계**(어느 속성이 몇 대에서 다른가: 같은 속성이 다수 호스트에서 다르면 기준이 틀렸을 가능성 안내) → **특이사항 목록**(BIOS 버전 불일치 호스트: 호스트·대상 버전·기준 버전, `DIFF_TXT_MODEL_MISMATCH`) → 분류 불가 목록(`NO_REFERENCE`, `UNREACHABLE` 등)
- `--from-dump 디렉터리` 로 저장된 JSON 덤프끼리 오프라인 비교 가능, 재시도 대상은 `retry.txt` (기존 규칙 동일; **구현 반영:** `REF_UNREACHABLE` 도 포함, `-retry-from` 으로 병합)

### 완료 조건 (성공기준 7)
mock BMC 로 모델 2종(예: DL360Gen11, DL360Gen10) × 기준 1(diff.txt 에는 hostname 만) + 대상 여럿(BIOS 버전이 다른 호스트 포함)을 구성해, 모델별로 올바른 기준과 비교되고 DIFF/ONLY_REF/ONLY_HOST 가 정확히 나오며, 기준 없는 모델은 `NO_REFERENCE`, BIOS 버전이 다른 호스트도 비교되며 특이사항에 `BIOS_VER_DIFF` 로 나오고, 제외 속성은 비교에서 빠지고, 어떤 쓰기 호출(PATCH/POST Job)도 mock 에 도달하지 않는다.
