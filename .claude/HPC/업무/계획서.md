# hpcbot — 업무 프로세스 챗봇 재설계 계획서 (인터뷰 완료 · 확정)

> 인계용 계획서입니다. 1단계(인터뷰·결정·설계 확정)는 2026-10-04 클라우드 세션에서 끝냈고, 결과는 §5에 있습니다.
> 구현 세션에서는 **§5 결정 사항이 §3 원문보다 우선**합니다. 추가 질문 없이 구현할 수 있는 상태입니다.
> 구현은 **로컬 세션**에서 합니다. 매뉴얼 원문은 공개 저장소에 올리지 않으므로 로컬에서 직접 복사해야 합니다(§11-1).

## 1. 목표 및 범위

- 기존 Go 챗봇(`main.go`·`hangul.go`·`jev.go`, 이 폴더에 기준본으로 커밋됨)을 **수정**해서, 서버 운영 매뉴얼의 **항목(블록) 단위로 정확하게 답하는 오프라인 키워드 점수 챗봇** `hpcbot`을 만든다.
- 키워드 점수는 **빌드할 때 Jev API로 받는다**(키워드 → 항목 확률). 운영 바이너리는 기본적으로 네트워크를 쓰지 않는다.
- **질문 100개(조정용 70 + 검증용 30)**를 자동 생성하고, Jev로 정답 라벨을 교차검증한다. 정확도 기준(§8)을 통과할 때까지 키워드와 가중치를 조정한다.
- 범위 밖: 2차 AI 연동(ntfy 경유 LLM). 메모만 남긴다(§10).

## 3. 원 요구사항 (원문 요약 — §5와 충돌하면 §5가 우선)

1. 레드햇(RHEL8)에서 쓸 챗봇. 빌드된 상태로 바로 구동하고, 부하는 적고 속도는 빨라야 한다 → Go(기존 결정 유지).
2. 질문의 키워드 점수를 바탕으로 프로세스나 설명을 답한다. 점수는 typesafe Jev API의 조언을 받는다.
3. 영타 → 한글 변환(`xptmxm` → 테스트, `dlrpehlfRk?` → 이게될까?). 영어가 섞일 수 있으므로 `/h xptmxm` 형식을 지원한다.
4. 정확도가 너무 낮으면 2차로 ntfy 등을 활용해 AI를 연동한다(아직 고려 대상 아님).
5. 재설계 사유: GPU 설치를 물으면 OS 설치로 답한다. 질문 50~100개를 생성해 정답 여부를 테스트하는 단계가 필요하다.

## 5. 결정 사항 (§3 원문보다 우선)

1. **언어**: Go, 표준 라이브러리만 사용, 정적 빌드 단일 바이너리 `hpcbot`.
2. **답변 단위 = 매뉴얼 블록**(§6-3 목록, 86개). 답변은 매뉴얼 원문을 그대로 보여준다(§6-6 렌더 규칙). 손으로 쓴 요약문 `manualResponses`와 `categories`, `localFallbackMatch`는 삭제한다.
3. **점수** = 질문에서 찾은 키워드들의 `w(키워드, 블록)` 합계. `w`는 Jev 확률로 정한다(§6-8). "설치"처럼 여러 블록에 걸친 일반어는 Jev 확률이 분산되므로 자연히 낮은 가중치를 받는다 → P1 해결.
4. **판정**: 1위 점수 < `min_score`이면 미매칭. 2위/1위 ≥ `ambig_ratio`이면 후보 번호 제시. 그 외에는 1위 답변(§6-5).
5. **운영 Jev**: `--jev` 옵션을 줄 때만, 로컬 판정이 후보/미매칭일 때 한 번 호출(§6-7). 기본은 완전 오프라인.
6. **영타**: 토큰 단위 자동 감지 + `/h` 강제(§6-4). hangul.go 버그 P5~P7을 수정한다.
7. **code·로그**: 질문마다 4자리 code를 부여하고, 화면과 `/tmp/hpcbot/query.log`(모든 사용자 공용)에 질문·답변 전문·점수를 기록한다(§6-6).
8. **질문셋**: 100개(train 70 / holdout 30)를 에이전트가 생성하고, Jev로 라벨을 교차검증한다. 튜닝은 train으로만 하고 holdout은 마지막 판정에만 쓴다(§6-9, §6-10).
9. **매뉴얼**: 커밋하지 않는다. 로컬에서 `data/manual.md`로 복사한다. 빌드 스크립트는 파일이 없으면 안내 후 종료한다.

## 6. 설계

### 6-1. 디렉터리·파일 (`.claude/HPC/업무/`)
```
go.mod                 # module hpcbot, go 1.20
main.go                # (수정) REPL + 한 줄 실행 + 플래그(--jev, -v)
hangul.go              # (수정) 영타→한글 + P5~P7 수정 + 토큰 단위 변환 함수
jev.go                 # (수정) 운영 --jev 용 Jev 클라이언트만 남김 (categories/manualResponses/localFallbackMatch 삭제)
kb.go                  # (신규) kb.json·manual.md 로드(내장/외부 우선), 매뉴얼 파서, 앵커 해석
match.go               # (신규) 정규화·키워드 매칭·점수·판정
render.go              # (신규) 블록 원문 → 터미널 출력 변환
qlog.go                # (신규) code 발급·공용 로그 기록·회전
*_test.go              # 단위 테스트 + accuracy_test.go(질문셋 판정·리포트)
data/manual.md         # 매뉴얼 원문 (gitignore, 로컬 복사)
data/kb_seed.json      # 블록·앵커·그룹·후보 키워드·accept (사람/에이전트가 편집하는 원본)
data/kb.json           # kbgen 산출물 (seed + Jev 가중치 + 임계값) — 내장 대상
testdata/questions.json# 질문 100개
testdata/jev_labels.json# Jev 교차검증 결과
tools/kbgen/main.go    # (신규) 빌드 도구: Jev로 키워드 가중치 생성 + 질문 교차검증 (자체 최소 Jev 클라이언트)
tools/kbgen/cache.json # Jev 응답 캐시(키워드/질문 → 확률). 재실행 시 API 재호출 방지. 커밋함(본문 없음)
test_report.md         # 정확도 리포트 (accuracy_test 가 생성)
build.sh               # manual.md 확인 → go vet/test → 정적 빌드 → dist/hpcbot
README.md / 사용법.txt / ARCHITECTURE.md / CHANGELOG.md
```
- 패키지 분리는 하지 않는다(루트 `package main` 하나 + `tools/kbgen` 독립 main). kbgen의 Jev 요청 타입 40줄 정도는 jev.go와 중복을 허용한다.

### 6-2. 데이터 로드 (kb.go)
- 우선순위(파일별 독립): `$HPCBOT_DATA/<파일>` → 실행 파일과 같은 폴더의 `<파일>` → 내장본.
- 로드할 때 kb.json의 모든 앵커를 매뉴얼에서 찾는다. 찾지 못한 블록은 stderr에 `[경고] 앵커 없음: <id>`를 출력하고 비활성화한다(종료하지 않음). 테스트는 경고 0건을 요구한다.
- `-v`로 실행하면 시작할 때 사용한 파일의 출처(내장/외부 경로)를 출력한다.

| ts (6) | `dhcp_fail` 13.1 · `pxe_fail` 13.2 · 13.3 행: `passwd_disk_full`(첫 칸이 `current password`로 시작) `ssh_kex`(SSH `key exchange failed`) `dracut`(OS 설치 후 `dracut` …) `dhcpd_fail`(DHCP 데몬 fail) |
| parts (2) | `parts_intake` 14.1 · `parts_guide` 14.2 |

- 표 행은 첫 칸에서 백틱과 `**`를 뺀 뒤 **앞부분 일치(prefix)**로 찾는다(예: 8.1 `*.so 파일…`, 13.3 `current password…`).
- **비슷한 블록 쌍(accept)**: `gpu_driver`↔`gpu_driver_incident`, `usb_block`↔`usb_monthly`, `os_install`↔`os_install_type`. 질문셋에서 서로 정답으로 인정한다(§6-9).
- **혼동 감시 그룹**: `os` 그룹 vs `gpu` 그룹 + `cuda`. 이 사이의 1위 오답은 1건도 허용하지 않는다.

### 6-4. 영타 → 한글 (hangul.go)
- 수정: P5는 호환 자모 표(ㄱㄲㄴㄷㄸㄹㅁㅂㅃㅅㅆㅇㅈㅉㅊㅋㅌㅍㅎ = U+3131,3132,3134,3137,3138,3139,3141,3142,3143,3145,3146,3147,3148,3149,314A,314B,314C,314D,314E)로 고친다. P6 단독 모음은 U+314F + 중성 인덱스로 바꾼다. P7은 `Q W E R T O P`를 뺀 대문자를 소문자로 처리한다.
- **보호 단어**: kb.json의 ASCII 키워드 전체 + 매뉴얼에 나오는 `[A-Za-z][A-Za-z0-9_.-]{1,}` 토큰(로드할 때 소문자 집합으로 만듦). 보호 단어는 변환하지 않는다.
- **`/h <문장>`**: 보호 단어를 뺀 모든 영문 토큰을 변환한 뒤 점수를 매긴다. 예: `/h gpu emfkdlqj tjfcl` → `gpu 드라이버 설치`.
- **자동 감지(`/h` 없을 때)**: 원문으로 먼저 판정한다. 결과가 "1위 답변"이 아니면 "변환 후보 토큰"(보호 단어가 아니고, 영문자로만 되어 있고, 변환 결과에 영문이 남지 않으며 완성형 음절이 1개 이상인 토큰)을 변환해서 다시 판정하고, 더 나은 쪽(답변 > 후보 > 미매칭, 같으면 1위 점수가 높은 쪽)을 쓴다. 변환본을 쓰면 `[자동 변환] <변환문>`을 출력한다.
- 단위 테스트 최소 케이스: `xptmxm`→테스트, `dlrpehlfRk?`→이게될까?, `rmfovlr`→그래픽, `emfkdlqj`→드라이버, `tjfcl`→설치, `dkssudgktpdy`→안녕하세요, `s`→ㄴ, `k`→ㅏ, `A`→ㅁ, `dlfrdj`→읽어.

### 6-5. 점수 엔진 (match.go)
1. **정규화**: 소문자로 바꾸고, 공백을 지운 압축 문자열 `c`를 만든다. 각 위치에 `boundaryBefore[i]`(원문에서 앞이 공백이었거나 i==0)를 기록한다.
2. **키워드 매칭**: kb 키워드(소문자, 공백 제거)를 **긴 것부터** `c`에서 찾는다. 이미 다른 키워드가 차지한 구간과 겹치면 건너뛴다. 키워드 1개는 1회만 센다.
   - 영문·숫자로만 된 키워드는 경계 조건을 둔다: 앞 글자가 시작이거나 `boundaryBefore`이거나 영숫자가 아니어야 하고, 뒤 글자도 끝이거나 `boundaryBefore`이거나 영숫자가 아니어야 한다(`os`가 `hosts`에 걸리지 않게). 한글이 섞인 키워드는 단순 부분 문자열로 찾는다.
   - `stopwords`(방법, 알려줘, 어떻게, 해줘, 요청, 확인, 문의, 좀, 뭐야 등)는 키워드에서 뺀다.
3. **점수**: `score(b) = Σ w(k,b)` (찾은 키워드 k 전체). `require_any`가 있는 블록은 그중 하나라도 `c`에 있어야 하며, 없으면 0점이다.
4. **판정**(임계값은 kb.json `thresholds`, 초기값 `min_score 0.5, ambig_ratio 0.8, cand_ratio 0.5`, 튜닝으로 확정):
   - `s1 < min_score` → **미매칭**
   - `s2/s1 ≥ ambig_ratio` → **후보**: 점수 ≥ `s1×cand_ratio`인 상위 블록 최대 3개
   - 그 외 → **답변**: 1위 블록. "다른 후보"로 2·3위 중 점수 > 0인 것의 제목을 표시
5. 결정적 동작: 동점이면 kb 순서가 앞선 블록이 이긴다(맵 순회 순서에 의존하지 않음).

### 6-6. 출력·code·로그 (render.go, qlog.go, main.go)
**렌더 규칙**(블록 원문 → 터미널): `**` 제거 / `> [!CAUTION]`→`[주의]`, `[!WARNING]`→`[경고]`, `[!IMPORTANT]`→`[중요]`, `[!NOTE]`→`[참고]`, 인용 `> ` 제거 / 코드펜스 줄 제거 후 내용 4칸 들여쓰기 / mermaid는 줄마다 `X["라벨"]`·`X{"라벨"}`→라벨, `-- 예 -->`→` ─(예)→ `, `-->`→` → `, `<br/>`→공백, `flowchart` 줄 삭제 / 표는 그대로.

- h4·표 행 블록의 표기: `§7.1 계정으로 서버 접속 불가`, `§8.1 Docker 설치`, 용어는 `§1 ITOM`.

**후보 모드**

- 한 줄 실행에서는 목록만 출력하고 종료한다.

**미매칭**: `매뉴얼에서 찾지 못했습니다. 비슷한 항목:` + 점수 상위 3개 제목(점수 > 0인 것만) + `code NNNN`.

**code**: 1000~9999 난수. 시작할 때 현재 로그에 있는 code 집합을 읽어 중복을 피한다(프로세스 간 동시 충돌은 무시).

- 디렉터리가 없으면 만들고 `chmod 1777`, 파일은 만들 때 `chmod 0666`으로 둔다. 모든 사용자가 한 파일에 기록한다.
- JSON Lines 1줄/건. 쓰기는 `syscall.Flock`(LOCK_EX) + O_APPEND. 10MB를 넘으면 `query.log.1` 하나만 남기고 회전한다(락 안에서).

- 로그 쓰기에 실패하면 stderr에 1줄 경고만 출력하고 답변은 정상 출력한다.

**실행 형태**
- `hpcbot` → REPL (기존 배너 유지, `exit`/`quit` 종료, `/h` 지원)
- `hpcbot <질문…>` → 인자를 공백으로 합쳐 1건 처리 후 종료. 종료 코드 0=답변, 2=후보, 1=미매칭

### 6-7. 운영 `--jev` 옵션 (jev.go)
- 로컬 판정이 후보/미매칭일 때만 Jev `choice` 1회를 호출한다(블록 86개를 2단계로: 그룹 → 그룹 안 블록, §6-8과 같은 방식). 타임아웃 5초.
- Jev 1위 신뢰도 ≥ 0.6이면 그 블록으로 답변하고 제목 옆에 `[Jev]`를 붙인다. 아니거나 실패하면 로컬 결과를 그대로 쓴다.
- 키 위치는 C6 순서. 키가 없으면 `--jev`를 무시하고 stderr에 1줄 안내한다.

### 6-8. 빌드 도구 kbgen (tools/kbgen) — Jev 키워드 점수
> 먼저 메모리 `reference_jev_api.md`로 SystemOne의 요청 형식, choice 선택지 개수 제한, 호출 제한을 확인한다. 기존 jev.go의 `SystemOneRequest` 형식(`state`, `model: jev-latest`, `questions{type:"choice", instructions, criteria}`, 응답 `answers[].probabilities`)이 기준이다.

- **입력**: `data/kb_seed.json`
  ```json
  {"version":1,
   "thresholds":{"min_score":0.5,"ambig_ratio":0.8,"cand_ratio":0.5},
   "stopwords":["방법","알려줘","어떻게","해줘","요청","확인","문의","좀","뭐야"],
   "groups":{"gpu":"GPU 드라이버·Fabric Manager·GPU 모드", "os":"OS 설치·재설치·패치·설치 후 설정", "...":"..."},
   "intents":[
     {"id":"gpu_driver","title":"GPU 드라이버 설치","group":"gpu","anchor":{"h":"6.1"},
      "keywords":["gpu","그래픽","그래픽카드","nvidia","엔비디아","드라이버","driver","nvidia-uninstall",".run","rc.local"]},
     {"id":"term_itom","title":"ITOM","group":"term","anchor":{"table":"1","row":"ITOM"},
      "require_any":["뜻","뭐","무엇","의미","약어","약자","이란"],"keywords":["itom","자산관리시스템"]}
   ],
   "overrides":[{"kw":"설치","id":"os_install","add":0.1,"reason":"…"}]
  }
  ```
  - 블록마다 후보 키워드 5~15개(한글·영문·약어·명령어·동의어·흔한 오타)를 넣는다. "설치" 같은 일반어도 넣는다(Jev가 분산 확률을 줌).
- **`kbgen weights`**: seed의 모든 키워드(합집합)를 하나씩 Jev에 보낸다.
  - 1단계: `state=키워드`, criteria = 그룹(설명 = 그룹 설명 + 소속 블록 제목) → `p(그룹)`
  - 2단계: `p(그룹) ≥ 0.05`인 그룹만, criteria = 그룹 안 블록(설명 = 블록 제목 + 매뉴얼 제목줄) → `p(블록|그룹)`
  - `w(k,b) = p(그룹) × p(블록|그룹)`, 0.02 미만은 버린다. 여기에 `overrides`를 더한다. 결과를 `data/kb.json`으로 출력한다(seed 내용 + `keywords:{kw:{id:w}}` + 생성 시각).
  - choice 선택지 개수 제한이 86개 이상이면 1단계로 처리해도 된다. 어느 쪽을 택했는지 리포트에 기록한다.
- **`kbgen validate`**: `testdata/questions.json`의 질문마다 같은 2단계로 Jev 1위를 구해 `testdata/jev_labels.json`에 저장한다. 정답 라벨(accept 포함)과 다르면 "라벨 재검토 목록"에 넣는다.
- **캐시**: `tools/kbgen/cache.json`에 (요청 해시 → 확률)을 저장해 같은 요청은 다시 호출하지 않는다. 호출 사이에 지연 200ms, 실패하면 3회 재시도(1s/2s/4s)한다.
- **`overrides` 사용 제한**: 최대 20개, 항목마다 `reason` 필수. 기본은 Jev 확률을 그대로 쓴다.

### 6-9. 질문셋 (testdata/questions.json)
```json
[{"id":"q001","set":"train","type":"normal","q":"gpu 드라이버 설치 어떻게 해?","expect":"gpu_driver"},
 {"id":"q071","set":"holdout","type":"h","q":"/h rmfovlr emfkdlqj tjfcl","expect":"gpu_driver"},
 {"id":"q090","set":"train","type":"ambiguous","q":"설치 방법 알려줘","expect_mode":"candidates","expect_any":["os_install","gpu_driver"]},
 {"id":"q095","set":"holdout","type":"nomatch","q":"오늘 점심 메뉴 추천","expect_mode":"nomatch"}]
```
- 총 100개 = train 70 + holdout 30(유형별 비율을 맞춰 나눔, 고정 시드).
- 유형 비율: normal 45 / 구어·짧은 질문 20 / 혼용(영어 용어 + 한글) 11 / 자동 영타 8 / `/h` 6 / ambiguous 5 / nomatch 5
- 커버리지: term을 뺀 74개 블록이 100개 안에 **각각 1회 이상** + term 질문 6개 이상 + **os·gpu·cuda 관련 질문 20개 이상**(예: "GPU 설치", "OS 재설치", "nvidia 드라이버 재설치", "그래픽카드 드라이버 버전 변경", "cuda 깔아줘", "PXE 설치 안됨").
- **작성 순서 규칙**: 질문셋은 kb 가중치를 보기 전에 작성하고 커밋한다. holdout 30개는 튜닝 중 수정하지 않는다. 단, Jev 교차검증으로 라벨 오류가 확인된 경우만 수정하고 리포트에 기록한다.
- 정답 비교: `expect`가 1위이거나 accept 쌍(§6-3)이면 정답이다.

### 6-10. 판정·튜닝 루프 (accuracy_test.go)
- `go test -run TestAccuracy`: 로컬 엔진만 쓴다(Jev 호출 없음). train과 holdout을 각각 집계해서 §8-1 기준을 assert한다. `HPCBOT_REPORT=1`이면 `test_report.md`를 다시 쓴다.
- 리포트 내용: 세트별 표(N, 1위 정확도, 3위 내 포함율, 1위 오답 수, os↔gpu 혼동 수, ambiguous·nomatch 정답 수), 실패 질문 목록(질문/정답/결과/상위 3개 점수), Jev 라벨 불일치 목록, 튜닝 라운드 기록(라운드별 정확도와 변경 내용 1줄).
- **튜닝 루프(train만 사용, 최대 10라운드)**: 실패 질문마다 ① 정답 블록 seed에 동의어나 키워드 추가 → 새 키워드만 `kbgen weights`(캐시 덕분에 증분 호출) ② stopword 추가 ③ 임계값 조정 ④ 최후 수단으로 override(§6-8 제한) 중에서 고른다.
- train이 기준을 통과하면 holdout을 **1회** 판정한다. 실패하면 질문과 무관하게 일반적인 보강(동의어·표기 변형)만 한 라운드 더 하고 holdout을 1회 재판정한다(총 2회까지). 두 결과 모두 리포트에 남긴다. 그래도 실패하면 리포트에 원인과 2차(AI 연동) 필요성 의견을 적고 멈춘다.

## 8. 검증 기준

### 8-1. 정확도 (accuracy_test.go, train·holdout 각각)
- 1위 정확도 **≥ 95%** (ambiguous·nomatch 유형은 기대 모드와 일치하면 정답)
- 정답이 상위 3개(답변 모드의 "다른 후보" 또는 후보 모드 목록) 안에 있는 비율 **= 100%**
- os 그룹 ↔ gpu 그룹+cuda 사이의 1위 오답 **0건**
- nomatch 질문은 전부 미매칭으로 판정

### 8-2. 단위·회귀 테스트 (`go test ./...` 전부 PASS)
- kb: 86개 앵커 전부 해석(경고 0), 외부 파일 우선순위, 내장본 동작
- 자기 검색: 블록마다 `title`(term은 `title + " 뜻"`)으로 질문하면 1위가 그 블록(accept 쌍 허용)
- 고정 회귀(질문셋과 별개): `GPU 설치`·`gpu 드라이버 설치`·`그래픽카드 드라이버 교체`·`nvidia 드라이버 재설치`·`/h rmfovlr emfkdlqj tjfcl` → gpu_driver(또는 accept) / `OS 설치`·`os 재설치`·`PXE로 OS 깔기` → os_install(또는 accept) / `fabric manager 설치`·`nvswitch` → fabric_manager / `cuda 설치` → cuda / `docker 설치` → docker / `설치` → 후보 모드 / `점심 메뉴` → 미매칭
- hangul: §6-4 케이스
- qlog: code 4자리·로그 내 중복 없음, JSON 1줄, 파일 0666·디렉터리 1777, 10MB 회전, 로그 실패 시에도 답변 출력
- 한 줄 실행 종료 코드 0/2/1

### 8-3. RHEL8 스모크 (home-test 스킬: Rocky .58)
- `build.sh` → `dist/hpcbot`. `file`로 statically linked 확인, `ldd`가 "not a dynamic executable"
- .58에서 한 줄 실행 10건(§8-2 고정 회귀 중 10건)이 기대 결과와 일치

- root와 일반 사용자 1명이 번갈아 실행했을 때 같은 `/tmp/hpcbot/query.log`에 모두 기록됨
- 질문 1건 처리 시간 < 50ms (`time hpcbot "gpu 드라이버 설치"`)

## 10. 2차(정확도 부족 시) 메모 — AI 연동, 지금은 구현하지 않음

- 구조안: 폐쇄망의 hpcbot이 미매칭·후보 질문과 상위 3개 블록 원문을 사내 ntfy 토픽에 게시 → 인터넷이 되는 중계 서버가 구독해서 LLM 호출 → 답을 다른 토픽에 게시 → hpcbot이 수신. 사내 보안 승인이 전제.
- 저렴한 API 후보(2025년 공개 가격 기준, 도입할 때 공식 가격표 재확인. 단위: 입력/출력 100만 토큰당 USD):

| 모델 | 가격 | 메모 |
|---|---|---|
| Google Gemini 2.5 Flash-Lite | 약 0.10 / 0.40 | 가장 저렴한 축, 한국어 무난 |
| OpenAI GPT-5 nano | 약 0.05 / 0.40 | 입력 최저가 축 |
| Anthropic Claude Haiku 4.5 | 약 1 / 5 | 한국어·지시 준수 품질 우선 시 |

- 비용 감: 질문 1건 ≈ 입력 2천 토큰(블록 3개 + 질문) / 출력 300 토큰 → Flash-Lite 약 $0.0003, Haiku 4.5 약 $0.0035. 1,000건 기준 각각 약 $0.3 / $3.5.
- 판단 기준: 운영 로그에서 미매칭 + 후보 비율이 20%를 넘거나 오답 보고가 잦으면 2차를 검토한다.
