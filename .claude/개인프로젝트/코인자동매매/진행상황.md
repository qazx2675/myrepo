# 진행상황 / 인수인계 문서

> **용도:** 일일 사용량 소진 등으로 다른 환경(다른 PC, 다른 세션, 다른 AI 도구)에서
> 이어서 작업할 때, 이 문서 하나만 읽으면 맥락이 복원되도록 만든 파일이다.
>
> **최종 갱신:** 2026-08-30 (M1~M8 코드 완성 + 터미널 대시보드)

## 0. 다른 곳에서 이어서 시작하는 방법

새 세션에 아래 3개 파일을 넣고 시작하면 된다.

| 파일 | 역할 |
|---|---|
| `계획서.md` | 전체 설계 (무엇을 왜 이렇게 만드는가) |
| `CLAUDE.md` | 작업 규칙 (하지 말아야 할 것) |
| `진행상황.md` | 지금 어디까지 왔고 다음에 뭘 하는가 (이 문서) |

**새 세션 첫 프롬프트 예시:**

> 첨부한 `계획서.md`, `CLAUDE.md`, `진행상황.md` 를 읽어줘.
> 빗썸 코인 자동매매 프로젝트를 이어서 진행할 거다.
> 진행상황.md 의 "다음 작업" 부터 시작해줘.

**M1 검증:** [1] 조회 성공, [4] .env 없으면 RuntimeError. **대기:** [2][3][5] → 사용자 키 필요.
**M3-a 검증:** `test_m3a` 8개 통과. BTC 튜닝기간 MA10/30: +143%, MDD -17.75%, 실효수수료 0.0400%.
**M2-a 검증:** `test_m2a` 7개 통과. 엔진은 전 기간 봉의 약 15~30%에서 패턴을 잡는다.
**M2-b 검증:** `test_m2b` 4개 통과. `run_m2b` 진입규칙 비교 (튜닝, 5코인 평균):

| 규칙 | 내용 | 수익률 | MDD | 거래 |
|---|---|---|---|---|
| A 무필터 | 크로스업이면 매수 | +265.7% | -29.7% | 45 |
| B 하락회피 | + not is_bearish | +265.7% | -29.7% | 45 |
| C 약가중치 | + combine≥0.45 | +265.7% | -29.7% | 45 |
| D 상승확인 | + combine≥0.60 (상승형 패턴 필수) | **+81.5%** | -25.3% | 11 |

**B·C 효과 0, D 는 교환비 나쁨** → 하드 게이트 비활성.

**M4 검증:** `test_m4a`(8) + `test_m4b`(4) 통과. `run_m4` 포트폴리오 백테스트 (튜닝, 8코인,
**M6 에서 유동성 필터 버그 고친 뒤 수치**):

| 모드 | 패턴 | 수익률 | MDD | 거래 | 청산 |
|---|---|---|---|---|---|
| conservative | 없음 | +77.8% | **-14.8%** | 102 | stop 78, TP 24 |
| conservative | 하락veto | +81.3% | -15.0% | 101 | stop 77, TP 24 |
| aggressive | 없음 | +131.8% | -20.2% | 65 | stop 49, TP 16 |
| aggressive | 하락veto | +136.1% | -18.0% | 64 | stop 48, TP 16 |

**결론:**
1. **리스크 규칙 정상 작동** — 손절·익절 청산 골고루, conservative < aggressive MDD ✓.
2. **패턴 필터는 여전히 중립~노이즈 수준.** 하락veto 가 이번엔 +3%p 나왔지만 표본 작음.
   **게이트 채택 안 함** 결론 유지. 엔진은 소프트 가산만.
3. **★ conservative MDD -14.8% — 목표(10% 이내) 초과.** 유동성 필터를 제대로 고치니 진입이
   늘어 손절도 늘었다. **스크리너 지표 강화 / 손절폭·`SCREEN_ENTRY_THRESHOLD` 튜닝이
   M6-a 실행 전 필수.** (지금 데모 스크리너는 20일 모멘텀+이평+RSI 만)
4. 손절률 ~76%. 위와 같은 원인.

**M5 검증:** `test_m5` 6개 통과 + `run_m5` 실 API 확인:
- 빗썸 공지: `거래유의`/`거래지원종료` → 즉시 청산 마켓, `입출금`/`마켓추가` + `virtual_asset_warning`(WARNING↑) → 진입금지 마켓. 실행 시점에 ICX/SNX 청산 대상으로 잡힘.
- 뉴스 RSS(Cointelegraph/CoinDesk/TheBlock): 청산은 **제목에 정식명칭+청산키워드** 동시일 때만(파괴적 행동 보수적), 보류는 제목+요약 아무 별칭+키워드. 짧은 티커는 단어경계 매칭(‘Canada’의 ada 오탐 차단).
- `portfolio_backtest` 에 `liquidate_provider` 훅 추가 → 유의종목 즉시 청산 동작 테스트 통과.
- `notifier`: `NTFY_TOPIC` 미설정이면 조용히 False, 발송 실패해도 예외 안 냄.

**M5.5 검증:** `test_m55` 8개 통과. `paper.execute_against_book(Order, book)` — 호가 잔량 순차 소진,
가중평균 체결가, 부분체결(`filled_fully`), 지정가 가격 제한. `execute_live` 는 `PAPER_LATENCY_MS`(300ms)
만큼 대기 후 최신 호가로 체결. `run_m55` 실측:
- **상위권 코인은 호가창이 깊어 1억 매수도 슬리피지 1bp 미만** (BTC 는 8개 레벨 소진하지만 값은 거의 안 밀림).
- → **1억 페이퍼의 진짜 함정은 슬리피지가 아니라 '최소주문 5,000원이 안 보이는 것'.** M6-b(10만원) 필수 재확인.

**M6 검증:** `test_m6` 4개 통과 (store 왕복 / 진입→손절 / 유의종목 청산 / 재시작 복원).
`live_loop --once` 실 API 정상 (조회 전용, paper 체결). `store.py` = SQLite `data/trades.db`.
루프: 공지·뉴스 poll → 유의종목 즉시청산 → 손절/추적/익절 → 스크리너 상위 진입 → 자산 스냅샷 → 하트비트.
**유동성 필터 버그 수정**: 스크리너가 '오늘'(진행중) 봉의 거래대금을 24h 기준과 비교하던 것 →
직전 7일 완결봉 평균으로 변경. 이걸 고치니 M4 수치가 바뀜(위 표).

**M7 검증:** `test_m7_m8`(6개 중 3) 통과. `trader.Trader()` 는 3중 게이트 실패 시 `RuntimeError`:
DRY_RUN=True(기본) / `.env` LIVE_TRADING≠1 / 주문권한 없는 키. **기본 상태에선 절대 주문 안 나감.**
`live_loop` 이 시작 시 "체결 모드: 페이퍼/실주문" 을 로그로 남김. 실주문 API 는 테스트에서 호출 안 함.

**M8 검증:** `test_m7_m8` 나머지 3 통과. `averaging.should_propose` = 진입가 대비
추적손절선보다 2%p 덜 빠진 지점(conservative -3%, aggressive -6%)에서 **제안만** 발송.
`approve_averaging.bat KRW-XXX` → `data/averaging_approved.txt` → 다음 틱에 1회 실행
(per_coin_max 한도 + 최소주문 검증). **자동 실행 절대 없음** (불변 규칙 2).

## 3. 확정된 의사결정 (재논의 불필요)

이미 검토를 마친 항목들이다. 새 세션에서 다시 논의하지 말 것.

### 3.1 플랫폼

| 항목 | 결정 | 근거 |
|---|---|---|
| 거래소 | **빗썸 전용** | 사용자 요구. 다거래소 확장 없음 |
| 라이브러리 | **`python-bithumb`** | ccxt는 다거래소용이라 배제 |
| 인증 | **JWT (HS256) + `pyjwt`** | 빗썸 API 2.0 방식 |
| 상품 | **현물만** | 선물/레버리지/마진 금지 |

### 3.2 자금

| 항목 | 결정 |
|---|---|
| 실전 예산 | **100,000원** |
| 페이퍼 자본 | **100,000,000원** (M6-a) → **100,000원** (M6-b) |
| 최소 주문금액 | **5,000원** (빗썸 KRW 마켓, 하드 제약) |
| 동시 보유 | **2종목** (5,000원 제약 때문에 3→2로 축소) |
| 기본 모드 | **conservative** |

### 3.3 검증

| 항목 | 결정 | 근거 |
|---|---|---|
| 빗썸 모의투자 | **없음** | → `src/paper.py` 자체 구현 |
| M1~M6 API 키 | **조회 전용 (주문 권한 없음)** | 소프트웨어 플래그보다 강한 안전장치 |
| 주문 권한 키 | **M7에서 신규 발급** | 그 전엔 발급도 하지 않는다 |
| 페이퍼 체결 | **호가 순차 소진 + 수수료 + 300ms 지연** | 끄면 검증이 거짓이 됨 |
| M6 분리 | **M6-a(1억, 전략) / M6-b(10만원, 제약)** | 1억에선 최소주문 제약이 안 보임 |

### 3.4 운영

| 항목 | 결정 |
|---|---|
| 알림 | **ntfy 푸시** (카카오·텔레그램 아님). OAuth·토큰갱신 없음 = 무기한 운용 함정 제거 |
| ntfy 토픽 | `.env` 의 `NTFY_TOPIC`. 토픽명이 곧 비밀번호 — 길고 추측불가하게 |
| 하트비트 | 매일 09시 1회 |
| 수수료 | 쿠폰 **무료 등록** (구매 아님), 30일 만료 → 실효 수수료율 감시 |
| 진입 시간대 | **24시간 제한 없음** |
| 공시 대체 | **빗썸 공지사항** (유의종목/거래지원 종료 → 즉시 청산) |
| 뉴스 | **RSS 키워드 필터 (LLM 미사용)** — 계획서 13장 |
| **런타임 API 비용** | **0원.** 24시간 루프에 유료 API 금지. 개발용 Claude는 일회성이라 논점 아님 |

### 3.6 마일스톤 순서 (계획서 표와 다름 — 이쪽이 맞음)

계획서 9장은 M2 → M3 순서지만, **M2-a 패턴 필터를 튜닝하려면 측정 도구(백테스터)가
먼저 필요**하다. 실제 진행 순서:

```
코드: M1 ✅ M3-a ✅ M2-a ✅ M2-b ✅ M4 ✅ M5 ✅ M5.5 ✅ M6루프 ✅ M7게이트 ✅ M8승인 ✅
실행/승인(사용자): 스크리너튜닝 → M6-a(2~4주) → M6-b(1주) → M7 실전전환 (M3-b 는 안 만듦)
```

M4·M5(공지 감시)는 M3-a 이후 어디든 병렬 가능. M1은 전부의 하드 전제.

### 3.7 단계별 모델 배정

| 단계 | 모델 | 메모 |
|---|---|---|
| M1 | Sonnet 5 | 정형 API 연동 |
| M3-a 설계 | **Opus 5** → 구현은 Sonnet 5 | 호가 순차체결·부분체결·지연이 미묘 |

**발견**: 상위권 코인 호가창이 생각보다 깊다. 1억 매수도 슬리피지 <1bp. 슬리피지 걱정은

### 5.8 M6 루프 — 완성. 남은 건 사용자가 시간 들여 돌리는 것

`store.py`(SQLite) + `live_loop.py`(Bot: 공지/뉴스 poll → 청산 점검 → 스크리너 진입 → 스냅샷
→ 하트비트). 재시작하면 `data/trades.db` 에서 포지션·현금 복원. `test_m6`(4) 통과.

**M6-a 실행 (사용자)**:
1. (권장) 스크리너/손절 튜닝 먼저 — 현재 데모 스크리너로는 conservative MDD ~15% (목표 초과).
   `screener.base_score` 지표 보강하거나 `SCREEN_ENTRY_THRESHOLD`↑ / 손절폭 조정 후 `run_m4` 재확인.
   그다음 홀드아웃 1회로 검증.
2. `.env` 에 `NTFY_TOPIC` 채우고 폰에 ntfy 구독 (알림 받으려면).
3. `run_m6.bat --reset` 로 시작 (`PAPER_CAPITAL=100_000_000` 기본). 집 PC/VPS 에서 **2~4주 상시 구동**.
4. `data/trades.db` 의 `equity` 테이블로 MDD 확인. 목표: 4주 MDD 10% 이내.

**M6-b 실행 (사용자)**: `config/settings.py` 의 `PAPER_CAPITAL = 100_000` 으로 바꾸고
`run_m6.bat --reset`, 1주. 목표: 최소주문/수수료로 **거부된 주문 0건** (로그 확인).

### 5.9 M7 실전 전환 — 코드는 있음. 활성화 절차 (전부 사용자)

`trader.py` 는 이미 있고 `live_loop` 이 자동 라우팅한다. 실주문을 켜려면 **3가지 전부**:
1. 빗썸에서 **주문 권한 있는** API 키 신규 발급 → `.env` 의 `BITHUMB_ACCESS_KEY/SECRET_KEY` 교체
2. `.env` 에 `LIVE_TRADING=1` 추가
3. `config/settings.py` 의 `DRY_RUN = False`
   → 이 3개가 다 맞아야 `trader.Trader()` 가 뜬다. 하나라도 아니면 페이퍼로 폴백.
4. `config/settings.py` 의 `PAPER_CAPITAL` 을 실제 예산(100,000)에 맞추고 `run_m6.bat --reset`
- **M6-b 페이퍼 검증 통과 전에는 하지 말 것** (불변 규칙 4).
- `trader._to_fill` 의 빗썸 응답 필드 파싱은 실주문 첫 1~2건으로 검증 필요 (문서 기준으로 작성함).

### 5.10 M8 물타기 — 코드는 있음. 쓰는 법

루프가 알아서 제안한다. 포지션이 진입가 대비 `추적손절선+2%p` 이하로 빠지면 ntfy 로
"`approve_averaging.bat KRW-XXX`" 안내가 온다. 승인하면 다음 틱에 1회 추가 매수.
승인 안 하면 그냥 추적손절이 처리. **자동 물타기는 없다.**
