# 빗썸 코인 자동매매 시스템 구축 계획서

> 원본: `국내주식_자동매매_구축_계획서.md` (KIS API 기반)
> 본 문서는 동일한 철학을 유지한 채 **빗썸(Bithumb) 암호화폐 시장**으로 이식한 버전이다.

---

## 0. 철학 (원본과 동일 — 변경 없음)

> **"돈을 버는 시스템"이 아니라 "잃지 않는 시스템"을 만든다.**

- 리스크 관리 로직이 매매 로직보다 **우선한다**.
- 수익률 극대화가 아니라 **생존**이 1차 목표다.
- 검증되지 않은 전략에 실제 자금을 넣지 않는다.
- 시스템이 판단을 못 하는 상황에서는 **아무것도 하지 않는 것**이 정답이다.

암호화폐 시장은 주식보다 변동성이 크고, 가격제한폭이 없으며, 24시간 열려 있다.
즉 **"잃지 않는다"는 원칙이 주식보다 더 중요하다.**

## 1. 빗썸 적용 가능성 검토 결과

### 1.1 결론: **가능하다.** 단, 한 가지 큰 제약이 있다.

| 항목 | 국내주식(KIS) | 빗썸 | 판정 |
|---|---|---|---|
| 공식 REST API | O | O (API 2.0, v2.1.5) | 가능 |
| 인증 | App Key/Secret + 토큰 | **API Key/Secret + JWT(HS256)** | 가능 |
| 시세/캔들 조회 | O | O (분/일/주/월 캔들, Ticker, 호가, 체결) | 가능 |
| 주문/취소/조회 | O | O (단건, 다건 최대 30건, TWAP) | 가능 |
| 잔고 조회 | O | O (전체 자산 조회, 주문 가능 정보) | 가능 |
| **모의투자 계좌** | **O (KIS 제공)** | **X (빗썸 미제공)** | **직접 구현 필요** |
| 파이썬 라이브러리 | python-kis | **python-bithumb** | 가능 |
| 시장 운영시간 | 09:00~15:30 | **24시간 365일** | 설계 변경 필요 |
| 가격제한폭 | ±30% | **없음** | 리스크 상향 |
| 공시(DART) | O | X → **빗썸 공지사항**으로 대체 | 대체 가능 |

### 1.2 유일한 블로커: 모의투자 계좌 부재

빗썸에는 KIS 같은 **모의투자 서버가 없다.** (코빗은 있고, 바이낸스는 testnet이 있으나
"빗썸 전용" 요구사항에 따라 배제)

**해결책: 페이퍼 트레이딩 엔진(`paper.py`)을 직접 만든다.**

- 실시간 시세/호가는 **실제 빗썸 API**에서 가져온다 (조회는 인증 없이도 가능).
- 주문만 로컬 가상 체결 엔진이 처리한다.
- 체결은 **호가 잔량을 순차 소진하는 방식**으로 시뮬레이션한다 (평균 체결가 계산).
- 수수료(0.04%)와 신호~주문 지연(300ms)을 **반드시 반영한다.**

이 방식이 오히려 KIS 모의투자보다 낫다: 모의투자 서버는 체결 로직이 실제와 다른데,
직접 만들면 **호가 기반이라 슬리피지가 정직하게 잡힌다.**

### 1.3 구조적 안전장치: 조회 전용 API 키

`DRY_RUN=True` 같은 **소프트웨어 플래그는 코드 버그로 뚫릴 수 있다.**
빗썸은 API 키 발급 시 권한을 선택할 수 있으므로:

- **M1 ~ M6 (전 검증 기간): 주문 권한이 없는 "조회 전용" 키만 사용한다.**
  → 코드에 어떤 버그가 있어도 **거래소가 주문을 거부한다.**
- **M7 실전 전환 시점에 주문 권한 키를 신규 발급한다.**

## 2. 자금 계획 (테스트 목적 10만원)

### 2.1 실전 예산

| 항목 | 금액 |
|---|---|
| 총 예산 | **100,000원** |
| conservative 운용금 | 50,000원 (예비 50,000원) |
| aggressive 운용금 | 100,000원 전액 |

### 2.2 검증 예산

| 단계 | 자본 | 목적 |
|---|---|---|
| L1 백테스트 | 과거 캔들 | 전략의 통계적 타당성 |
| L2 페이퍼 | **가상 1억원** | 전략 로직 검증 (유의미한 거래 횟수 확보) |
| **L2.5 페이퍼** | **가상 10만원** | **제약 검증 (최소주문/수수료 비중)** |
| L3 실전 | 실제 10만원 | 실제 체결/슬리피지 |

### 2.3 ★ 1억 페이퍼의 함정 (반드시 이해할 것)

가상 1억으로만 검증하면 **10만원에서만 터지는 버그를 못 잡는다.**

- 빗썸 KRW 마켓 **최소 주문금액 = 5,000원**
- 1억에서는 이 제약이 사실상 존재하지 않는다.
- 10만원에서는 **"+10% 도달 시 절반 익절"이 최소금액 미달로 거부**될 수 있다.

→ 그래서 M6를 **M6-a(1억) / M6-b(10만원)** 로 쪼갠다. 같은 코드, `PAPER_CAPITAL` 값만 바꾼다.

또한 1억 페이퍼는 **호가 순차 소진 체결**이 아니면 시장 충격을 무시해 버려
"1억으로 알트코인 매수해도 슬리피지 0%" 라는 거짓 결과가 나온다. → `PAPER_USE_ORDERBOOK=True` 필수.

## 3. 수수료 설계

| 구분 | 요율 |
|---|---|
| **쿠폰 등록 시** | **0.04%** |
| 미등록 (거래대금 1000만원 미만) | 0.25% |
| 미등록 (1000만 ~ 5억) | 0.20% |
| 미등록 (5억 초과) | 0.15% |

### 3.1 수수료 쿠폰은 **무료다** (구매 아님)

- 빗썸이 상시 제공하며, 마이페이지에서 등록하면 된다.
- **유효기간 30일.** 만료 시 `[기간연장]` 버튼으로 재등록.

### 3.2 만료가 곧 사고다

10만원 예산 기준 월 수수료 차이:

| 요율 | 월 수수료 (왕복 20회 가정) | 예산 대비 |
|---|---|---|
| 0.04% | 약 800원 | 0.8% |
| 0.25% | 약 5,000원 | **5.0%** |

**차이 약 4,200원 = 예산의 4.2%.** "예적금 수익률 초과"라는 목표가 수수료만으로 무너진다.

### 3.3 런타임 감시 (필수 구현)

```
실효 수수료율 = 실제 지불 수수료 / 실제 체결금액   (체결 내역에서 역산)

if 실효_수수료율 > FEE_ALERT_ABOVE (0.05%):
    ntfy 알림 발송
    신규 진입 중단        # 보유 포지션 청산 로직은 그대로 동작
```

쿠폰 만료를 **사람이 기억하는 것에 의존하지 않는다.**

## 4. 운용 모드 (10만원 기준)

| 항목 | **conservative (기본)** | aggressive |
|---|---|---|
| 운용금 | 50,000원 (예비 50,000) | 100,000원 전액 |
| 동시 보유 | 최대 **2종목** | 최대 **2종목** |
| 코인당 최대 투입 | 25,000원 | 50,000원 |
| 1차 진입 비중 | 60% (15,000원) | 70% (35,000원) |
| 손절선 | **-7%** | -12% |
| 익절 | +10%에 50% 매도 | +20%에 1/3 매도 |
| 추적 손절 | -5% | -8% |
| 일일 손실 한도 | -3% (3,000원) | -6% (6,000원) |
| 스크리닝 범위 | 24h 거래대금 상위 20 | 상위 50 |
| 최소 24h 거래대금 | 100억원 | 30억원 |
| 스크리닝 주기 | 1시간 | 15분 |
| 신규 진입 시간대 | **24시간 (제한 없음)** | 24시간 |

### 4.1 왜 동시 보유가 3종목(주식)에서 2종목으로 줄었나

최소 주문금액 5,000원 때문이다.

```
3종목 × conservative 50,000원  →  코인당 16,666원
1차 진입 60% = 10,000원
2차 물타기 전 상태에서 절반 익절 = 약 5,000원 언저리  →  경계선
분할 매도가 조금만 어긋나도 주문 거부
```

→ **2종목으로 줄이고 1차 진입 비중을 60%로 올려** 모든 분할 주문이 5,000원을 넘게 만든다.

### 4.2 모든 주문은 발주 전 최소금액 검증을 통과해야 한다

```python
if 주문금액 < MIN_ORDER_KRW:      # 5000
    # 분할 매도라면 -> 전량 매도로 승격
    # 신규 진입이라면 -> 진입 스킵 + 로그
```

## 6. 알림 — ntfy 푸시

### 6.1 왜 ntfy 인가

| 항목 | 카카오 | **ntfy** |
|---|---|---|
| OAuth / 토큰 갱신 | 필요 (access 6h, refresh 2개월) | **없음** |
| 무기한 운용 함정 | refresh_token 조건부 재발급 → 조용히 죽음 | **없음** |
| 비용 | 무료 | 무료 (공개 토픽) / 자가호스팅 가능 |
| 수신 | 카카오톡 | ntfy 앱 (iOS/Android/웹), 여러 기기 동시 |
| 심사 | 나에게 보내기는 불필요 | 불필요 |

토큰 만료로 알림이 조용히 멈추는 리스크가 **구조적으로 사라진다.**

### 6.2 전송 — JSON 발행 (헤더 방식 아님)

```
POST https://ntfy.sh            (토픽 아님, 서버 루트)
Body(JSON): {"topic": "<NTFY_TOPIC>", "message": "...", "title": "...",
             "priority": 1~5, "tags": ["warning"]}
[Authorization: Bearer <NTFY_TOKEN>]  # 보호 토픽만
```

- **헤더에 제목을 넣으면 안 된다** — `requests` 가 latin-1 로 인코딩해서 한글이 깨진다. JSON 본문은 UTF-8.
- **토픽 이름이 곧 비밀번호다.** 길고 추측 불가능하게 (`.env` 의 `NTFY_TOPIC`).
- 손절/청산 = priority 5 + `warning`. 하트비트 = priority 2.
- 공개 토픽이면 `NTFY_TOKEN` 불필요.

### 6.3 하트비트

매일 09시, 손익/보유/시스템 상태를 1회 발송한다.
**알림이 안 오는 것 자체가 장애 신호**가 되게 만든다. (ntfy 앱에서 "마지막 수신" 확인 가능)

### 6.4 알림은 사후 통지다

**손절/청산은 알림 성공 여부와 무관하게 집행한다.**
ntfy 서버 장애가 매매 로직을 막아서는 안 된다. 전송은 짧은 타임아웃 + 실패 시 로그만.

## 7. 차트 패턴 분석 (M2에 배치)

### 7.1 위치 정정: M5가 아니라 **M2**

차트 패턴은 **결정론적 코드**다 (선형회귀, 스윙 추출).
M5는 Claude가 뉴스를 읽고 판단하는 **LLM 레이어**다. 성격이 다르다.

→ 패턴은 **M2 스크리닝**에 들어간다.

### 7.2 성능 검토 결과: 무거워지지 않는다

| 항목 | 비용 |
|---|---|
| 스윙 추출 | ~0.3 ms / 코인 |
| 선형회귀 2회 | ~0.05 ms / 코인 |
| 20종 패턴 매칭 | ~0.5 ms / 코인 |
| **50코인 합계** | **~50 ms** |
| 같은 스크리닝의 캔들 API 호출 | **수 초 ~ 수십 초** (레이트리밋) |

→ 패턴 연산은 **API 대기시간의 1/100 미만.** 성능은 논점이 아니다.

### 7.3 진짜 비용은 **검증 불가능성**이다

| 항목 | 패턴 없음 | 20종 전부 |
|---|---|---|
| 자유 파라미터 | 약 8개 | **약 100개** |
| M2 개발 기간 | 1주 | 3~4주 |
| 그리드 서치 | 가능 | **불가능** |
| 4주 페이퍼 진입 횟수 | 8~20회 | 8~20회 (동일) |
| **패턴당 관측 수** | - | **1회 미만** |

**패턴 20종을 4주 페이퍼로 검증하는 건 통계적으로 불가능하다.**
검증 안 된 100개 파라미터 = 과최적화 = "잃지 않는 시스템" 철학 위반.

### 7.4 20종 → 2개 엔진으로 압축

**엔진 A — 추세선 2개 선형회귀**
고점들에 회귀선 1개, 저점들에 회귀선 1개. **기울기 부호 + 수렴/발산**으로 분류.

| 패턴 | 상단선 | 하단선 |
|---|---|---|
| ① 대칭 삼각수렴 | 하락 | 상승 |
| ② 상승 삼각수렴 | 수평 | 상승 |
| ③ 하락 삼각수렴 | 하락 | 수평 |
| ④ 메가폰(확대형) | 상승 | 하락 |
| ⑪ 상승 쐐기 | 상승 | 더 가파른 상승 |
| ⑫ 하락 쐐기 | 하락 | 더 완만한 하락 |
| ⑬ 불 플래그 | 하락 | 하락 (평행) |
| ⑭ 베어 플래그 | 상승 | 상승 (평행) |
| ⑮ 페넌트 | 하락 | 상승 (짧은 수렴) |
| ⑱ 박스권 | 수평 | 수평 |

→ **10개 패턴, 파라미터 6~8개.**

**엔진 B — 스윙 시퀀스 매칭**
지그재그/프랙탈로 스윙 고저점 추출 → 최근 3~5개의 **높이 비율 비교**.

| 패턴 | 조건 |
|---|---|
| ⑤ 헤드앤숄더 | 고점 3개, 가운데가 최고 |
| ⑥ 역헤드앤숄더 | 저점 3개, 가운데가 최저 |
| ⑦ 더블탑 | 고점 2개, 높이 유사 |
| ⑧ 더블바텀 | 저점 2개, 깊이 유사 |
| ⑨ 트리플탑 | 고점 3개, 높이 유사 |
| ⑩ 트리플바텀 | 저점 3개, 깊이 유사 |

→ **6개 패턴, 파라미터 4~5개.**

### 7.5 보류: ⑯ 컵앤핸들 / ⑰ 역컵앤핸들 / ⑲ 원형바닥 / ⑳ 다이아몬드

**이유: 시간축 불일치.**
이 패턴들은 완성까지 **수 주 ~ 수 개월**이 걸린다.
2~4주 페이퍼 검증 기간에는 **사례 자체가 잡히지 않는다.** 검증 불가능한 코드는 넣지 않는다.

### 7.6 단계적 도입 (확정)

| 단계 | 내용 | 근거 |
|---|---|---|
| **M2-a** | 엔진 A → **하락형 회피 필터로만** 사용 (③⑤⑦⑨⑪⑭) | **틀린 회피 = 기회비용. 틀린 진입 = 실손실.** 회피 쪽이 파라미터 민감도가 낮고 철학에 부합 |
| **M2-b** | 엔진 A 상승형(②⑫⑬⑱)을 **기존 신호의 가산 가중치**로 | **단독 진입 신호로 쓰지 않는다** |
| M3 이후 | 홀드아웃 백테스트 통과 시에만 **엔진 B** 추가 | 통과 못 하면 넣지 않는다 |
| 보류 | ⑯⑰⑲⑳ | 시간축 불일치 |

### 7.7 홀드아웃 검증 (필수)

```
튜닝 기간 : 2023-01 ~ 2024-12   (파라미터 조정 자유)
검증 기간 : 2025-01 ~ 2026-06   (단 한 번만 돌린다)
```

**검증 기간에서 성능이 무너지는 패턴은 버린다.** 대부분 버려질 것으로 예상하고 시작한다.

### 7.8 차트 이미지 디버그 모드 (필수)

패턴 탐지 시 캔들 + 탐지된 추세선/스윙점을 PNG로 저장한다.
**"왜 이걸 헤드앤숄더로 봤나"를 눈으로 확인 못 하면 튜닝이 불가능하다.**

## 8. 빗썸 공지 감시 (주식의 DART 대체)

암호화폐에는 DART 같은 공시가 없다. 대신 **빗썸 공지사항**이 사실상의 공시다.

| 공지 유형 | 대응 |
|---|---|
| **투자유의종목 지정** | **모드 무관 즉시 전량 시장가 청산** |
| **거래지원 종료(상장폐지)** | **즉시 전량 시장가 청산** |
| 입출금 중단 | 신규 진입 금지 |
| 신규 상장 | 진입 대상에서 **제외** (변동성 과다) |

이건 뉴스 판단(LLM)이 아니라 **결정론적 규칙**이다. 코드로 처리한다.

## 13. 운영 비용 — 런타임 API 비용 0원 설계

10만원 예산에서 월 고정비가 붙으면 전략이 아무리 좋아도 본전을 못 맞춘다.
→ **24시간 돌아가는 부분에는 유료 API를 일절 쓰지 않는다.**

| 구성요소 | 비용 |
|---|---|
| 빗썸 시세/캔들/호가/잔고/주문 API | **무료** |
| 빗썸 투자경보·공지 | **무료** (`get_virtual_asset_warning` + 공지 페이지 파싱) |
| 코인 뉴스 | **무료** (RSS + **키워드 필터**, LLM 호출 없음) |
| ntfy 푸시 | **무료** (공개 토픽) / 자가호스팅 가능 |
| **합계 (런타임)** | **0원** |

### 13.1 뉴스는 LLM이 아니라 키워드 필터로 처리한다

원본 계획서의 "Claude가 뉴스를 읽고 판단" 레이어는 **런타임 비용**이므로 제거한다.
대신 `src/news.py` 가 RSS 제목/요약에 **결정론적 키워드 매칭**을 한다.

```
청산 트리거 키워드 : 해킹, 탈취, 상장폐지, 거래중단, 횡령, 파산, 도난, 지급불능
진입 보류 키워드   : 소송, 규제, 조사, 압수수색, SEC, 논란
```

- 트리거 키워드 히트 → 해당 코인 보유 시 **즉시 청산** (공지 감시와 동일 취급)
- 보류 키워드 히트 → 해당 코인 **신규 진입 24h 금지**
- 오탐이 나도 손해는 기회비용뿐이다. (철학: 틀린 회피 < 틀린 진입)

### 13.2 개발 단계의 Claude 사용은 비용 논점이 아니다

코드를 짜는 동안 Claude를 쓰는 것은 일회성이다. **문제는 24시간 루프 안에서
매시간 호출되는 유료 API다.** 그건 이 설계에 존재하지 않는다.

### 13.3 유일하게 남는 비용: 전기/호스팅

상시 구동 환경(집 PC 또는 최저가 VPS)의 전기·요금만 남는다.
이 결정은 M6 이전에 별도로 한다. (진행상황.md 7장 미결 항목)
