## 0. 코드 확인 결과 (추측 아님, 소스 직접 확인)

- **현재 CLI**: `-cpu -cores -numa -mem -disk -shares-ev01 -ht` 등 ev01/ev02/ev03별 옵션을 전부 수동으로 입력해야 함(`main.go`). 이 부분이 "옵션을 주렁주렁 달아야 하는" 문제의 실체.

- **폴더명 기반 스펙 매핑은 완전히 신규**: `-f`는 hostname 목록 파일일 뿐 폴더명 파싱 로직이 코드 어디에도 없음. `_spec.txt` 컨벤션도 저장소 전체에 존재하지 않음(신규 설계).

## 1. 목표 및 범위

**포함**: 폴더명 기반 스펙 자동 로드(CLI 옵션 대체), Task 폴더 예외 대응, 대상 VM만 조회하도록 조회 범위 축소(성능 개선), 폐쇄망 빌드/README 정비.
**제외**: 체크/교정 로직 자체의 신규 판정 항목 추가. 기존 `-fix` 파이프라인의 안전장치(게이트) 로직 변경 — 그대로 재사용.

## 2. 주요 기능 (우선순위 순, 결정사항 반영)

1. **대상 VM의 vCenter 인벤토리 폴더 자동 조회 → `_spec.txt` 자동 매칭** (필수, 핵심 요구사항)
   - **"폴더"의 정의(결정됨)**: 로컬 파일시스템 경로가 아니라, **VM이 실제로 속해 있는 vSphere 인벤토리 폴더**(vCenter 상의 Folder 오브젝트). 사용자가 폴더명을 직접 입력하는 게 아니라, 도구가 `-f`로 지정된 대상 VM들의 `InventoryPath`/부모 Folder를 vCenter API로 조회해서 폴더명을 알아낸다.
   - 조회된 폴더명을 하이픈으로 분리해 **레코드 1·3·4는 완전 일치, 레코드 2는 `CAE` 뒤 숫자를 정규화(무시)하고 비교**하는 규칙으로, 새 플래그 `-specRoot <로컬 스펙 저장 루트 경로>` 하위에서 이름이 매칭되는 스펙 디렉토리를 찾고, 그 안의 `[폴더명]_spec.txt`를 읽어 기존 플래그(`-cpu`/`-cores`/...)로 변환
     - 사용자 제공 예시로 규칙 검증됨: `TST-CAE001-SAMP48c-QRST` / `DEV-CAE001-SAMB16c-UVWX` / `DEV-CAE001-SAMC16c-UVWX+VDT` — 셋 다 레코드2(`CAE001`)만 같고 나머지가 달라 서로 다른 스펙으로 판정되어야 함(regex 예: `^CAE\d+$` 매칭 시 `CAE`로 정규화)
   - **매칭 후 확인 절차(결정됨)**: 매칭된 스펙을 dry-run처럼 화면에 보여주고 "이 스펙(`[폴더명]_spec.txt`, 이런 값들)으로 진행할까요? (y/N)" 확인을 받은 뒤에만 체크/교정 진행. 매칭되는 스펙이 없거나 여러 개면 진행하지 않고 사용자에게 알림(요구사항3의 대화형 폴백과 동일한 패턴)
   - **우선순위 확정**: 사용자가 CLI에서 같은 플래그를 수동으로 주면 그 값이 spec.txt보다 항상 우선 (결정됨)
   - `-affinityFile01/02/03`도 spec.txt 옆에 두는 파일 경로로 스펙에 포함
   - VM 그룹(ev01/ev02/ev03)이 서로 다른 vCenter 폴더에 속할 가능성은 낮지만, 다르게 나올 경우 그룹별로 폴더를 따로 조회해 각각 매칭
2. **폴더 셋업 스크립트** (신규 추가, 사용자 요청) — 현업에서 신규 CAE 폴더를 만들 때 폴더 + `[폴더명]_spec.txt` 스캐폴드를 생성해주는 보조 스크립트/서브커맨드. 예: `vm-param-check -initFolder <폴더명> [-template <기존폴더명>]`로 디렉토리와 spec.txt 틀을 만들고, 기존 유사 스펙이 있으면 그 값을 템플릿으로 복사
3. **Task 폴더 예외 처리** (필수) — 포트그룹명 파싱 매칭(`폴더이름-cae-10-1-2-3` 패턴) → 실패 시 대화형 확인(y/N 아니라 스펙 선택 프롬프트)으로 폴백
4. **병목 확인됨 — 대상 VM만 조회하도록 변경** (필수, 원인 특정 완료)
   - **근거**: `vcenter/client.go`의 `FetchVMs`(174행)는 `-f`로 VM 2대만 지정해도, `cv.Retrieve`가 **vCenter 인벤토리 전체의 무거운 속성**(`config.hardware`, `config.extraConfig`, `config.numaInfo` 등)을 다 받아온 뒤 `targetNames` 필터링을 **클라이언트 쪽에서 사후에** 적용함(`main.go:232` → `client.go:174`). 즉 병렬화 여부와 무관하게, 지정 대상이 몇 대든 인벤토리 전체 크기에 비례해서 느려지는 구조 — 사용자가 체감한 "VM 2대에도 느림"의 정확한 원인.
   - **해결 방향(2단계 조회로 전환)**:
     1. 1차: `name`, `guest.hostName`만 가져오는 가벼운 벌크조회로 전체 VM 목록에서 대상 이름과 일치하는 `ManagedObjectReference`만 추림(이 단계는 필드가 2개뿐이라 인벤토리가 커도 상대적으로 가벼움)
     2. 2차: 그 morefs만 골라 `property.Collector.Retrieve`로 무거운 속성 세트를 조회 — `targetNames`가 `nil`(전체 순회 모드)일 때는 기존처럼 1회 벌크조회 유지
   - `-specRoot` 자동매칭 모드는 항상 소수의 특정 VM(ev01/ev02/ev03)만 대상이므로 이 최적화의 효과를 가장 크게 받는 경로
   - (참고: `main.go`의 vCenter별 고루틴 병렬 연결과 `checkWG` 체크 병렬 처리는 이미 정상 동작 중이라 그대로 유지, 손댈 필요 없음)
5. **폐쇄망 빌드/README 정비** (필수) — 기존 `vendor/`는 이미 존재(확인됨), 기존 README 구조는 유지하고 `-specRoot`/`_spec.txt`/`-initFolder` 관련 신규 옵션 설명만 추가

3-1. **다중 vCenter 대응 보강** — ✅ **완료 (2026-08-18)**

   여러 vCenter를 `vcenter.txt`에 모두 넣고 대상이 여러 vCenter에 흩어져 있는 실제 운용 방식을 검토하면서 나온 두 가지를 반영했다.

   - **못 찾은 대상 경고 (신규)**: 기존에는 `-f`로 10대를 요청해도 8대만 찾으면 조용히 8대만 체크했고, vCenter 하나가 접속 실패하면 그 vCenter의 대상이 아무 경고 없이 사라졌다. "체크 통과"로 보이는데 실은 검사조차 안 된 서버가 남는 문제라 `findMissingTargets`를 추가하고, 조회 직후와 실행 마지막 양쪽에 경고를 출력한다(긴 로그에 묻히지 않도록).
   - **VM별 기대값으로 전환**: 대상이 서로 다른 스펙의 폴더에 걸쳐 있으면 이전 구현은 "폴더별로 나눠서 실행해주세요"로 중단했다. 이제 **VM마다 자기 폴더의 스펙**을 적용한다. 기대값 10개를 `expectSet` 구조체로 묶고, `buildExpect()`를 스펙마다 반복 호출하는 구조로 바꿨다(스펙 간 값 오염을 막으려 매번 `restoreFlags`로 사용자가 준 상태로 되돌린 뒤 적용).
   - **스펙 파일 권한 제한**: 스펙 파일이 `-fix`/`-out` 같은 동작 플래그까지 바꿀 수 있으면 파일 하나로 실제 설정 변경이 시작될 수 있어서, `specSettableFlags` 화이트리스트로 **기대값 관련 옵션만** 허용한다.
   - (VM 이름이 vCenter 간 중복되는 경우는 실환경에서 발생하지 않는다는 확인을 받아 대응하지 않음.)

   **검증 결과**:

   | 시나리오 | 결과 |
   |---|---|
   | vCenter 2개 × 서로 다른 폴더/스펙 | 각 VM이 자기 스펙으로 체크됨 — `aaaev01`은 cpu=40/cores=20(RND), `bbbev01`은 cpu=32/cores=16(MEM) |
   | 없는 대상 2대 + 접속 불가 vCenter 1개 | 경고에 못 찾은 대상 목록·건너뛴 vCenter 모두 표시, **실행 마지막에도 재출력** |
   | 실 vCenter 회귀(`-specRoot` 없이) | 상세·요약 CSV 모두 2단계 기준선과 동일 |

   빌드·`go vet`·전체 테스트 통과.

3-2. **`-yes`가 실제 설정 변경까지 건너뛰지 못하게 변경** — ✅ **완료 (2026-08-18)**

   확인 프롬프트가 두 군데(① 스펙 자동매칭 확인, ② `-fix` 실제 변경 확인)인데 `-yes` 하나가 둘 다 건너뛰고 있었다. 사용자 결정에 따라 **②는 `-yes` 여부와 무관하게 항상 묻도록** 변경했다(`runFix`에서 `autoYes` 분기 제거, 파라미터도 삭제). 이제 `-yes`는 ①에만 적용된다.

   초기 `vm-param-fix-plan.md`에서 "`-yes`/`--force` 같은 스킵 플래그는 처음부터 만들지 않는 걸 제안 — 실수로 무인 실행되는 경로 자체를 없애기 위함"이라고 했던 방향과 일치한다. 무인 실행으로 stdin이 비어 있으면 `confirmYes`가 false를 돌려주므로 **아무것도 바꾸지 않고 종료**한다(안전한 쪽으로 실패).

   **검증**(vcsim, 전원 OFF 상태 VM 2대):

   | 시나리오 | 결과 |
   |---|---|
   | `-fix -yes` + `n` | 스펙 확인은 생략(`-yes 지정됨`)되지만 변경 확인은 뜸 → 취소, 무변경 |
   | `-fix -yes` + `y` | 게이트 통과 → 적용 → 재검증까지 진행 |
   | 재검증 기대값 | 스펙값이 정확히 사용됨(cpu=40/numa=20/mem=16) — `expectByVM`이 재검증 경로까지 올바르게 전달됨을 확인 |
   | 교정 반영 | `config.hardware.numCPU 40/40 OK`, `numa.vcpu.maxPerVirtualNode 20/20 OK` |

   > 재검증에 남는 `설정없음` 항목들은 vcsim이 일부 필드를 구현하지 않아 생기는 시뮬레이터 한계다. `-fix`의 실제 값 반영 정확성은 이전 프로젝트에서 실 vCenter로 검증되어 있으며, 이번 작업에서 재검증하지는 않았다(이번 변경은 확인 프롬프트와 기대값 전달 경로에 한정).
4. **폴더 셋업 스크립트 구현** — ✅ **완료 (2026-08-18)**
   - `config/init.go` 신설: `InitFolder(specRoot, folderName, templateFolder)`. `main.go`에는 `-initFolder`/`-template` 플래그와 vCenter 미접속 조기종료 훅(`-demo`/`-scale`와 같은 자리)만 얇게 추가.
   - **안전장치**: 폴더명이 CAE 규칙에 안 맞으면 거부(만들어도 자동매칭이 안 되므로), 이미 같은 스펙(차수만 다른 경우 포함)이 존재하면 **덮어쓰지 않고 거부**.
   - `-template` 미지정 시 필수/선택 옵션 이름을 전부 보여주는 빈 틀 생성. `-template=<기존 폴더명>` 지정 시 그 스펙의 값을 그대로 복사 — **affinity 파일처럼 상대경로로 참조된 파일도 새 디렉터리로 함께 복사**해서, 복사된 spec.txt가 옛 디렉터리를 계속 가리키는 문제를 방지.

   - **CLI 종단 검증**: 빈 틀 생성 → 값 채움 → **3단계 `-specRoot` 자동매칭 도구로 실제 매칭 성공**(별도 폴더가 아니라 같은 파이프라인의 다음 단계로 바로 이어짐)까지 확인. 중복/규칙위반/`-specRoot` 누락 거부, `-template` 복사도 모두 실동작 확인.
   - 빌드·`go vet`·전체 테스트 통과.
5. **Task 폴더 예외 로직 구현** — ✅ **완료 (2026-08-18)**
   - `config/portgroup.go` 신설: `ExtractFolderFromPortgroup` — 포트그룹명 `<폴더명>-cae-옥텟-옥텟-옥텟-옥텟`에서 폴더명을 복원하는 정규식 매칭. 단위 테스트 6종 통과.
   - `main.go`에 VM 단위 폴백 체계 추가: `resolveVMFolders`가 각 VM의 `vm.Folder`가 CAE 규칙(`config.NormalizeFolderName`)을 만족하는지 먼저 확인 → 만족하면 그대로, 아니면(`Task` 등) `resolveExceptionFolder` 호출.
     - **1차: 포트그룹 파싱** — VM에 붙은 네트워크 어댑터 포트그룹명 전부에서 후보를 뽑아 `FindSpec`으로 실존 여부 확인. **정확히 하나만 유효하면** 자동 확정.
     - **2차: 대화형 폴백** — 후보가 0개(또는 2개 이상이라 자동으로 못 고르면) `promptFolderName`으로 직접 입력받음. `?` 입력 시 `-specRoot` 아래 사용 가능한 스펙 목록을 보여줌. 3회 시도해도 유효한 입력이 없으면 중단.
     - **`-yes`와의 상호작용**: 자동으로 못 정하는 상황에서 `-yes`가 켜져 있으면 대화형 프롬프트로 못 들어가므로 **즉시 중단**하고 `-yes` 없이 재실행하라고 안내(무인 실행 중 알 수 없는 입력을 기다리며 멈추는 것을 방지).
   - 폴더별이 아니라 **VM별로** 해석하므로, 같은 `Task` 폴더 안에 서로 다른 스펙에 속한 VM이 섞여 있어도 각자 올바른 스펙으로 갈린다. dry-run 출력에도 "vCenter 폴더: Task (VM: ...) ※ CAE 규칙과 안 맞아 포트그룹 파싱으로 스펙 결정"처럼 **출처를 명시**해 사람이 확인 단계에서 알아챌 수 있게 함(5장 안전장치와 일관).
   - **검증**(vcsim, `Task`라는 이름의 실제 폴더를 만들고 VM 네트워크 어댑터에 포트그룹을 붙여서):

     | 시나리오 | 결과 |
     |---|---|
     | Task 폴더의 VM 2대 모두 포트그룹에 실제 폴더명 내포 | 둘 다 자동 유추 성공 → 옵션 자동 적용 → 체크 완주 |
     | 포트그룹 없음/무관 + `-yes` | 사람에게 물어볼 수 없다는 사유와 함께 즉시 중단 |
     | 포트그룹 없음/무관 (대화형) | `?`로 스펙 목록 조회 → 유효한 이름 입력 시 그 스펙으로 진행 |
     | 실 vCenter, `-specRoot` 없이 | 상세·요약 CSV 모두 2단계 기준선과 동일(회귀 없음) |
   - 빌드·`go vet`·전체 테스트 통과.

## 4. 기술 스택 / 아키텍처

- 기존 Go/govmomi 스택, 동일 패키지 구조에 신규 파일만 추가:
  ```
  vm-param-check/
  ├── main.go          (수정) -specRoot 플래그, spec 병합 로직 진입점
  ├── config/
  │   └── spec.go        ★ 신규 — 폴더명 파싱 + _spec.txt 로더 (LoadLines 재사용)
  ├── vcenter/inventory.go ★ 신규 — 대상 VM의 InventoryPath/부모 Folder 조회 (govmomi object.VirtualMachine.Path 또는 SearchIndex 활용)
  ├── vcenter/client.go (수정) FetchVMs를 2단계 조회(가벼운 name 조회 → 대상 morefs만 무거운 속성 조회)로 전환
  ├── fixer/gates.go   (그대로) 안전장치 재사용
  └── (기타 기존 구조 그대로)
  ```
- **spec.txt 포맷**: 사용자 예시(`ht=on --cores=20 --numa=20`)를 그대로 살려 기존 CLI 플래그 문법 재사용 — 새 파서 대신 `flag` 패키지 재파싱 또는 `config.LoadAffinityFile`과 동일한 `key=value` 방식 중 1단계에서 실제 예시 파일로 확정

## 5. 안전장치 (결정됨: 기존과 동일 수준 요구)

이 개선은 체크 파이프라인 앞단(옵션 자동화)만 건드리고, 실제 설정 변경(`-fix`)은 기존 `fixer/gates.go`·`fixer/apply.go`를 그대로 통과합니다. 즉:
- 그룹 동질성 검증 + 전원 OFF 게이트 — 변경 없음, 그대로 통과해야 함
- spec.txt로 자동 로드된 값도 dry-run 단계에서 사람이 최종 확인 후에만 적용
- **신규 리스크**: 폴더명 매핑이 잘못된 스펙을 자동으로 골라올 경우, 그 결과가 게이트를 통과해버릴 수 있음 → 이미 결정된 대로 매칭 직후 "이 스펙(vCenter 폴더: ..., 매칭된 spec.txt: ...)으로 진행할까요? (y/N)" 확인을 반드시 거치고, dry-run 출력에도 스펙 출처(자동매칭 vs 수동)를 표시
