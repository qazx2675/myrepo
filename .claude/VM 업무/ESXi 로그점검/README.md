# ESXi 로그점검 (ESXi Log Check) 툴 및 모의 환경 기술문서

이 문서는 ESXi 서버 환경에서 발생하는 각종 치명적인 로그(MCE, PSOD, APD/PDL, vSAN ESA, NVMeoF 단절 등)를 수집 및 분석하는 도구(`esxi-log-check`)와 이를 검증하기 위한 **ESXi 모의 환경(Mock Generator)**의 설치, 빌드 및 사용 가이드를 제공합니다.

⚠️ **주의사항 (Disclaimer)**
본 로그 분석 관련 스크립트 및 툴은 100% 신뢰하기보다는 참고용(보조 도구)으로 사용하는 것을 권장합니다. 설정 변경 스크립트의 경우에는 설정변경후 랜덤한 서버 몇개를 확인해서 실제로 변경되었는지 확인하는 절차가 반드시 필요합니다.

## 1. 빌드 및 설치 방법

본 프로젝트는 보안이 적용된 **인터넷이 차단된 폐쇄망 환경**에서도 빌드가 가능하도록 의존성 모듈(`vendor`)을 모두 포함하고 있습니다. Go 언어 컴파일러 환경이 구성되어 있어야 합니다.

1. **프로젝트 다운로드 및 이동**
   Git 등에서 해당 저장소를 다운로드하여 통째로 압축한 뒤, 폐쇄망 서버(Rocky Linux 등)로 이동시키고 압축을 해제합니다.
2. **빌드 경로로 이동**
   ```bash
   cd "ESXi 로그점검"
   ```
3. **바이너리 빌드**
   폐쇄망 환경이므로 외부 네트워크 접근 없이 로컬 패키지(`vendor`)만을 사용하도록 설정된 `setup.sh` 스크립트를 실행하여 빌드해야 합니다.
   ```bash
   bash setup.sh
   # (실행 시 자동으로 go build -mod=vendor 명령어가 수행됩니다)
   ```
4. **권한 부여**
   필요한 스크립트 파일들의 실행 권한을 부여합니다.
   ```bash
   chmod +x run_analyzer.sh
   chmod +x esxi-log-check
   ```

### 전역 명령어로 사용하기 (선택 사항)
빌드된 `esxi-log-check` 바이너리를 매번 해당 폴더로 이동하지 않고 시스템 어디서든 기본 명령어처럼 편리하게 사용하려면, 환경 변수(`PATH`)가 지정된 기본 경로로 파일을 복사하거나 이동해 주시면 됩니다.
```bash
# 예: /usr/local/bin 경로로 복사하여 전역 명령어로 등록
sudo cp esxi-log-check /usr/local/bin/
```
이후부터는 터미널 어느 경로에서나 `esxi-log-check` 명령어만 입력하면 툴이 즉시 실행됩니다.

## 2. 사용 방법

가장 직관적이고 권장되는 사용 방법은 메뉴 기반의 쉘 스크립트인 `run_analyzer.sh`를 활용하는 것입니다. CLI를 통한 직접 실행도 가능합니다.

### 2.1 대화형 스크립트 실행 (권장)
```bash
./run_analyzer.sh
```
위 명령어를 실행하면 다음과 같은 대화형 메뉴가 나타납니다.

1. **실제 ESXi 서버 분석 (IP 직접 입력)**: 분석할 단일 타겟의 IP를 입력하여 즉시 로그를 수집하고 텍스트로 요약 결과를 확인합니다.
2. **실제 ESXi 서버 분석 (호스트 목록 파일 기반)**: 분석 대상 서버들의 IP가 줄바꿈으로 기재된 파일(예: `real_hosts.txt`)을 입력받아 일괄 분석하고 HTML 형태의 리포트를 생성합니다.
3. **모의 테스트 모드 실행**: 전체 에러 패턴을 모의(Mock) 주입하여 분석 기능이 정상 작동하는지 확인하기 위해 `mock_test_report.html`을 생성합니다. (결함 확인용)
4. **웹 서버 모드로 실행 (백그라운드)**: 대상을 선택(모의 테스트 / 실제 IP / 호스트 파일)하여 백그라운드에 웹 서버(기본 12345 포트)를 구동합니다. 실시간 대시보드를 제공합니다.
5. **임시 파일 및 캐시 정리**: 분석 과정에서 생성된 캐시 데이터, 임시 수집 폴더, 불필요한 `.csv` 파일 등을 말끔하게 정리합니다.
6. **종료**: 스크립트를 종료하고 메뉴를 빠져나갑니다.

### 2.2 웹 서버 대시보드 모니터링 연동 방법
1. `./run_analyzer.sh` 실행 후 **4번 (웹 서버 모드)**를 선택합니다.
2. "2) 실제 ESXi IP 직접 입력" 또는 "3) 실제 호스트 목록 파일 기반" 등을 선택하여 타겟을 지정합니다.
3. 웹 브라우저를 열고 해당 리눅스의 IP와 할당된 포트로 접속합니다. (예: `http://192.168.0.58:12345`)
4. 브라우저 내 화면을 통해 각 ESXi 서버의 위험(Critical) 및 경고(Warning) 로그 통계를 한눈에 확인할 수 있습니다.

## 3. 옵션별 상세 설명

인터랙티브 스크립트(`run_analyzer.sh`) 외에, 분석기 코어 바이너리(`esxi-log-check`)를 직접 실행하여 자동화 파이프라인이나 스케줄러(cron 등)에 연동할 때 사용하는 CLI 인자값입니다.

- `-w <파일명>`
  - 설명: 분석할 대상 호스트(IP) 목록이 담긴 텍스트 파일을 지정합니다. 호스트들은 한 줄에 하나씩 작성되어야 합니다. (예: `-w hosts.txt`)
- `-format <형식>`
  - 설명: 출력될 결과 포맷을 지정합니다.
  - 지원 포맷: `text` (터미널용), `html` (시각적 리포트), `json` (타 시스템 연동용)
- `-out <파일명>`
  - 설명: 결과를 저장할 파일명을 지정합니다. 이 옵션을 생략하면 기본적으로 표준 출력(터미널)에 표시됩니다. (예: `-out report.html`)
- `-server <주소:포트>`
  - 설명: 분석 결과를 정적 파일로 남기지 않고, 내장된 HTTP 웹 서버를 통해 서비스합니다. (예: `-server :12345`) 브라우저로 접속해 리포트를 볼 수 있습니다.
- `-onlyProblems`
  - 설명: 로그 분석 결과, 이상이나 발견된 오류(Finding)가 존재하는 호스트만을 필터링하여 출력합니다. 정상인 호스트는 리포트에서 생략됩니다.

## 4. 문서별 고유 설명

### 4.1 로그패턴 분류 (32종 카테고리)
현재 `esxi_critical_patterns.yaml` 환경 설정 파일에 정의된 주요 카테고리는 다음과 같습니다.

* **CPU_MCE**: MCE(Machine Check Exception), PSOD를 유발하는 치명적인 하드웨어 에러 (엔지니어 영역)
* **MEMORY**: 메모리 컨트롤러 불량, Uncorrectable ECC 에러 및 DIMM 폴트 (엔지니어 영역)
* **STORAGE_APD_PDL**: All Paths Down, Permanent Device Loss와 같은 스토리지 단절 현상 (서버운영/엔지니어 복합)
* **STORAGE_LATENCY**: 스토리지 읽기/쓰기 응답 지연 (서버운영 영역)
* **VSAN_ESA**: vSAN 관련 네트워크 단절, 디스크 그룹 장애 및 커밋 실패 (엔지니어/운영 영역)
* **NETWORK_LINK**: NIC 링크 다운, vmnic 단절 현상 (서버운영 영역)
* **NFS_LOST**: NFS 데이터스토어 연결 유실 (서버운영 영역)
* **HOSTD_CRASH**: hostd 프로세스 크래시 (서버운영 영역 - 보통 서비스 재시작 혹은 재부팅 조치)
* **KERNEL_PANIC**: 커널 패닉 및 시스템의 비정상 리부트 (서버운영 영역)
* **HARDWARE_SENSOR**: 온도, 팬, 전원, 배터리 등 IPMI 센서 에러 (엔지니어 영역)
* **DUMP**: 코어덤프 및 크래시 덤프 수집 관련 에러 (엔지니어 영역)

*(그 외 NVM_EOF, VM_STUN, SECURE_BOOT 등 총 32개의 세밀한 정규표현식 카테고리를 지원하여 각종 문제를 분류합니다.)*

### 4.2 로그패턴에 대한 테스트 케이스
모의 테스트 도구(`esxi_mock_logger`)는 실제 운영망에서 발생할 수 있는 32개 카테고리의 100여 개 세부 상황을 코드 수준에서 재현할 수 있습니다. 이를 통해 툴의 신뢰성과 무결성을 사전에 검증할 수 있습니다.

* **MCE / PSOD 발생 테스트**:
  - `vmkernel.log`에 `@BlueScreen: Machine Check Exception` 메시지를 가상으로 주입합니다.
  - 분석기가 이를 `CRITICAL` 등급으로 식별하고, 정확히 **하드웨어 엔지니어 조치 권고**로 안내하는지 확인합니다.
* **메모리 Uncorrectable 에러 테스트**:
  - `Memory controller error` 메시지 발생 시 정확하게 불량 메모리 뱅크 점검이 필요한 **엔지니어 영역**으로 분류하는지 테스트합니다.
* **커널 패닉(Kernel Panic) 테스트**:
  - `hostd.log`나 시스템 로그에 커널 패닉 메시지가 주입되었을 때, 이를 **서버운영 영역 (재부팅 조치 필요)**으로 적절히 가이드하는지 확인합니다.
* **코어 덤프(DUMP) 테스트**:
  - 디스크 공간 부족 등으로 인한 덤프 수집 실패 로그 발생 시, 덤프 수집 권한을 다루는 **하드웨어 엔지니어**에게 담당이 배정되도록 분류하는지 테스트합니다.
* **스토리지(APD/PDL) 테스트**:
  - 일시적 경로 단절(APD)과 영구 장치 손실(PDL)을 구분하여 리포팅하고, 스토리지 스위치 조치(포트 확인, LUN 확인 등)를 올바르게 권고하는지 검증합니다.

위의 테스트 케이스들은 `./run_analyzer.sh` 내의 **3번 메뉴(모의 테스트 모드)**를 통해, 혹은 웹 인터페이스를 통해 언제든 원클릭으로 검증(무결성 확인)해 볼 수 있습니다.
