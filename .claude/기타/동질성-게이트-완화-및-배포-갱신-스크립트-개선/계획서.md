### 요청 내용

`-fix` 실행 중 아래 메시지들로 정상적인 교정이 중단된다.

1. `동질성 검증 실패: ev01 그룹 내 스펙 불일치 …` — 코어/소켓은 NUMA로 판단하는 값이라면 비교에서 빼야 한다. NUMA도 FAIL이 날 수 있는 항목이기 때문이다.
2. PASS인 VM이 한 대라도 있으면 "그룹별 VM 대수가 다르다"며 작업이 진행되지 않는다. PASS/FAIL과 상관없이 ev01/ev02가 같은 구성인지만 봐야 한다.
3. 위 수정을 기존 파일에 영향 없이 서버에 반영하는 게 `update_deploy.sh`가 맞는지, 어떻게 실행하는지 알려 달라. 회사 환경에서 쓰는 `01.vm_setting_check_insert.sh`에는 영향이 없어야 한다.
4. (진행 중 추가) master에 반영하고, 브랜치에는 해당 디렉토리만 올려 달라.

## 1. 원인

### (1) 코어/소켓·NUMA 비교 (`fixer/gates.go` `diffSpec`)

코어/소켓(`hardware.numCoresPerSocket`)은 NUMA에서 파생되는 값이 아니라 vCenter의 **별도 설정**이다(NUMA는 `numa.vcpu.maxPerVirtualNode`). 다만 둘 다 `-fix`가 기대값으로 직접 고치는 항목(`fixable`)이라 FAIL인 VM은 값이 다를 수밖에 없다. 게이트가 이 값을 비교하면 **고치려는 바로 그 불일치** 때문에 교정이 막힌다.

### (2) 그룹 대수 (`checkHomogeneity`)

그룹 간 VM 대수를 교정 대상(`plan.TargetVMs()`)으로 셌다. PASS인 VM은 교정 대상에서 빠지므로, ev01 PASS 1 + FAIL 1 / ev02 FAIL 2 같은 실제 2:2 구성이 ev01=1대, ev02=2대로 계산됐다. 그런데 `CheckGates`에는 조회한 VM 전부(`allVMs`)가 이미 넘어오고 있었다.

### (3) `update_deploy.sh` — 두 가지 결함 (록키에서 그대로 재현)

- 배포 폴더를 통째로 `<경로>.bak.<시각>`으로 옮기고 새로 복사 → 배포 경로에 같이 있던 `01.vm_setting_check_insert.sh`, `vcenter.txt`, `SPEC_DIR/`가 배포 경로에서 **사라짐**(백업 폴더에만 남음).
- 9/18 커밋 `f8a2e7e`(vendor 공유화)로 이 도구의 `vendor/`가 저장소에서 빠지고 `setup.sh`가 `../../../공통/govendor/govmomi-0.39.0`로 심볼릭 링크를 거는 구조가 됨 → 평평한 배포 경로에는 그 경로가 없어 `go build -mod=vendor`가 `inconsistent vendoring`으로 실패. 앞 결함 때문에 이미 옮겨진 뒤라 **실행파일까지 없는 상태**로 끝남.

## 4. 열린 항목 / 주의

- vCPU와 HT도 `-fix`가 고치는 항목이라 같은 논리가 적용될 수 있다. 이 둘이 FAIL인 VM이 섞여 게이트에 막히면 `diffSpec`에서 같은 방식으로 뺄 수 있다(이번엔 요청 범위를 넘지 않음).
- **`vm-param-check-standalone`은 master와 자동으로 동기화되지 않는다.** master의 이 폴더를 고칠 때마다 아래 `작업기록.md`의 절차로 다시 조립해서 올려야 한다. `update_deploy.sh`는 이 브랜치에서 받는다.
- `update_deploy.sh` 기본 URL은 GitHub public 저장소다. 저장소를 private로 바꾸면 인증 없이 받을 수 없으므로 `REPO_URL`(토큰 포함 주소 / 사내 미러 / `file://` 경로)을 지정해야 한다.
