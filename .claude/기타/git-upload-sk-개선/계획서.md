# git-upload-sk 개선 프로젝트 계획서

> 상태: **초안 확정(사용자 검토 중)** — 사용자가 완벽하다고 판단하면 그때 기존 `git-upload-sk` 스킬에 반영한다. 그 전에는 스킬을 수정하지 않는다.
> 요구사항·인터뷰 결정: [요구사항.md](요구사항.md) (결정 1~23)
> 실행은 승인 후 `/jev-plan-router` 로 단계별 모델 배정.

## 목표 및 범위

- **0순위 목표:** 신규 작성이든 업데이트든 스크립트를 **한 번 실행**하면 폐쇄환경 세팅이 끝난다.
  - 신규: `가이드 실행 → 변수 입력 → (setup.sh 가 있으면 자동 이어서) → 완료`
  - 기존 프로젝트: `패치 스크립트 적용 → 신규·변경 변수만 가이드 → 완료`
- **포함**
  - 빈 변수 입력 가이드 (`read -p`, 설명·예시, 검증, 색상)
  - 앵커 기반 업데이트 패치 스크립트 (마스킹된 현장 수정 보존)
  - 패치 생성기 (`make_update.sh`)
  - 위 규칙을 `git-upload-sk` 스킬에 넣을 문안 (승인 후 반영)
  - config_check 파일럿
- **제외**
  - 스킬 본문 수정 (승인 전)
  - auto_setup·awx_script 소급 적용 (파일럿은 config_check 만)
  - Python·Perl 의존

## 산출물 구조 (프로젝트 쪽)

| 위치 | 내용 |
|---|---|
| `conf/` (설정파일을 쓰는 프로젝트) 또는 새 `setup/` | **가이드·패치에 필요한 스크립트와 파일만** 둔다 (패치와 무관한 파일 금지). 프로젝트 루트는 깨끗하게 유지 |
| `setup_guide.sh` | 신규용 대화형 가이드 (역할 선택 → 입력 → 검증 → 적용 → setup.sh 가 있으면 이어서 실행) |
| `update_v<버전>.sh` | 버전별 **자체포함 단일** 패치 스크립트 (엔진 + 이번 변경 명세 + 변수 변경분) |
| `vars.manifest` | 변수 목록. 가이드·패치·생성기가 공유 (패치에 필요한 파일이므로 허용) |
| (개발자용, 스킬 쪽) `make_update.sh` | 이전→신규 변경과 manifest 로 `update_v*.sh` 를 자동 생성, 사람 검토 단계 포함 |

## 주요 기능

### 필수

1. **manifest** (파이프 구분)
   - 필드: `변수명 | 대상(파일/conf) | 종류(path·host·secret·text) | 역할(os8·os6·공통) | 그룹(택일·의존) | 필수 | 설명 | 예시 | 검증 | since | renamed_from`
   - 헷갈렸던 `auto_done_dir`/`auto_done_host` 는 요구사항 2-1절의 **정확한 동작 설명**을 `설명` 필드에 그대로 넣는다.
2. **가이드 (`setup_guide.sh`)**
   - 역할 선택 후 그 역할의 변수만 `read -p` 로 질문
   - 변수마다 `echo` 로 설명 + 예시 (`예: /path/config_check.sh`)
   - 현재값 표시, Enter 로 유지
   - 비밀번호는 `read -s`, 화면·로그에는 마스킹
   - 택일·의존 그룹은 상황 질문("이 스크립트는 어느 서버에서 실행?")으로 하나만 채움
3. **점검**
   - 정적 검증(경로 존재·형식) + 연결 점검(예: `gossh -p` 로 1대 `hostname`)
   - 변수별 `정상 / 이상(이유)` 표 출력 → 이상 변수만 재입력하거나 건너뛰기
   - 전체 dry-run 은 프로젝트에 안전한 `--dry-run` 이 있을 때만
4. **업데이트 엔진**
   - 입력 사본의 `\r` 제거 (vim 으로 정리한 LF 사본 기준, CRLF 가 섞여도 자동 처리, 결과는 LF)
   - **앵커 기반 삽입·치환**
   - **마스킹 불변 검사**: 삭제·변경되는 기존 줄에 주석·코멘트 문구가 있거나, 앵커가 없거나 여러 곳이면 적용하지 않고 중단 + 위치 안내
   - 적용 후 `bash -n` 문법 확인
   - 자동 `.bak`(타임스탬프), 실패 시 자동 복구, `--undo`
5. **업데이트 중 변수 처리**
   - 신규·변경된 변수만 질문, 기존 값 자동 이전 (이름 변경은 rename map)
   - 삭제된 변수는 유지하되 경고
6. **실행 범위**
   - 변수 적용 → 점검 → `setup.sh` 이어서 실행(y/n) → 요약
   - **`setup.sh` 가 없으면 이 단계는 건너뜀** (보통 `setup.sh` 는 Go 프로젝트에만 있음)
   - 마지막에 Disclaimer 출력: "설정 변경 후 랜덤 서버 몇 대에서 실제 변경 확인"
7. **색상 규칙** (스킬 규칙에도 포함)
   - 정상=초록, 경고=노랑, 오류=빨강, 안내=시안, 변수명=굵게, 예시=회색
   - `NO_COLOR` 또는 tty 가 아니면 끔
   - 기존 `[O]` / `[!]` / `[X]` 표시와 통일
8. **비밀번호 저장**: 소스에 평문 기록 + 파일 권한 600 + "저장소 커밋 금지" 경고. 화면·로그·백업 출력은 마스킹.

### 선택

- 이전·신규 비교로 `rename map` 후보 자동 제안

## 단계별 마일스톤

1. **인터뷰 확정** — 결정표(1~23) 확정. 남은 가정 없음 확인.
2. **manifest 스키마 + 공용 라이브러리** — bash 4.1 호환 (`sed`/`awk`/`grep` 만). 이후 모든 스크립트의 기반이라 가장 먼저.
3. **가이드** — 입력·검증·색상·역할·택일/의존 그룹, 빈 변수 5개 이하 확인 질문.
4. **업데이트 엔진** — 앵커 적용, 마스킹 검사, 백업·복구·`--undo`, 변수 이전.
5. **생성기 `make_update.sh`** — 엔진을 한 파일에 합쳐 복사·붙여넣기 반입 가능하게.
6. **config_check 파일럿** — 기존 `apply_auto_mode.sh` 를 대체하고, `auto_done_dir`/`auto_done_host` 를 택일 그룹으로 모델링.
7. **검증** — .58 랩 + RHEL6(.60) bash 4.1 에서 아래 시나리오 실행.
8. **스킬 반영 문안** — 위 규칙을 `git-upload-sk` 에 넣을 문안으로 정리 → 사용자 최종 승인. 승인 전에는 스킬을 수정하지 않는다.

## 검증 시나리오 (완료 기준)

- **신규 (필수):** 빈 변수 사본에 스텁 입력 → 가이드 한 번으로 (setup.sh 가 있으면) 설치까지 통과. `setup.sh` 없는 프로젝트(config_check)는 설치 단계를 건너뛰고 통과.
- **업데이트:** 벤더 문자열·경로·주석·코멘트를 수정한 사본에 적용 → 변경 0건 유지, 신규 변수만 질문, 실패 시 자동 복구.
- **입력 이상:** 잘못된 경로·응답 없는 호스트·CRLF 혼입 → 변수별 이유 표시, 재입력·건너뛰기, 중단 후 원상복구.
- **RHEL6 bash 4.1:** 같은 시나리오를 실제 RHEL6 환경에서 확인.
- 실제 현장 값(실경로·실서버)은 검증할 수 없다. 스텁 검증이라는 점을 결과 보고에 명시한다.

## 기술 스택 / 아키텍처

- **bash + sed/awk/grep 만** — 폐쇄망 서버에 Python·Perl 이 없고 RHEL6 에서도 돌아야 하므로.
- **자체포함 단일 패치 스크립트** — 반입이 복사·붙여넣기 1회라서 엔진과 명세를 한 파일에 넣는다.
- **앵커 기반** — diff 패치는 이번에 회사 사본이 달라 실패했다. 줄 일치 대신 코드 앵커로 위치를 찾고, 못 찾으면 중단.
- **conf 프로젝트** — Go 등 빌드 언어는 `conf/*.conf` 에 `key=value` 로 적용 (auto_setup 에서 쓴 방식과 동일).

## 리스크 및 제약사항

- **빈 변수가 5개 이하이면 실제로 실행할지 먼저 묻는다.** 변수가 적은 단순한 프로젝트에는 가이드·패치가 과할 수 있어서, `가이드를 실행하시겠습니까? (y/n)` 로 사용자가 직접 정한다. n 이면 변수 목록과 직접 채울 위치만 안내하고 종료.
- **앵커 취약성:** 업스트림이 앵커 줄을 리팩터링하면 중단된다. 생성기가 앵커 후보를 제시하고 사람이 검토.
- **붙여넣기 크기:** 터미널 붙여넣기 한계로 단일 스크립트가 잘릴 수 있다. 엔진 크기 상한과 끝줄 검사(잘림 감지)를 둔다.
- **연결 점검의 비밀번호 노출:** `gossh -p` 는 프로세스 목록에 보일 수 있다. 점검은 1대·짧은 시간으로 하고 가이드에 안내.
- **마스킹 판정 한계:** 주석·코멘트 변경 판단은 줄 패턴(`#`, 담당자·감사합니다 등)이라 프로젝트별 키워드를 manifest 에서 추가할 수 있게 한다.
- **현장 값 검증 불가:** 폐쇄망이라 실제 경로·서버를 개발 중에 확인하지 못한다. 가이드의 점검 단계가 이를 현장에서 보완.
- **스킬 범위 확장:** 모든 프로젝트에 적용되면 과합니다 → 위 "5개 이하 확인 질문"으로 완화.

## 확정된 가정

- **A.** `setup/`(또는 `conf/`)에는 **패치에 필요한 스크립트와 파일만** 둔다 (`vars.manifest` 포함, 그 외 파일 금지).
- **B.** 완료 기준: 신규 + 업데이트 보존 + 입력 이상 + RHEL6 bash 4.1 호환 모두 포함.
- **C.** `setup.sh` 가 없는 프로젝트는 설치 단계를 건너뛴다 (보통 `setup.sh` 는 Go 프로젝트에만 있음).
