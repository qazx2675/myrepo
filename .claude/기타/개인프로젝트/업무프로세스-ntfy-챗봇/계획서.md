# 업무프로세스 ntfy 챗봇 — 계획서

휴대폰(ntfy)으로 질문하면 **집 PC의 로컬 LLM(qwen3:8b)**이 **업무프로세스 문서만 근거로** 답하고, 답변마다 👍/👎 피드백을 남길 수 있게 한다.
미답변 질문과 피드백은 질문마다 기록해 두고, 이를 활용해 문서를 보강하는 **보조툴**을 다음 단계로 만든다.

> 상태: **계획만 작성**. 코드는 아직 만들지 않았다.

---

## 1. 배경과 전제

| 항목 | 내용 |
|---|---|
| 사용 이유 | 사내망에서는 외부 통신이 불가 → 업무프로세스 문서는 **집 PC**에 있고, 여기서 LLM을 돌린다 |
| 질문 위치 | 휴대폰 (회사·외부, LTE 등) |
| 채팅 수단 | **ntfy** — 공용 서버 **ntfy.sh 사용 (확정)** |
| 문서 | 텍스트 1개, **712줄 / 15,782자** |
| 데이터 저장 위치 | **`D:\업무프로세스`** (문서·로그·상태·설정 모두) |
| PC | Windows, RTX 3060 12GB, DDR4 48GB, NVMe(DRAM리스, **HMB 지원**) |
| LLM | Ollama + **qwen3:8b** — **이미 설치됨** |
| Python | **설치 안 되어 있음 → 설치 필요** (5.3 단계 1) |

## 2. 전체 구조

```
[휴대폰 (Android / iPhone)]
   │  ① 질문 발행 (질문 토픽)
   ▼
[ntfy.sh] ◀────────────────────────────────────────┐
   │  ② 구독 스트림                                   │ ④ 답변 발행 (답변 토픽)
   ▼                                                │    + [👍 좋음] [👎 나쁨] 버튼
[집 PC: bot.py] ──③ 문서 전체 + 질문──▶ [Ollama] ──┘
   │
   ├─ ⑤ 버튼 클릭 → 피드백 토픽 → bot.py → D:\업무프로세스\logs\feedback.jsonl
   └─ ⑥ 모든 질문·답변 → qa.jsonl / 미답변 → unanswered.jsonl
                     ↓ (다음 단계)
              [보조툴] 미답변·👎 검토 → 문서 보강 초안 → 사용자 확인 후 반영
```

- 집 PC는 **바깥으로 나가는 연결만** 쓴다 (ntfy 구독·발행). 포트 개방·공유기 설정 불필요.
- 토픽 3개
  - 질문 토픽 (`…-q`): 휴대폰 → 봇
  - 답변 토픽 (`…-a`): 봇 → 휴대폰 (휴대폰은 이것을 구독)
  - 피드백 토픽 (`…-fb`): 답변의 버튼 → 봇

## 3. 핵심 결정

### 3.1 RAG 없이 "문서 전체를 매번 넣기"

- 문서가 15,782자로 작아서 **통째로 프롬프트에 넣을 수 있다**. 임베딩·벡터DB·청킹이 필요 없다.
- 장점: 검색 누락이 없음, 구성 단순, 문서 수정 시 재색인 불필요.
- 문서는 **system 메시지 맨 앞**에 고정 → Ollama가 질문 사이에 문서 부분을 재계산하지 않아(프롬프트 캐시) 두 번째 질문부터 빠르다.
- 즉 `업무프로세스.md`는 **모든 질문에 기본으로 첨부되는 문서**다. 휴대폰에서 따로 첨부할 필요가 없다.
- 마크다운 형식이면 `#` 제목이 그대로 모델에 전달되어, 답변의 `(근거: …)`에 항목 제목을 정확히 적기 쉽다. 문서를 쓸 때 절차마다 제목을 달아 두면 좋다.
- 문서는 **질문마다 다시 읽는다** → 파일을 고치면 재시작 없이 반영 (보조툴이 문서를 보강해도 바로 적용).

### 3.2 모델: qwen3:8b (설치 완료)

| 항목 | 값 | 근거 |
|---|---|---|
| 모델 | **`qwen3:8b`** (Q4_K_M) | Ollama 라이브러리 기준 다운로드 **5.2GB** |
| 구동 가능 여부 | **가능** | 모델 5.2GB + KV 캐시 약 3.4GB(24K 토큰) + 여유 ≈ 10GB 이하 → 12GB 안에 들어감 |
| 설치 | **이미 설치됨** — 봇 첫 실행 시 `ollama ps` 로 100% GPU 인지만 확인 | |
| num_ctx | **24576** (시작값) | 아래 3.3 참고 |
| thinking | 끔 (`think: false`) | 답변 지연 감소 |
| temperature | 0.2 | 문서 그대로 답하도록 |

- `ollama ps` 에 CPU 비율이 보이면 num_ctx를 줄인다.
- KV 캐시 양자화(`OLLAMA_KV_CACHE_TYPE=q8_0`)는 8b에서는 **필수 아님**. VRAM이 부족할 때만 쓴다.
- 디스크(DRAM리스 + HMB): 영향 없음으로 본다. 디스크를 많이 쓰는 건 모델 적재(5.2GB 순차 읽기) 한 번뿐이고, 적재 후에는 VRAM에서 돈다 (`keep_alive 30m`). 로그는 질문당 몇 KB 추가라 무시할 수준. HMB는 시스템 RAM 일부(보통 수십 MB)를 SSD 매핑 캐시로 빌려 쓰는 기능이라 RAM 48GB에도 영향이 없다.

### 3.3 num_ctx 24576 이란?

- **글자 수가 아니라 토큰 수**다. 모델이 한 번에 보는 입력+출력의 최대 길이.
- 한글은 대략 1글자 ≈ 0.7~1토큰 수준이라, 문서 15,782자는 **약 1만~1.6만 토큰으로 추정**한다 (정확한 값은 첫 실행 때 측정).
- **qwen3:8b에도 유효한 값이다.**
  - Qwen3-8B의 기본 컨텍스트는 32,768 토큰(설정상 최대 위치 40,960) → 24,576은 그 안이다.
  - VRAM 계산: Qwen3-8B는 36층 × KV 헤드 8 × 헤드 크기 128 → 토큰당 KV 캐시 약 144KB(fp16) → 24,576토큰 ≈ 3.4GB. 모델 5.2GB와 합쳐도 12GB 안이다.
- 배분: 문서(약 1만~1.6만) + 규칙·질문(수백) + 답변(최대 약 1천) → 24,576이면 여유가 있다.
- **주의**: Ollama는 num_ctx를 넘으면 **프롬프트 앞부분(=문서 앞쪽)을 조용히 잘라낸다.**
  → 봇 시작 시 "워밍업 호출"로 실제 토큰 수(`prompt_eval_count`)를 측정해 출력하고, num_ctx의 90%를 넘으면 경고한다. 질문마다 같은 검사를 해서 로그에 남긴다. 보조툴로 문서가 길어질수록 중요하다.

### 3.4 거절 규칙 (문서 밖 질문)

system 프롬프트 규칙:
1. 문서에 근거가 없거나 문서만으로 판단할 수 없으면 추측하지 말고 정확히 **"문서에 없는 내용입니다."** 한 문장만 답한다.
2. 일반 상식·외부 지식으로 보충하지 않는다.
3. 간결하게, 절차는 번호 목록.
4. 마지막 줄에 `(근거: 문서의 항목/제목)`.
5. 1000자 이내.
6. 여러 작업을 함께 묻는 질문은 **작업별로 나눠** 답하고, 문서에 있는 **선후관계·주의사항**을 먼저 말한다.

봇은 답변에 거절 문구가 들어 있으면 **미답변**으로 분류해 `unanswered.jsonl`에 따로 기록한다 → 보조툴의 입력이 된다.

### 3.5 ntfy 사용 방식

- 발행은 **JSON 본문**으로 서버 루트에 POST (헤더 방식은 한글 제목이 깨짐 — 코인자동매매 프로젝트에서 확인한 사항).
- 메시지 한도 4,096바이트(한글 약 1,300자, 넘으면 첨부파일로 바뀜) → 넘으면 `(1/2)`, `(2/2)`로 나눠 보내고 버튼은 마지막 조각에만.
- 피드백 버튼은 ntfy **http 액션**: 누르면 피드백 토픽으로 `good <질문ID>` / `bad <질문ID>` 를 POST.
- 봇이 꺼져 있던 동안 온 질문도 처리: 마지막 처리한 메시지 ID를 `state.json`에 저장하고 재연결 시 `since=<ID>`로 이어 받는다 (ntfy.sh 보관 12시간).
- 연결이 끊기면 5초부터 최대 5분까지 늘려 가며 재연결.
- **토픽 이름 = 비밀번호**: ntfy.sh 공개 토픽은 이름을 아는 사람이면 읽고 쓸 수 있으므로, 추측 불가능한 긴 무작위 이름을 쓴다 (첫 실행 시 자동 생성).

### 3.6 휴대폰 사용 — ntfy 앱 (1차)

봇은 **하나만** 만들면 된다. 봇은 ntfy 토픽만 다루고, 휴대폰 종류는 ntfy 앱이 처리한다.

| 기능 | Android | iPhone | 확인 근거 |
|---|---|---|---|
| 답변 알림 수신 | ntfy 앱 | ntfy 앱 | 공식 앱 둘 다 있음 |
| 👍/👎 버튼 (http 액션) | ✓ | ✓ | ntfy 문서 "Action buttons — Supported on: Android, Apple, Firefox" (Android 전용은 broadcast 액션뿐) |
| 질문 보내기 | ntfy 앱 토픽 화면 하단 입력창 | **ntfy 웹앱** (`https://ntfy.sh/app`, Safari "홈 화면에 추가") | iOS 앱 발행 기능은 문서에서 확인 못 함 → 웹앱 사용 (iOS 16.4 이상) |

### 3.7 전용 앱 하나로 Android·iPhone 모두 — 있음 → 제작 고려

**하나의 코드로 Android와 iPhone 앱을 함께 만드는 방법이 있다.** 1차는 ntfy 앱으로 운영하고, 전용 채팅 앱은 **제작을 고려**한다 (별도 계획서로 진행).

| 방식 | 하나로 둘 다 | iPhone 빌드·설치 조건 | 비고 |
|---|---|---|---|
| **PWA (웹앱을 홈 화면에 설치)** | ✓ | Mac 불필요, 앱스토어 불필요. iOS 16.4 이상에서 웹 푸시 알림 가능 | HTTPS 주소에 올려야 함. 가장 부담이 적음 |
| **Flutter** | ✓ (Dart 한 코드) | **Mac + Xcode 필요** | 네이티브 앱 |
| **React Native** | ✓ (JavaScript/TypeScript) | **Mac + Xcode 필요** | 네이티브 앱 |
| **Kotlin Multiplatform (Compose)** | ✓ (Kotlin) | **Mac + Xcode 필요** | clipSend 처럼 Kotlin 경험 활용 가능 |

- 네이티브 앱을 iPhone에 설치하려면 Apple 개발자 계정이 필요하다. 무료 계정으로 직접 설치한 앱은 **7일마다 다시 설치**해야 하고, 계속 쓰려면 Apple Developer Program(연 $99)이 필요하다.
- 전용 앱도 서버는 지금과 같이 **ntfy.sh 토픽**을 그대로 쓰면 봇(bot.py)을 바꿀 필요가 없다.
- 결론: 제작한다면 **PWA를 1순위**로 검토 (Mac·개발자 계정 없이 두 기종 모두 지원). 다만 다른 주소의 웹앱에서 ntfy.sh를 직접 호출할 수 있는지(CORS)와 iPhone 백그라운드 알림 방식은 제작 계획 단계에서 확인한다.

## 4. 설정 — 코인자동매매의 ntfy 설정을 참고

코인자동매매 프로젝트(`../코인자동매매`)에서 ntfy를 이미 운영했으므로 **같은 구조·규칙을 그대로 따른다.**

| 코인자동매매 | 이 프로젝트 | 비고 |
|---|---|---|
| `NTFY_SERVER = "https://ntfy.sh"` (config/settings.py) | `ntfy_server` | 동일 |
| `NTFY_TOPIC` (.env, git 제외) | 답변 토픽 | 폰이 구독하는 토픽 |
| `NTFY_APPROVAL_TOPIC` (폰 버튼 → 루프) | 피드백 토픽 | 같은 원리: 알림 버튼이 별도 토픽으로 발행 |
| — | 질문 토픽 | 새로 추가 |
| `NTFY_TOKEN` (보호 토픽만, 공개 토픽이면 비움) | `ntfy_token` | ntfy.sh 공개 토픽이므로 비워 둠 |
| JSON 본문 발행, 실패 시 예외 없이 로그만 | 동일 | |
| 비밀값(토픽·토큰)은 git 제외 | 동일 | 토픽이 곧 비밀번호 |

## 5. 구현 계획

### 5.1 기술 선택

- **Python 표준 라이브러리만** (`urllib`, `json`) → Python 설치 후 pip 추가 설치 불필요.
- 실행: `run.bat` (`chcp 65001` + `py bot.py`). Windows `python3`/`python` 명령은 스토어 스텁일 수 있어 **`py` 런처**를 쓴다.

### 5.2 폴더 구성 — `D:\업무프로세스`

```
D:\업무프로세스\
├── 업무프로세스.md         # 문서 (원본, 모든 질문에 기본 첨부)
├── 백업\                   # 보조툴이 문서를 고치기 전 자동 백업 (다음 단계)
├── logs\
│   ├── qa.jsonl            # 질문마다: ID·시각·질문·답변·미답변 여부·토큰 수
│   ├── unanswered.jsonl    # 미답변 질문마다: ID·시각·질문
│   ├── feedback.jsonl      # 버튼 클릭마다: 질문ID·시각·평가(good/bad)·질문·답변
│   └── errors.jsonl        # LLM 호출 실패
├── tests\
│   ├── 테스트케이스.txt    # 7절 질문 목록
│   └── 결과_YYYYMMDD.csv   # 일괄 테스트 결과 (판정 칸 포함)
├── state.json              # 마지막 처리 메시지 ID
├── .env                    # 토픽·토큰 (비밀값)
└── bot\                    # 프로그램 (bot.py, run_tests.py, run.bat, README.md)
```

- 저장소(`.claude/기타/개인프로젝트/업무프로세스-ntfy-챗봇/`)에는 **프로그램과 계획서만** 올린다. 문서·로그·.env 는 D: 에만 둔다.
- 로그는 모두 **질문 ID로 연결**된다 → 보조툴이 미답변·피드백·원래 답변을 한 번에 모아 볼 수 있다.

### 5.3 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | **Python 설치**: python.org 설치 파일 또는 `winget install Python.Python.3.12` (3.12 이상). 설치 시 "Add python.exe to PATH"와 **py launcher** 선택 | `py --version` 출력 |
| 2 | bot.py 작성 (설정·워밍업·구독·답변·피드백·로그) | 모의 ntfy/Ollama 서버로 로컬 테스트 통과 |
| 3 | `D:\업무프로세스` 구성, 첫 실행 → 토픽 생성 | 워밍업 로그에 토큰 수 출력, 90% 경고 없음, `ollama ps` 100% GPU |
| 4 | 휴대폰에 답변 토픽 구독, 질문 토픽으로 발행 (Android 앱 / iPhone 웹앱) | 질문 → 답변 알림 수신 |

## 6. 검증 기준

1. **자연어 테스트케이스 60개** (7절, 문서 안 50 + 문서 밖 10)
   - 문서 안 50개: 사람이 판정해 **90% 이상 "맞음"**. 맞음 = 문서 내용과 일치 + `(근거: …)` 표시 + 복합 질문은 작업을 빠짐없이 다루고 순서가 문서와 같음.
   - 문서 밖 10개: **100% "문서에 없는 내용입니다."** + `unanswered.jsonl`에 기록.
   - 판정이 "틀림"인 항목은 원인을 **문서 부족 / 모델 오해 / 프롬프트 문제** 중 하나로 표시.
2. 👍/👎 버튼 → **질문마다** `feedback.jsonl`에 질문ID·시각·평가·질문·답변이 기록된다 (Android·iPhone 구분 없이 같은 형식).
3. 1,300자 넘는 답변 → 나눠서 순서대로 도착.
4. 봇 종료 중 보낸 질문 → 재시작 후 답변 도착.
5. 응답 시간: 첫 질문(모델 적재 포함)과 이후 질문 각각 측정해 기록. 목표는 이후 질문 30초 이내.

## 8. 다음 단계 — 보조툴 (계획 있음)

봇 1차 완성 후 **별도 계획서**로 진행한다. 지금 단계에서는 보조툴이 바로 쓸 수 있게 **로그를 질문마다, 질문 ID로 연결해** 남기는 것까지 한다.

### 8.1 미답변 보강 툴 (`unanswered.jsonl` 활용)

1. `unanswered.jsonl`에서 아직 처리 안 한 질문을 읽는다.
2. 각 질문이 **업무프로세스와 관련된 내용인지** 분류한다 (관련 / 무관). 무관(F 유형)은 건너뛴다.
3. 관련 질문은 문서 어디에 어떤 내용을 추가하면 되는지 **보강 초안**을 만든다.
4. **사용자가 확인·수정한 것만** 문서에 반영한다 (LLM이 쓴 내용을 자동으로 문서에 넣지 않는다 — 문서가 유일한 근거이므로). 반영 전 `D:\업무프로세스\백업\`에 원본을 복사한다.
5. 처리한 질문은 처리 목록에 기록해 다시 나오지 않게 한다.

### 8.2 피드백 분석 툴 (`feedback.jsonl` 활용)

1. 질문마다 기록된 👍/👎 를 질문ID로 `qa.jsonl`과 묶어 본다.
2. 👎 답변은 원인을 **문서 부족 / 모델 오해 / 프롬프트 문제**로 나눠 목록화 → 문서 부족은 8.1 흐름으로 보강, 나머지는 프롬프트 수정 후보.
3. 👍 받은 질문·답변은 7절 테스트케이스에 추가해 **회귀 테스트 세트**로 쓴다.
