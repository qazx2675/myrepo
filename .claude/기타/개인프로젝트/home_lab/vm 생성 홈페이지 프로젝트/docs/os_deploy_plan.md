# OS 자동 배포 기능 — 추가 계획서 (M10~M13)

> 현재 상태: 계획 단계. Phase 1~9 + 파이프라인은 실측 완료된 상태이고, 이 문서는 그 위에 얹을 신규 기능(OS 표준별 자동 배포)의 설계·마일스톤·리소스 검토를 다룬다.
> 이 기능은 완성 전까지 대시보드에서 **별도 "Beta" 배너/섹션**으로 노출하고, 기존 Phase 1~9와는 분리해 운영한다. 안정화되면 **Phase 4(MAC/IP 추출)를 이 기능으로 대체**할 예정.

---

## 1. 목표

사용자가 OS 종류 + 버전을 선택하면, **그 OS가 이미 설치되어 부팅되는 VM**을 자동으로 만들어준다.
지금의 Phase 3(빈 VM 생성) + Phase 4(MAC/IP 추출 후 수동 Kickstart 설치)를 하나의 "선택 → 즉시 부팅 가능한 VM" 흐름으로 합치는 것이 최종 목표.

요구사항 재확인 (이번 대화에서 확정된 것):
- 배포된 OS는 **부팅만 되면 됨** — 로그인 계정, 네트워크 커스터마이징 등은 지금 스코프 밖.
- 지금은 **테스트 목적**이라 동시에 몇 대 켜두는 정도(대규모 운영 아님).
- vCenter/ESXi/Rocky 포털이 전부 **한 컴퓨터(i5-9400F, 32GB) 안에서 VMware Workstation의 중첩(nested) VM**으로 돌아가는 구조.

---

## 2. 구현 방식 두 가지

### 방식 A — 골든 이미지 Full/Linked Clone (1차 MVP, 권장)

OS별로 미리 설치·정리해 둔 "골든 템플릿" VM을 vCenter에 Template으로 등록해두고, 배포 요청이 오면 govmomi의 `VirtualMachine.Clone(ctx, folder, name, CloneSpec)`으로 그 템플릿을 복제한다. 지금까지 만든 스크립트들과 동일하게 "기존 govmomi API를 exec 바이너리로 감싸는" 패턴을 그대로 따를 수 있다.

- **장점**: 배포가 수 초~수십 초 내 끝남(설치 과정 자체가 없음). 구현이 단순하고 기존 아키텍처(exec.Command 래핑)에 자연스럽게 들어맞음. 별도 네트워크 인프라(DHCP/PXE)가 필요 없음.
- **단점**: OS/버전별로 템플릿을 미리 준비해야 함(초기 구축 비용). 파티션 구조가 템플릿에 고정됨(설치 시점 커스터마이징 불가 — 필요하면 클론 후 스크립트로 후처리).
- "부팅만 되면 된다"는 지금 요구사항에 정확히 맞는 방식.

### 방식 B — PXE + Kickstart/Autoinstall (확장 옵션, 나중에)

포털이 격리된 vSwitch 안에서 DHCP + PXE(TFTP/HTTP) 서버를 띄우고, OS별 무인 설치 스크립트(Kickstart, cloud-init autoinstall, Windows면 unattend.xml)를 자동 생성해 배포한다. VM은 빈 디스크로 생성되고, 네트워크 부팅 후 사용자가 지정한 파티션·호스트명 등으로 실제 OS 설치가 진행된다.

- **장점**: 설치 시점에 파티션/네트워크를 사용자가 원하는 대로 커스터마이징 가능. 템플릿을 미리 만들어둘 필요가 없음(설치 스크립트만 관리).
- **단점**: 설치에 수 분~수십 분 소요. **DHCP 서버를 새로 띄우는 것 자체가 리스크** — 지금 환경은 가정용 공유 네트워크(192.168.0.0/24)에 물려 있어서, 스코프를 격리하지 않으면 다른 기기(가족 PC, 공유기)의 IP 할당과 충돌할 수 있음. 반드시 Phase 2에서 만드는 전용 vSwitch/포트그룹 안에서만 DHCP가 응답하도록 물리적으로 격리해야 함. 구현 복잡도도 훨씬 높음(TFTP/HTTP 부트 서버, iPXE 메뉴, OS별 시드파일 관리 전부 신규 개발).

### 권장

**1차는 방식 A로 MVP를 구현**하고, 안정화된 뒤 필요하면 방식 B를 "고급 배포(커스텀 파티션)" 옵션으로 얹는다. 지금 요구사항("부팅만 되면 됨")에는 A만으로 충분하고, B는 네트워크 격리 설계까지 별도로 검증해야 해서 리스크 대비 이득이 낮다.

## 3. 하드웨어 스펙 평가

**전제**: Windows 호스트 + VMware Workstation + Rocky 포털 + VCSA(vCenter) + nested ESXi가 전부 이 컴퓨터 한 대(i5-9400F, 32GB RAM, 여유 디스크 181GB, D: 재포맷 후 +230GB) 안에 3중으로 중첩되어 있고, 그 nested ESXi 위에 다시 골든 템플릿과 배포된 테스트 VM들이 올라가는 구조.

### RAM — 가장 타이트한 자원

| 구성 요소 | 예상 RAM |
|---|---|
| Windows 11 호스트 자체 | 4~8GB |
| VCSA (vCenter, Tiny 최소 규격) | 공식 최소 12GB (축소 구성이면 더 적을 수 있음) |
| nested ESXi (오버헤드) | 최소 4GB, 게스트 여러 대 올리려면 8GB+ |
| Rocky 포털 VM | 2~4GB |
| **인프라 합계** | **약 22~24GB** |
| **32GB 중 남는 여유** | **약 8~10GB** |

이 8~10GB로 "부팅만 하면 되는" 최소 Linux 게스트(512MB~1GB)라면 이론상 6~10대까지 가능하지만, 동시에 여러 대를 켜면 nested ESXi의 CPU 스케줄링 오버헤드까지 겹쳐 체감 성능은 더 떨어진다. **"1~2대씩 켰다 끄는" 테스트 용도로는 충분하지만, 5대 이상 상시 동시 구동은 권장하지 않는다.**

> ⚠️ 위 수치는 공식 최소 권장값 기준 추정이다. 실제로 VCSA/nested ESXi에 얼마를 할당해뒀는지는 사용자마다 다르므로, **작업 착수 전(M10) vSphere Client 리소스 화면 또는 nested ESXi의 `esxtop`으로 실제 할당량을 먼저 확인**하는 것을 첫 단계로 넣어둔다.

### CPU

i5-9400F는 6코어 6스레드(하이퍼스레딩 없음)이고, 이미 Windows+VCSA+ESXi+포털이 상시로 코어를 나눠 쓰는 중이다. "부팅만 되면 된다" 수준의 가벼운 idle 게스트라면 CPU는 크게 문제되지 않는다. 클론 자체도 vCenter API 호출 한 번으로 끝나는 디스크 복사 작업이라 CPU 부담이 적다. 다만 여러 대를 동시에 클론+부팅하면 순간적으로 6코어가 포화될 수 있으므로, **배포 요청은 순차 실행**(지금 포털의 동기 실행 모델과 자연스럽게 맞음)으로 제한할 것을 권장한다.

### 디스크

- 현재 여유 181GB (D: 재포맷 후 +230GB = 최대 411GB)
- 씬 프로비저닝 기준, Rocky/Ubuntu 등 최소 설치 Linux 템플릿은 실사용 8~15GB 수준 → 템플릿 4~5종이면 약 50~75GB.
- Windows 계열까지 포함하면 템플릿당 20~40GB(씬 기준)로 뛰므로, 지금 181GB 안에서는 **Linux 위주 3~4종 + Windows 1종 정도가 안전선**.
- 방식 A 채택 시 **Linked Clone**을 쓰면 배포된 VM이 템플릿과의 델타만 저장하므로 Full Clone보다 디스크 사용량을 크게 줄일 수 있다(다만 템플릿을 지우거나 옮기면 하위 클론들이 깨지므로 템플릿 보존 정책이 필요).

### 결론

**"테스트만, 부팅만 되면 됨" + "동시 2~3대"라는 실제 요구 수준에서는 지금 스펙(32GB/181GB)으로 충분하다.** 단, RAM 여유가 실제로 8~10GB가 맞는지는 사전 실측이 필요하고(M10), 디스크는 Linux 템플릿 위주로 가면 지금도 넉넉하지만 Windows 템플릿을 여러 개 늘리고 싶다면 D: 230GB 확보 후 진행하는 게 안전하다. 가장 유력한 병목은 CPU나 디스크가 아니라 **RAM**이므로, 포털 쪽에 "동시 구동 대수 제한" 안전장치(M13)를 넣는 것을 필수로 권장한다.

## 4. 마일스톤

### M10 — 골든 이미지 준비 및 현재 리소스 실측
- vSphere Client 또는 nested ESXi의 `esxtop`으로 VCSA·ESXi에 실제 할당된 RAM/CPU 확인
- OS별 최소 설치 VM을 1대씩 수동으로 준비(Rocky, Ubuntu 우선) → vCenter에서 Template으로 변환
- 템플릿 명명 규칙 정의 (예: `tpl-rocky9-minimal`, `tpl-ubuntu2204-minimal`)

### M11 — Clone 기반 배포 바이너리 개발
- 기존 스크립트들과 동일한 패턴(govmomi 직접 사용)으로 `os_deploy` 신규 Go 바이너리 작성
- `-templateName -vmName -datastore -cloneType(full|linked)` 플래그로 govmomi `Clone()` 호출
- 클론 완료 후 자동 전원 On까지 수행("켜지기만 하면 된다" 요구 반영)

### M12 — 포털 통합 (Beta 배너로 분리)
- 대시보드에 "Beta" 전용 섹션/배너로 새 메뉴 노출 — 기존 Phase 1~9와 시각적으로 분리
- RBAC은 처음엔 Admin 전용(Lv.5)으로 시작해, 안정화되면 낮추는 것을 검토
- vCenter에서 사용 가능한 템플릿 목록을 실시간 조회해 드롭다운으로 제공 (OS/버전 선택 UX)
- Phase 3/4와는 당분간 병행 운영, 안정화 후 Phase 4를 이 기능으로 교체 예정임을 UI에 명시

### M13 — 안전장치 및 정리 정책
- 동시 배포/실행 대수 제한 (리소스 보호 — RAM이 병목이므로 필수)
- 오래된/미사용 배포 VM 정리 (Dry-run으로 먼저 대상 확인 후 삭제, 기존 Phase 8 `vm_delete` 재사용)
- 템플릿·배포 VM 디스크 사용량 모니터링 (Phase 9 리포트 확장 고려)

## 5. 리스크

| 리스크 | 완화 방안 |
|---|---|
| RAM 부족으로 동시 구동 실패 | M13 동시 대수 제한, 배포 전 여유 RAM 체크 |
| (방식 B 채택 시) DHCP 충돌로 홈 네트워크 장애 | 반드시 격리 vSwitch 사용, 1차는 방식 A로 회피 |
| 템플릿 노후화(보안 패치 누락) | 정기적 템플릿 재구축 필요 — 이번 스코프에서는 수동, 자동화는 향후 검토 |
| Linked Clone 사용 시 템플릿 삭제/이동으로 하위 클론 손상 | 템플릿 보존 정책 문서화, 삭제 전 하위 클론 존재 여부 확인 로직 추가 |
