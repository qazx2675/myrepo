# VM PCI 패스스루 통합 (활성화 + VM 연결 + 정상 부팅) 계획서

작성 2026-10-28. 작업 브랜치 `passthrough` (워크트리 `C:\AndroidStudioProjects\clipSend-passthrough`, origin/master 기준).

## 1. 배경

- 예전 방식은 두 개로 나뉘어 있었다: 패스스루 활성화(Go, `.claude/VM/passthrough/enable-go`)와 VM 연결(PowerShell, `.claude/VM/passthrough/attach_pci.ps1`).
- 둘을 한 스크립트로 묶으면 VM 전원이 켜지지 않았고, PCI 를 빼면 켜졌다.
- 원인 후보 두 가지:
  - ① 패스스루를 켠 직후, 아직 활성(Active)이 아닌 장치를 바로 연결했다. 이 경우 호스트를 재부팅해야 활성이 된다.
  - ② SDK 로 직접 붙이면서 backing `SystemId` 에 `host.Hardware.SystemInfo.Uuid` 를 넣었다. 실제로는 ESXi 의 system uuid(`esxcli system uuid get`)여야 한다.
- **2026-10-28 사용자 확인: 실제 원인은 ②.** ESXi 의 UUID 와 vCenter 에서 PCI 를 추가할 때 들어간 UUID 가 달라서 부팅이 안 됐다. ESXi UUID 기준으로 등록하니 정상 부팅됐다. 따라서 backing `SystemId` 는 반드시 ESXi 의 system uuid 여야 한다(`esxcli system uuid get` 값 = QueryConfigTarget 이 돌려주는 SystemId). `host.hardware.systemInfo.uuid`(하드웨어/BIOS UUID)를 쓰면 안 된다.
- PowerCLI `Add-PassthroughDevice` 는 `EnvironmentBrowser.QueryConfigTarget(host).PciPassthrough[]` 에서 올바른 `SystemId` 와 장치 정보를 받는다. 그래서 PowerShell 연결본은 전원이 켜졌다.

## 2. 결정 사항 (인터뷰)

| # | 항목 | 결정 |
|---|---|---|
| D1 | 설정 위치 | SPEC 스펙 파일에 `pci-evNN=<vendor>`. 예: `pci-ev01=mellanox` |
| D2 | vendor 값 | `mellanox`, `nvidia`, VendorId(10진 `5555` 또는 16진 `15b3`/`0x15b3`). 그 밖의 값은 장치명(DeviceName)의 부분 문자열로 찾는다(대소문자 무시). 체크 쪽 VM backing 에는 장치명만 있어서, 도구와 체크가 같은 규칙을 쓰도록 이렇게 맞췄다(`checker/pci.go` 의 `MatchPCIVendor` 와 도구의 복사본은 늘 같아야 한다). Intel 은 `0x8086` 으로 적는다. `8086` 은 10진으로 해석된다 |
| D3 | 장치 배분 | ev 마다 **PCI 장치(function) 1개**씩, PCI 주소 순서대로 배분한다(ev01 이 첫 장치). 카드 단위(같은 슬롯의 function 전부)가 필요해질 때를 위해 문서에 기록한다 |
| D4 | 전원 | VM 이 켜져 있으면 끄고 작업한다. 연결한 뒤 전원 ON 으로 정상 부팅을 확인하고 **켜 둔 채로** 둔다 |
| D5 | 재부팅이 필요한 장치 | ESXi 8.0.3 에서도 '재부팅 후 활성'이면 그 BM 은 활성화까지만 하고 "호스트 재부팅 필요"로 보고한다. 재부팅 뒤 같은 명령을 다시 돌리면 **이어서**(이미 된 것은 건너뛰고) 연결과 전원 ON 까지 진행한다 |
| D6 | 언어 | Go 하나. `VMsetup/pci_passthrough-source/main.go` + `setup.sh`(govendor 오프라인 빌드). PowerShell 은 더 쓰지 않는다 |
| D7 | 스펙 체크 | vm-param-check 에 "PCI 패스스루" 체크를 추가한다. pci-evNN 이 있는 VM 에 그 벤더의 패스스루 장치가 붙어 있는지 본다. **V2 복사본만** 고친다 |
| D8 | vm_setup 단계 | 스펙마다 lpage 다음에 "PCI 패스스루" 단계를 넣는다. 스펙에 pci-* 가 없으면 건너뛴다 |
| D9 | 커밋·푸시 | 다음 순서로 올린다: `passthrough` 브랜치 → master(`.claude/VM/V2`) → V2 브랜치. V2 브랜치는 V2 폴더 내용만 담고 테스트 파일은 뺀다(기존 subtree 방식) |
| D10 | 바이너리 | `bin_os6/` 에 pci_passthrough 와 vm-param-check 를 다시 빌드해 넣는다(.60, Go 1.20). `bin_os8/` 를 새로 만들어 **이번에 바뀐 것만**(pci_passthrough, vm-param-check) 넣는다. 용량 때문에 전체는 넣지 않는다. 바뀐 항목만 적용하는 가이드를 함께 둔다 |
| D11 | 검증 | 랩 vCenter 가 꺼져 있어서 vcsim 기반으로 끝까지 진행한다. 꺼진 이유: Windows VBS(`EnableVirtualizationBasedSecurity=1`) 때문에 Workstation 이 ULM 으로 돌아 중첩 VT-x 가 없다. 실 vCenter 시험은 **보류 목록**으로 남기고, 사용자가 요청하면 그때 한다 |
| D12 | 실행 방식 | `/jev-plan-router` 로 단계를 실행한다. "VM 에 PCI 를 연결했을 때 정상 부팅되게 만드는 단계"(S3)는 **Opus 5.5 고정**이다 |

## 3. 안전장치

- 호스트 관리망 등 vmnic 으로 쓰이는 물리 NIC(`host.config.network.pnic[].pci`)는 패스스루로 켜지 않는다. 켜면 호스트 네트워크가 끊긴다.
- 활성화는 이번에 배분할 장치에만 한다. 같은 벤더라도 남는 장치는 건드리지 않는다.
- 다른 VM 에 이미 연결된 장치는 배분 대상에서 뺀다.
- 실패는 VM·BM 단위로 기록하고 나머지는 계속 진행한다. 실패가 하나라도 있으면 종료코드는 1 이다. vm_setup 은 다른 도구와 같은 규칙으로 처리한다.

## 4. 단계 (jev-plan-router 실행 단위)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| S1 | 검증 하네스 `pcisim` 을 만든다. govmomi simulator 확장으로, ① 호스트 `hardware.pciDevice` ② `HostPciPassthruSystem`(UpdatePassthruConfig, 재부팅 필요 장치 흉내) ③ `QueryConfigTarget.PciPassthrough` ④ PowerOn 실패 흉내(SystemId 불일치, 비활성 장치, 메모리 예약 부족)를 넣는다 | .58 에서 vcsim 처럼 띄워 govc 로 장치가 보인다 |
| S2 | `pci_passthrough` Go 도구를 만든다: worklist(BM) + `-pciEvNN=<vendor>` → 장치 배분 → 활성화 → 활성 확인 → VM 끄기 → 연결 → 전원 ON | pcisim 에서 정상·재부팅필요·재실행이어하기·이미연결 시나리오가 통과한다 |
| S3 | **(Opus 5.5 고정)** 정상 부팅 보장: QueryConfigTarget 기반 backing(SystemId/DeviceId/VendorId), 메모리 100% 예약 확인, NVIDIA 등 큰 BAR 장치의 64bit MMIO, 전원 ON 결과·실패 원인 보고 | pcisim 의 PowerOn 검증 규칙을 통과하고, 일부러 틀린 경우 원인 메시지가 나온다 |
| S4 | vm-param-check 를 바꾼다: 스펙 파서·export 에 `pci-evNN`, 체크 항목 "PCI 패스스루" | `go test ./...` 와 specExport 출력, pcisim 체크 PASS/FAIL 이 확인된다 |
| S5 | vm_setup.sh 를 연동한다: build_flags → PCI_ARGS, step_pci(lpage 다음), 실행 계획 표시, ensure_bin. V2 `setup.sh`/`build_os6.sh` 에 도구를 추가한다 | pcisim 대상 vm_setup 실행(파이프 입력)에서 PCI 단계와 체크가 통과한다 |
| S6 | 바이너리와 문서: bin_os6(.60)·bin_os8(.58) 빌드, 바뀐 항목 적용 가이드, README/CHANGELOG/스펙 예시/workflow.mmd, 작업기록(보류 목록 포함) | 빌드 산출물이 실행되고 문서가 갱신된다 |
| S7 | 커밋·푸시: passthrough → master → V2 브랜치(subtree split, 테스트 파일 제외, 빌드 확인) | origin 에서 세 브랜치를 확인한다 |

## 5. 보류(실 vCenter/실장비 확인 필요)

- ESXi 8.0.3 실장비에서 Mellanox 활성화 직후 `PassthruActive` 가 바로 true 가 되는지(재부팅 필요 여부)
- 실 vCenter 에서 연결 후 전원 ON 성공, 게스트 안에서 장치 인식
- NVIDIA(GPU) 64bit MMIO 크기 적정값
- vCenter 8.0.3 이 붙어 있는 패스스루 장치의 backing 편집(SystemId 교정)을 받아주는지, 아니면 늘 "제거 후 다시 연결" 대체 경로로 가는지(대체 경로는 게스트가 보는 PCI 슬롯이 바뀔 수 있음)
- 실 호스트에서 QueryConfigTarget 의 SystemId 가 `esxcli system uuid get` 값과 같은지
- BIOS VM 에 64bit MMIO 를 켰을 때 실제 동작, MMIO 창이 작을 때의 실제 거부 메시지, 실 GPU 에 맞는 MMIO 크기(현재는 VRAM 16GB 이하 가정, 1~2장은 64GB)
- 실 ESXi 의 QueryConfigTarget 이 활성 장치만 돌려주는지, Mellanox SR-IOV(VF) 항목이 어떻게 보이는지
- 큰 VM 의 메모리 100% 예약이 호스트 예약 가능 메모리 부족으로 실패하지 않는지
- 랩 재개 조건: Windows VBS 를 끄고 Workstation ESXi VM 의 `vhv.enable=TRUE` 로 vCenter 를 켠다
