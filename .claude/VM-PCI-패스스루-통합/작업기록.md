# VM PCI 패스스루 통합 — 작업기록

작성 2026-10-28. 계획은 [계획서.md](계획서.md)(결정 D1~D12, 안전장치, 보류 목록). 작업 브랜치 `passthrough`.

## 1. 결과 요약

- 패스스루 활성화(Go)와 VM 연결(PowerShell)로 나뉘어 있던 것을 Go 도구 하나 **`V2/VMsetup/pci_passthrough-source`** 로 합쳤다. 순서: 장치 배분 → 활성화 → VM 연결 → 전원 ON, VM 은 켜 둔다.
- `vm_setup.sh` 가 스펙의 `pci-evNN=<벤더>` 를 읽어 lpage 다음 단계에서 이 도구를 실행한다. vm-param-check(V2 복사본)는 "PCI 패스스루" 체크를 한다.
- OS6 실행파일 `bin_os6/` 는 바뀐 2개만 다시 빌드했다. `bin_os8/`(신규)에는 바뀐 2개만 넣었다. 기존 설치 서버에 변경분만 반영하는 방법은 `V2/UPDATE_PCI_PASSTHROUGH.md` 에 있다.
- 검증은 PCI 패스스루를 흉내 낸 vcsim(pcisim)으로 했고, 2026-10-29 랩 ESXi 8.0.3 에 직접 붙여 핵심 흐름(활성화·SystemId·교정·업링크 거부)을 확인했다(§4 실 ESXi 시험). 이때 vm-param-check 의 장치 이름 판정 버그를 찾아 고쳤다. 남은 실장비 항목은 **보류 목록**에 있다.

## 2. 확인된 원인 (2026-10-28 사용자 확인)

예전에 활성화와 연결을 한 스크립트로 묶었을 때 VM 전원이 켜지지 않았다. 원인은 **backing `SystemId` 에 `host.hardware.systemInfo.uuid`(하드웨어/BIOS UUID)를 넣은 것**이었다. `SystemId` 에는 ESXi 의 system uuid(`esxcli system uuid get`)가 들어가야 한다. ESXi UUID 로 다시 등록하니 정상 부팅됐다.

그래서 새 도구는 backing 값(`Id`/`SystemId`/`VendorId`/`DeviceId`/`DeviceName`)을 모두 `EnvironmentBrowser.QueryConfigTarget(host).PciPassthrough[]` 에서 받는다. PowerCLI `Add-PassthroughDevice` 도 같은 곳에서 값을 받는다. 하드웨어 UUID 는 어디에도 쓰지 않는다. 이미 붙어 있는 장치의 SystemId·VendorId·DeviceId 가 틀렸으면 교정한다. vCenter API 로 처리하므로 SSH 와 `esxcli` 는 필요 없다.

### 실 ESXi 8.0.3 시험 (2026-10-29, 랩 192.168.0.59)

- **경로**: 랩 vCenter(192.168.0.50)의 평가판 라이선스가 만료돼 호스트 재연결이 `License not available to perform the operation` 으로 실패했다. 그래서 도구를 **ESXi 에 직접**(`-vcTargetIP=192.168.0.59 -id=root`) 붙여 시험했다. 쓰는 API(UpdatePassthruConfig, QueryConfigTarget, ReconfigVM, PowerOnVM)는 vCenter 경유와 같다.
- **장치**: Workstation ESXi VM 에 `vvtd.enable=TRUE`(가상 IOMMU)와 host-only e1000e NIC(`ethernet1`)를 넣었다. 어느 vSwitch 에도 연결되지 않은 vmnic1 `0000:13:00.0`(Intel 82574L, `0x8086`)을 패스스루 대상으로, 업링크 vmnic0 `0000:0b:00.0`(vmxnet3)을 거부 시험용으로 썼다.
- **시험 VM**: ESXi 직접 접속에서는 호스트 이름이 `localhost.localdomain` 이라 worklist 에 그 이름을 쓰고, 1GB·EFI·디스크 없는 `localhostev01` 을 만들어 썼다(시험 뒤 삭제). 기존 192ev01/02 는 건드리지 않았다(호스트 여유 메모리 4.2GB).

## 5. 랩 상태

- (2026-10-29 갱신) VBS 는 사용자가 껐고 vCenter 는 켜진다. 다만 **랩 vCenter 평가판 라이선스가 만료**돼 ESXi 호스트를 vCenter 에 다시 붙일 수 없다(`License not available`). vCenter 경유 시험에는 라이선스 키가 필요하다. ESXi 평가판은 2026-12-27 까지.
- Workstation ESXi VM 설정에 `vvtd.enable=TRUE`, `ethernet1`(e1000e, host-only)을 넣어 두었다(원본 백업 `E:\VMs\VMware ESXi 8\VMware ESXi 8.vmx.before-pcitest-20261028`). 그대로 두면 다음 시험에 바로 쓸 수 있다.
- (예전 기록) 랩 vCenter 가 꺼져 있었다. 원인: Windows VBS(`EnableVirtualizationBasedSecurity=1`)가 켜져 있어 VMware Workstation 이 ULM(User Level Monitor, Hyper-V 위)으로 돈다. 그래서 중첩 VT-x 가 없고, 중첩 ESXi/vCenter 가 뜨지 않는다.
- Workstation 은 호스트 PC 의 PCI 장치(예: RTX 3060)를 VM 에 넘겨줄 수 없다. 그래서 집 랩에서는 vCenter 를 켜도 **실제 Mellanox/NVIDIA 장치로 패스스루를 시험할 수 없다**. 실장비 항목은 회사(ESXi 8.0.3)에서 확인해야 한다.
- 가능성(미확인): Workstation 의 "Virtualize IOMMU" 를 켜면 중첩 ESXi 가 가상 NIC(e1000, VendorId `0x8086`) 같은 가상 장치를 패스스루 가능으로 볼 수도 있다. 그러면 SystemId·backing Edit 수용·전원 ON 흐름을 집에서 일부 볼 수 있다. 이때 벤더 값은 `0x8086` 이나 장치 이름 일부를 쓴다. 관리망 vmnic 은 도구가 알아서 뺀다.

5. ~~실 호스트에서 QueryConfigTarget 의 SystemId 가 `esxcli system uuid get` 값과 같은지~~ — 같음 확인(2026-10-29, 랩 ESXi 8.0.3)
6. BIOS VM 에 64bit MMIO 를 켰을 때 실제 동작, MMIO 창이 작을 때 실제 거부 메시지, 실 GPU 에 맞는 MMIO 크기(현재는 VRAM 16GB 이하로 가정하고 1~2장은 64GB)
7. 실 ESXi 의 QueryConfigTarget 이 활성 장치만 돌려주는지, Mellanox SR-IOV(VF) 항목이 어떻게 보이는지
8. 큰 VM 의 메모리 100% 예약이 호스트의 예약 가능 메모리 부족으로 실패하지 않는지
9. 랩 재개 조건: ~~Windows VBS 를 끄고 vCenter 를 켠다~~(해결) → 랩 vCenter 평가판 만료. vCenter 경유 시험에는 라이선스 키가 필요하다

### 재개 절차

**0) 랩을 켤 때 (집 랩, 선택)**: 관리자 PowerShell 에서 VBS 를 끈다. 순서: 코어 격리 > 메모리 무결성 끔 → `reg add HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard /v EnableVirtualizationBasedSecurity /t REG_DWORD /d 0 /f` → `bcdedit /set hypervisorlaunchtype off` → 재부팅. 그다음 ESXi VM 의 `.vmx` 에 `vhv.enable = "TRUE"` 를 넣고 vCenter 를 켠다. 이 상태로는 위 5장의 한계(실 PCI 없음) 때문에 4·5번 정도만 볼 수 있다.

**1) 장치·UUID 확인 (회사 ESXi 8.0.3, 대상 BM 1대)** — 보류 5·7

```bash
# ESXi 셸
esxcli system uuid get                       # ESXi system uuid
esxcli hardware pci list | grep -i -B2 -A12 -e mellanox -e nvidia   # 주소·VendorId·패스스루 상태
```

**2) 도구 단독 실행 (BM 1대, ev01 하나만)** — 보류 1·2·5

```bash
cd /home/V2/VMsetup
export VC_PASSWORD="$(. ../secret_lib.sh; secret_get vcenter lscsystems@vsphere.local)"
echo <BM 이름> > pci_one.txt                 # vm_create 로 만든 <BM>ev01 VM 이 있어야 함
./pci_passthrough-source/pci_passthrough -vcTargetIP=<vCenter> -worklistFile=pci_one.txt -ev01Pci=mellanox; echo rc=$?
```

볼 것:
- 결과 줄 `연결 0000:xx:00.0 (SystemId=...)` 의 값이 1)의 `esxcli system uuid get` 과 같은지
- 종료코드. 3 이면 "활성화 직후 재부팅 필요"가 실장비에서도 맞다는 뜻이다(보류 1). 호스트를 재부팅한 뒤 같은 명령을 다시 실행해 이어지는지 본다
- 성공 뒤 VM 이 켜져 있는지, 게스트에서 `lspci | grep -i mellanox` 로 장치가 보이는지(보류 2)
- 다시 실행하면 `스킵: … 이미 연결됨, 전원 켜짐` 이 나오는지

**3) SystemId 교정 경로** — 보류 4

- 예전 방식(하드웨어 UUID)으로 붙어 있는 VM 이 있으면, 그 VM 을 끈 뒤 2)를 실행한다.
- 결과 줄이 `SystemId 교정 (… → …)` 이면 vCenter 가 Edit 을 받은 것이다. `Edit 대신 제거 후 다시 연결` 이면 받지 않은 것이다.
- 어느 쪽이든 전원 ON 성공을 확인하고, 게스트의 PCI 슬롯이 바뀌었는지 본다.

**4) NVIDIA GPU (EFI VM)** — 보류 3·6

```bash
./pci_passthrough-source/pci_passthrough -vcTargetIP=<vCenter> -worklistFile=pci_one.txt -ev01Pci=nvidia      # 자동 64GB
# 실패하면 vCenter 메시지·진단 줄을 기록하고, VRAM 이 큰 GPU 는 -mmioSizeGB=128 / 256 으로 다시
```

- 게스트에서 `nvidia-smi` 로 확인한다.
- BIOS VM 은 도구가 실패로 남기는 것이 정상이다. 일부러 시험할 때만 govc 로 64bit MMIO 를 직접 넣어 실제 메시지를 기록한다.

**5) vm_setup.sh 종단 (스펙에 pci 넣기)** — 보류 2·8

```bash
# SPEC_DIR/<스펙>/<스펙>_spec.txt 에 pci-ev01=mellanox 추가
cd /home/V2/VMsetup
./vm_setup.sh -u <user> -v <vCenter> -n        # 계획에 "pci_passthrough … ev01: Pci=mellanox"
./vm_setup.sh -u <user> -v <vCenter>           # 실행 → 모니터의 "PCI 패스스루" 단계, 스펙 체크의 "PCI 패스스루" 항목 OK
```

- 재부팅이 필요하면 `run_<user>/pci_resume_<번호>.sh` 가 생긴다. 호스트를 재부팅하고 실행한 뒤 `vm-param-check/01.vm_setting_check_insert.sh -u <user>` 로 다시 체크한다.
- 큰 VM(메모리 수백 GB)은 메모리 100% 예약 때문에 전원 ON 이 실패하지 않는지 본다(보류 8).

**결과 반영**: 확인한 것은 `pci_passthrough-source/README.md` 의 "실장비 확인이 필요한 것", `VMsetup/README.md` 알려진 한계, 계획서 §5 에서 지운다. 동작이 다르면(예: Edit 거부가 기본) 도구를 고치고 `bin_os6`/`bin_os8` 를 다시 빌드한다.

## 7. 앞으로: 카드 단위 배분 (D3)

- 지금은 ev 마다 **PCI 장치(function) 1개**를 PCI 주소 순서로 준다. 예: 듀얼 포트 카드의 `3b:00.0` 은 ev01, `3b:00.1` 은 ev02.
- 한 카드의 function 전부(같은 `도메인:버스:슬롯`)를 한 VM 에 줘야 하는 경우가 생기면 다음을 바꾼다.
  - 배분 단계에서 장치를 슬롯 단위로 묶어 묶음째 배분한다.
  - 활성화·연결도 묶음의 function 전부에 한다.
  - 이때 `pciPassthruInfo.dependentDevice` 도 함께 확인한다.
  - 스펙에는 예를 들어 `pci-ev01=mellanox:card` 같은 확장이 필요하다. 체크(`checker/pci.go`)도 "장치 1개 이상"에서 "카드의 function 전부"로 바꿔야 한다.
