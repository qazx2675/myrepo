# vm-ip-change

네트워크로 접속할 수 없는(IP 가 잘못 할당된) RHEL 8.10 VM 의 IP 를, **vCenter API 경로만으로**
재설정하는 도구입니다. 대상 VM 에 SSH/네트워크로 접속하지 않고, vCenter -> ESXi -> VMware
Tools(vmtoolsd) 경로(Guest Operations API)로 게스트 내부에서 `nmcli` 를 실행합니다. 이
경로는 VM 의 네트워크 스택을 거치지 않으므로, 관리서버가 그 VM 의 (잘못된) IP 로 접속하지
못하는 지금 같은 상황에서도 동작합니다.

⚠️ **주의사항 (Disclaimer)**
본 로그 분석 관련 스크립트 및 툴은 100% 신뢰하기보다는 참고용(보조 도구)으로 사용하는 것을 권장합니다. 설정 변경 스크립트의 경우, 설정 변경 후 무작위로 서버 몇 대를 골라 실제로 변경되었는지 직접 확인하는 절차가 반드시 필요합니다.
이 도구는 **설정 변경 도구**입니다. 적용 후 대상 VM 몇 대는 직접(콘솔 등으로) 접속해 IP 가 실제로 반영됐는지 확인하십시오.

> 실행 흐름은 [WORKFLOW.md](WORKFLOW.md), 폴더·파일별 역할은 [ARCHITECTURE.md](ARCHITECTURE.md) 를 참고하십시오.

같은 저장소의 [`ip_change`](../../Network_Change_Integration_Script/projects/ip_change)
와 목적은 비슷하지만, 그쪽은 `gossh` 로 **대상 노드에 SSH 접속**해 `ifcfg-*` 파일을 고치는
방식이라 네트워크가 살아있어야 합니다. 이 도구는 **네트워크 접속이 불가능한 VM** 을 위한
것입니다.

## 2. 입력 파일 준비

```bash
cp vcenter.txt.example vcenter.txt
cp list.txt.example    list.txt
```

- **`vcenter.txt`** — 작업 대상을 찾아야 하는 vCenter 주소, 한 줄에 하나. 여러 vCenter 를
  순서대로 뒤져 VM 이 있는 vCenter 에서 처리합니다.
- **`list.txt`** — `VM호스트네임 새IP` 공백 구분, 한 줄에 하나. `VM호스트네임` 은 vCenter
  인벤토리상의 **VM 표시 이름**입니다(도메인 없음, 게스트 OS 안의 hostname 이 아닙니다).

두 파일 모두 빈 줄과 `#` 로 시작하는 줄은 무시합니다. 실제 값이 든 두 파일은
`.gitignore` 에 이미 제외되어 있습니다(커밋하지 마십시오).

## 3. 실행

```bash
export VC_USER=administrator@vsphere.local
export VC_PASSWORD='********'      # vCenter 로그인
export GUEST_USER=root
export GUEST_PASSWORD='********'   # 대상 VM 게스트 OS(RHEL) 로그인

./bin/vm-ip-change
```

플래그로 파일 경로를 바꿀 수 있습니다(기본값은 각각 `vcenter.txt`, `list.txt`):

```bash
./bin/vm-ip-change -vcenter /path/to/vcenter.txt -list /path/to/list.txt
```

### 실행 흐름

1. `list.txt` 의 대상을 먼저 화면에 출력합니다(호스트네임 -> 새 IP, 게이트웨이 포함).
2. `vcenter.txt` 를 순서대로 접속하며, 아직 처리하지 못한 호스트네임과 일치하는 VM 을
   그 vCenter 인벤토리에서 찾습니다.
3. VM 을 찾으면 전원이 켜져 있고 VMware Tools 가 실행 중인지 확인합니다(둘 다 Guest
   Operations 전제조건입니다). 아니면 그 자리에서 `[FAIL]` 로 기록하고 건너뜁니다.
4. 대상 호스트네임이 `...ev02` 로 끝나면(물리서버(BM) 하나를 `ev01`/`ev02` 두
   VM 이 공유하는 명명 규칙), 워커를 배정받기 직전 짝(`ev01`) 게스트에서 `uptime`
   으로 1분 부하평균을 확인합니다. 짝이 BM 의 물리 코어 수 이상을 쓰고 있으면
   이 ev02 대상은 워커를 잡지 않고 뒤로 미루며(다른 대상이 그 자리를 바로 씀),
   **2분마다** 다시 확인하다가 코어 이하로 내려가면 그 확인이 곧 배정이 되어
   바로 처리를 시작합니다. 짝을 못 찾았거나 BM 물리 코어 수를 못 읽었으면
   미루지 않고 바로 진행합니다. `ev02` 로 끝나지 않는 대상(단독 VM, `ev01`
   자신 등)은 이 확인을 전혀 하지 않습니다.
5. 준비된 대상은 **최대 16대까지 동시에** 3단계로 처리합니다(순서는 무관, 병렬):
   1. **연결 확인** — 게스트 안에서 현재 활성 NetworkManager 연결(`nmcli con show
      --active` 의 첫 번째, `lo` 제외)을 찾고, 되돌릴 때 쓸 원래 설정을 캡처합니다.
   2. **IP 설정 적용** — 그 연결의 `ipv4.addresses`/`ipv4.gateway` 를 새 IP 로
      `manual` 재설정합니다(아직 반영 안 함). 서브넷마스크는 `255.255.255.0`(prefix
      24) 고정, 게이트웨이는 새 IP 의 마지막 옥텟을 `1` 로 바꾼 값입니다
      (예: `10.10.5.23` -> 게이트웨이 `10.10.5.1`).
   3. **연결 재기동** — `nmcli con up` 으로 그 연결만 다시 올립니다(서비스 전체
      재시작 아님). 성공하면 `[OK]`.
   각 단계는 게스트 명령이 끝날 때까지 **타임아웃 없이** 기다립니다 — 물리 코어를
   다른 VM 에 과점유당해 게스트 명령이 느려진 VM 도, 병렬 처리 덕분에 다른 VM 을
   막지 않고 언젠가 끝날 때까지 정상 처리됩니다.
6. 모든 vCenter 를 다 뒤져도 못 찾은 호스트네임은 `[FAIL]` 로 표시합니다.
7. 하나라도 실패하면 종료 코드 1, Ctrl+C 3번으로 중단하면 130 을 반환합니다.

### 진행 화면

시작 60초까지는 한 줄짜리 진행률만 갱신됩니다.

```
진행: 12/40 (30%)
```

60초를 넘으면 화면이 **대체 화면 버퍼**(vim/htop/less 와 같은 방식)로 바뀌어 전체
대상을 **페이지 단위**로 보여 줍니다. 매초 다시 그려도 터미널 스크롤백에는 쌓이지
않고, 끝나면 실행 전 화면으로 돌아간 뒤 전체 결과표가 출력됩니다.

| 키 | 동작 |
|---|---|
| ↑ / ↓ | 대상 선택 (페이지 끝에서 다음/이전 페이지로 넘어감) |
| ← / → 또는 PgUp / PgDn | 이전/다음 페이지 |
| Enter | 선택한 대상의 현재 단계(연결 확인 → IP 설정 적용 → 연결 재기동) 보기 |
| s | 그 시점의 완료/실패/진행중 전체 목록을 `vm-ip-change-snapshot-<시각>.txt` 로 저장 |
| 상세 화면에서 아무 키 | 목록으로 돌아가기 |

```
=== vm-ip-change 진행 중 === 경과 00:01:23
완료 12/1000 (1%)  진행중 16  대기 972  실패 0
↑/↓ 선택  ←/→ 또는 PgUp/PgDn 페이지  Enter 상세  s 목록 저장   [페이지 1/53]

  web0001                  완료(OK)     00:00:12
> web0002                  IP 설정 적용  00:01:05
  web0003                  대기중        00:00:00
```

- `s` 는 이 대화형 화면(60초 이후)에서만 동작합니다. 저장된 파일은 vm-ip-change 를
  실행한 디렉터리에 생기며, 저장 직후 화면에 "저장됨: <경로>" 가 잠깐 뜹니다.
- 경과 시간은 **끝난 대상은 끝난 시점에서 멈춥니다**(진행 중인 대상만 계속 올라감).
- 한 페이지 줄 수는 터미널 높이에 맞춰 자동으로 정해집니다.
- 대상이 1000대여도 가볍게 돌도록, 화면에 보이는 한 페이지만 그리고, 화면 전체를
  지우지 않고 줄 단위로 덮어쓰며, 바뀐 게 없으면 아예 출력하지 않습니다. 1초에
  터미널로 나가는 양은 대상 수와 무관하게 한 화면 분량(수 KB) 이하입니다
  (1000대·40줄 기준 프레임 약 2.6KB, 생성 0.1ms 미만 — `internal/tui/tui_test.go`).

출력이 터미널이 아닌 곳(로그 파일 등)으로 리다이렉트된 경우에는 이 대화형 화면
없이 한 줄 진행률만 계속 찍힙니다.

### 중단(Ctrl+C)

실수로 한 번 눌러 작업이 끊기지 않도록, **5초 안에 Ctrl+C 를 3번** 눌러야 즉시
종료합니다. 1~2번째에는 화면에 `Ctrl+C 1/3 — 5초 안에 2번 더 누르면 즉시
종료합니다` 같은 안내만 뜨고 작업은 계속됩니다.

즉시 종료 시 **되돌리기는 하지 않습니다.** 대신 터미널을 원래대로 돌려놓은 뒤
완료/실패/시작 안 함/도중 중단 개수와, 도중에 끊긴 대상 목록을 출력합니다:

- 연결 확인 중 끊긴 대상 → 설정 변경 전이라 변경 없음.
- IP 설정 적용/연결 재기동 중 끊긴 대상 → IP 가 바뀌었을 수 있습니다. 원래 IP 로
  되돌리려면 그 VM 게스트에서(콘솔 등으로) 출력에 표시된
  `bash /tmp/vm-ip-change/<호스트네임>.revert.sh` 를 실행하십시오(1단계에서 캡처해 둔
  원래 설정으로 복구하는 스크립트).

`pkill vm-ip-change`(SIGTERM)는 가로채지 않으므로 그대로 즉시 종료됩니다(이 경우
위 요약은 출력되지 않습니다).

## 4. 제약 사항

- 대상 VM 은 **RHEL 8.10, NetworkManager(nmcli) 사용**을 전제합니다. 다른 OS/네트워크
  구성 도구(netplan, systemd-networkd 등)는 지원하지 않습니다.
- VM 에 활성 네트워크 연결(NIC)이 **여러 개**인 경우, `nmcli con show --active` 가 돌려주는
  첫 번째(=lo 제외 가장 먼저 나열되는) 연결만 변경합니다. 어느 연결을 바꿀지 지정하는
  기능은 없습니다.
- `list.txt` 의 새 IP 는 항상 `/24`(`255.255.255.0`) 로 취급됩니다. 다른 서브넷마스크가
  필요하면 지금 버전으로는 처리할 수 없습니다.
- vCenter 인증서 검증은 하지 않습니다(폐쇄망 자체서명 인증서 환경 전제).
- 실행 후 네트워크 서비스 자체는 재시작하지 않고, 변경한 연결만 `nmcli con up` 으로
  다시 올립니다.
- 동시 처리 대수는 16 으로 고정입니다(코드 수정 없이는 조절 불가).
- `ev02` 짝 우선순위 확인(위 실행 흐름 4단계)은 호스트네임이 정확히 `...ev01`/
  `...ev02` 로 끝나고, vCenter 인벤토리에 BM 이름(접미사를 뺀 이름)과 같은
  ESXi 호스트(HostSystem)가 있을 때만 동작합니다. 재확인 주기(2분)는 코드
  수정 없이는 조절할 수 없습니다.
- 대화형 목록/상세보기(`internal/tui`)는 `golang.org/x/term` 으로 터미널을 raw
  모드로 바꿔 화살표 키를 직접 읽습니다. 이 때문에 `vendor/` 에
  `golang.org/x/term`, `golang.org/x/sys` 가 추가됐습니다(둘 다 기존과 동일하게
  폐쇄망에서 `-mod=vendor`로 빌드됩니다).

## 5. 시험 환경 (실제 vCenter 없이)

`cmd/fake-vcenter`(래퍼 `fake-vcenter.sh`)는 govmomi 의 vCenter 시뮬레이터(vcsim)로
가짜 vCenter 와 VM 을 원하는 수만큼 띄우고, 게스트 명령 실행(Guest Operations)만
직접 흉내 냅니다. 실제 VM·도커·네트워크 변경 없이 병렬 처리, 느린 VM, 실패, 60초 이후
진행 화면(페이지), Ctrl+C 3회 종료, **ev02 짝 우선순위 확인**을 모두 재현할 수
있습니다. `./setup.sh` 가 함께 빌드하며, 같은 `vendor/` 만 쓰므로 폐쇄망에서도 됩니다.

VM 은 BM(물리서버) 하나를 공유하는 두 대씩 `host0001ev01`/`host0001ev02` 로
이름 붙습니다. BM 도 같은 이름("host0001")의 가짜 ESXi 호스트로 만들어지고
`-cores` 개 물리 코어를 갖습니다.

명령만 순서대로 모은 것은 상위 폴더의 **`사용법.txt`** 를 보십시오.

### 자동 시험 — `./e2e-test.sh`

VM 20대(실패·전원꺼짐·없는 호스트 섞음)로 vm-ip-change 를 끝까지 돌리고, 도구가
`[OK]` 로 보고한 수와 가짜 vCenter 가 실제로 IP 가 바뀐 것을 확인한 수가 같은지,
엉뚱한 IP·반쯤 바뀐 VM 이 없는지 검사합니다. 약 20초, 마지막 줄이 `PASS`/`FAIL`.
CI(`.github/workflows`)도 같은 스크립트를 돌립니다.

### 수동 시험 — `./fake-vcenter.sh`

터미널 A 에서 가짜 vCenter 를 띄우면 `testrun/vcenter.txt`, `testrun/list.txt` 를 만들고
터미널 B 에서 붙여넣을 명령을 출력합니다. 시험이 끝나면 터미널 A 에서 Ctrl+C →
VM 별 실제 적용 결과(정상 / 기대와 다른 IP / 반쯤 변경 / 실패 / 변경 없음)를 출력하고
`testrun/report.txt` 로 저장합니다.

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `-vms` | 50 | 가짜 VM 수 (이름 `host0001ev01`, `host0001ev02`, `host0002ev01`..., BM 은 2대씩 공유) |
| `-cores` | 8 | BM(가짜 ESXi 호스트) 물리 코어 수 |
| `-busy-ev01` | 0 | 그 중 일부 짝의 `ev01` 이 BM 물리 코어 이상의 load average 를 계속 쓰는 것으로 흉내 낼 비율(%) — 해당 `ev02` 대상은 처리를 시작하지 못하고 계속 후순위로 밀림(§3 4단계) |
| `-min` / `-max` | 1s / 4s | 보통 VM 의 게스트 명령 1개 소요시간 범위 |
| `-slow` | 10 | 느린 VM 비율(%) — CPU 과점유로 느려진 VM 흉내 |
| `-slow-delay` | 40s | 느린 VM 의 게스트 명령 1개 소요시간 (3단계라 약 2분) |
| `-fail` | 5 | "IP 설정 적용" 단계에서 exit 1 로 실패하는 VM 비율(%) |
| `-off` | 0 | 전원 꺼진 VM 비율(%) |
| `-missing` | 0 | list.txt 에만 있고 vCenter 에 없는 호스트 수 |
| `-seed` | 1 | 난수 시드 — 같은 값이면 같은 VM 이 느림/실패/과점유로 뽑힘 |
| `-addr` | 127.0.0.1:18443 | 가짜 vCenter 주소 |
| `-out` | testrun | 입력/결과 파일 폴더 |

가짜 vCenter 계정은 `administrator@vsphere.local` / `VMware1!`, 게스트 계정은
`root` / `guestpass` 입니다(틀리면 실제처럼 로그인 실패가 납니다). VM 1000대는
뜨는 데 수 초가 걸리니 `가짜 vCenter 실행 중` 이 출력된 뒤 vm-ip-change 를 실행하십시오.

**ev02 우선순위 확인 시험**: `-busy-ev01 30` 처럼 주면 그 비율만큼의 짝에서 `ev01`
이 "항상 과점유 중"으로 고정됩니다(부하가 바뀌지 않으므로 2분마다 재확인해도
절대 안 풀립니다 — 일부러 그렇게 만들었습니다: 실제로 부하가 안 내려가면
`ev02` 대상은 무기한 대기한다는 뜻이기도 합니다). vm-ip-change 목록 화면에서 그
`ev02` 대상만 계속 "대기중"으로 남는지 확인하고, `s` 로 현재 목록을 저장하거나
Ctrl+C 3회로 중단해 보십시오 — 짝이 과점유 중인 `ev02` 는 "시작 안 함"으로,
나머지는 정상 처리됐어야 합니다.

알아둘 점:
- 게스트 명령은 vm-ip-change 가 종료돼도 게스트 안에서 끝까지 실행되므로(실제 VM
  과 동일), Ctrl+C 3회 직후 "IP 설정 적용 중 중단"이던 VM 은 검증 결과에서
  "반쯤 변경"으로, "연결 확인 중 중단"이던 VM 은 "변경 없음"으로 나와야 정상입니다.
- 실제 `nmcli`/`uptime` 동작(연결 이름 찾기, 원래 설정 캡처, 되돌리기 스크립트 내용,
  실제 부하평균 계산)은 흉내 내지 않습니다 — 이 부분은 실제 VM 몇 대로 확인해야
  합니다. `-busy-ev01` 도 정해진 값을 고정으로 돌려줄 뿐, 시간에 따라 부하가
  바뀌는 상황은 흉내 내지 않습니다.
