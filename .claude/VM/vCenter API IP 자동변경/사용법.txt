git clone -b vm-ip-change-standalone https://github.com/qazx2675/myrepo.git vm-ip-change
cd vm-ip-change/project
./setup.sh

[2] 자동 시험 (list.txt 구성 both/ev02-only/ev01-only 3가지 x 약 20초, 마지막 줄 PASS 확인)
./e2e-test.sh

[3] 수동 시험 - 터미널 A (가짜 vCenter, VM 1000대, 느린 VM 10%, 실패 2%)
cd vm-ip-change/project
./fake-vcenter.sh -vms 1000 -slow 10 -slow-delay 40s -fail 2
(“가짜 vCenter 실행 중” 출력될 때까지 대기)

[4] 수동 시험 - 터미널 B
cd vm-ip-change/project
export VC_USER='administrator@vsphere.local' VC_PASSWORD='VMware1!' GUEST_USER='root' GUEST_PASSWORD='guestpass'
./bin/vm-ip-change -vcenter testrun/vcenter.txt -list testrun/list.txt
(60초 뒤 목록 화면: ↑ ↓ / ← → / PgUp PgDn / Enter 상세 / s 목록 저장 / 아무 키)
(Ctrl+C 1번 → 안내만 / 5초 안에 3번 → 즉시 종료)

[5] 터미널 A 에서 결과 검증
Ctrl+C
cat testrun/report.txt

[6] 수동 시험 - ev02 우선순위 확인, 계속 밀리는 경우 (짝 ev01 이 영원히 과점유)
(list.txt 엔 ev02 60개만 있고 짝 ev01 은 부하 확인용으로만 조회되는, 가장 흔한 실제 형태.
 그 중 절반(-busy-ev01 50)은 짝이 과점유라 대기, 나머지 절반은 바로 처리됨)
터미널 A: ./fake-vcenter.sh -vms 120 -pair-mode ev02-only -busy-ev01 50 -out testrun-ev
터미널 B: ./bin/vm-ip-change -vcenter testrun-ev/vcenter.txt -list testrun-ev/list.txt
(60초 뒤 목록 화면에서: 짝(ev01)이 과점유로 뽑힌 ev02 대상 약 30개는 "대기중"에 계속
 머물고, 나머지 약 30개는 금방 "완료(OK)"로 바뀌는 걸 확인 — 이게 우선순위가 바뀐
 모습입니다: 뒤로 밀린 대상은 워커를 안 잡고 대기만 하므로 앞선 대상이 먼저 끝남)
(s 로 현재 목록 저장 후 Ctrl+C 3회로 중단)
cat testrun-ev/report.txt   (과점유 ev01 의 ev02 짝만 "시작 안 함"으로 나와야 정상)

[6-1] 수동 시험 - ev02 우선순위 확인, 다시 풀리는 경우 (짝 ev01 부하가 90초 뒤 내려감)
(2분 재확인 주기 때문에 완료까지 약 2분 10초 걸립니다 — 기다려서 직접 확인하십시오.
 처음엔 "대기중"이던 대상이, 약 2분 뒤 한꺼번에 처리를 시작해 "완료(OK)"로 바뀌는
 순간이 우선순위가 다시 올라간 모습입니다)
터미널 A: ./fake-vcenter.sh -vms 120 -pair-mode ev02-only -busy-ev01 50 -busy-ev01-for 90s -out testrun-ev2
터미널 B: ./bin/vm-ip-change -vcenter testrun-ev2/vcenter.txt -list testrun-ev2/list.txt
(약 2분 10초 뒤 전부 완료 확인 — rc=0, cat testrun-ev2/report.txt 로 "정상 변경" 개수 확인)

[6-2] (선택) 짝 ev01 자신도 동시에 변경 대상인 경우 — -pair-mode both 로 교체해 반복
./fake-vcenter.sh -vms 120 -pair-mode both -busy-ev01 50 -busy-ev01-for 90s -out testrun-ev3
