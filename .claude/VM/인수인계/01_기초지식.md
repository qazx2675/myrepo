# 01. 기초지식 — vSphere 개념 정리

이 문서는 **도구의 옵션 이름들이 왜 그렇게 생겼는지**를 이해하기 위한 최소한의 가상화 개념만 다룹니다. VMware 자격증 수준의 설명은 아닙니다.

---

## 1. 물리 서버부터 VM까지

### ESXi

물리 서버 한 대에 설치하는 **VMware의 운영체제**입니다. 리눅스나 윈도우 대신 ESXi를 깔면, 그 서버는 "가상 머신을 여러 개 돌리는 기계"가 됩니다. 이 문서들에서 **"호스트(Host)" = ESXi가 깔린 물리 서버 한 대**입니다.

- 이 저장소에서는 물리 서버를 **BM(Bare Metal)** 이라고 부릅니다. `BM = 호스트 = ESXi 서버` 전부 같은 뜻으로 쓰입니다.

### VM (가상 머신)

ESXi 위에서 돌아가는 가상 컴퓨터입니다. 여기서는 이 저장소의 이름 규칙이 중요합니다.

```
서버이름이 "svr01" 이면
   svr01ev01   ← 1번 VM
   svr01ev02   ← 2번 VM
   ...
   svr01ev99   ← 최대 99번 VM (V2 기준)
```

**`ev01`~`ev99`를 "그룹"이라고 부릅니다.** 도구 옵션에 `-cores-ev02`, `-ev05Cpu` 같은 게 잔뜩 나오는 이유가 이겁니다 — 같은 물리 서버 위에 올라간 VM이라도 역할이 달라서 스펙(vCPU 수, 메모리)이 다르고, 그룹별로 기대값을 따로 줘야 하기 때문입니다.

- `ev01` : 필수. 보통 메인 워크로드용, 가장 큼
- `ev02` 이후 : 선택. ev01부터 번호가 **연속**이어야 함
- 번호가 두 자리(`ev%02d`)라 99가 상한입니다 (`ev100`은 `ev10`으로 잘못 판정됨)

### vCenter

ESXi 서버가 수백 대면 하나씩 접속할 수 없습니다. **vCenter는 ESXi들을 한꺼번에 관리하는 중앙 관리 서버**입니다.

- 웹 UI를 **vSphere Client**라고 부릅니다 (브라우저로 `https://<vCenter IP>` 접속).
- **이 저장소의 도구들은 거의 전부 vCenter의 API에 접속합니다.** 개별 ESXi에 SSH로 들어가지 않습니다.
- 접속 포트는 **443/tcp(HTTPS)** 입니다. 방화벽에서 이게 열려 있어야 합니다.
- 규모가 커지면 vCenter도 여러 대입니다. 그래서 도구들이 `vcenter.txt`(vCenter 주소 목록 파일)를 받습니다.

### 인벤토리와 폴더

vCenter 안의 트리 구조를 **인벤토리(Inventory)** 라고 합니다.

```
vCenter
└── 데이터센터 (Datacenter)         ← 논리적 최상위 묶음
    ├── 호스트 폴더 / 클러스터        ← ESXi 호스트들이 들어감
    │   └── ESXi 호스트
    └── VM 폴더                     ← VM들이 들어감
        └── TST-CAE001-SAMP48c-QRST   ← 이런 이름의 폴더 안에 VM들이 있음
            ├── svr01ev01
            └── svr01ev02
```

> **이 폴더 이름이 중요합니다.** `vm-param-check`의 `-specRoot` 기능은 "VM이 어느 폴더에 들어 있는가"를 보고 그 VM의 기대 스펙을 자동으로 찾아옵니다. 폴더 이름 자체가 스펙 식별자 역할을 하는 겁니다. 자세한 규칙은 [11번 문서](./11_vm-param-check.md)에 있습니다.

## 2. 성능 설정 개념 (도구 옵션의 대부분이 여기서 나옵니다)

### vCPU / 소켓 / 코어

VM에 CPU를 줄 때 vSphere는 세 가지 숫자를 씁니다.

| 용어 | 의미 | 도구 옵션 |
|---|---|---|
| **vCPU 수** | VM이 보는 논리 CPU 총 개수 | `-cpu`, `-ev01Cpu` |
| **소켓당 코어 수** (`coresPerSocket`) | 그 vCPU를 몇 개의 "물리 소켓"으로 나눠 보여줄지 | `-cores`, `-ev01Cores` |
| **소켓 수** | vCPU 수 ÷ 소켓당 코어 수 | `-ev01Sockets` |

**왜 신경 쓰나?** 게스트 OS와 애플리케이션이 "CPU가 몇 소켓짜리인지"를 보고 메모리 접근 전략을 바꾸기 때문입니다. 잘못 나누면 성능이 떨어집니다. 그래서 `vCPU 수는 소켓당 코어 수로 나누어떨어져야` 하고, 도구들이 이걸 검사합니다.

### NUMA

물리 서버에 CPU 소켓이 2개 있으면, **각 소켓에 붙어 있는 메모리가 따로 있습니다.** 자기 소켓에 붙은 메모리는 빠르고, 옆 소켓의 메모리는 느립니다. 이 "CPU+메모리 묶음" 하나를 **NUMA 노드**라고 합니다.

```
[소켓 0] ── 빠름 ── [메모리 0]     ← NUMA 노드 0
   │
   └── 느림 ──┐
              ▼
[소켓 1] ── 빠름 ── [메모리 1]     ← NUMA 노드 1
```

VM이 NUMA 노드 하나에 딱 들어가면 빠르고, 두 노드에 걸치면 느려집니다. 그래서:

| 설정 | 의미 | 도구 옵션 |
|---|---|---|
| `numa.vcpu.maxPerVirtualNode` | 가상 NUMA 노드 하나에 최대 몇 개의 vCPU를 넣을지 | `-numa` |
| `config.numaInfo.coresPerNumaNode` | NUMA 노드당 코어 수 (vSphere UI: 설정 편집 > VM 옵션 > CPU 토폴로지) | `-numa` 로 함께 체크 |
| `numa.vcpu.preferHT` | NUMA 배치 시 하이퍼스레드를 우선 사용할지 (TRUE/FALSE) | `-preferHT` |

> `config.numaInfo.coresPerNumaNode`에는 함정이 있습니다. vSphere UI에서 "NUMA 노드 — 전원을 켤 때 할당됨"(Auto)으로 되어 있으면, 이 값에는 **지난번 전원 켤 때의 값이 그냥 남아 있을 뿐**이고 의미가 없습니다. 도구는 Auto 상태를 감지하면 "설정없음"으로 처리합니다 (2026-08-23에 수정된 버그).

### CPU Affinity (vCPU 고정)

"이 VM의 3번 vCPU는 물리 CPU 17번이나 19번에서만 돌아라"처럼 **vCPU를 물리 CPU에 고정**하는 설정입니다. VM끼리 CPU를 뺏고 뺏기는 걸 막아 성능 편차를 줄입니다.

vSphere에는 저장 위치가 두 군데 있습니다. 이 저장소의 도구들은 주로 두 번째를 씁니다.

1. `Config.CpuAffinity.AffinitySet` — 구조화된 필드
2. **`sched.vcpu0.affinity`, `sched.vcpu1.affinity`, ...** — vCPU 개수만큼 생기는 ExtraConfig 키 (← 이쪽)

값은 `17,19,21,23` 같은 물리 CPU 번호 목록입니다.

> **순서는 의미가 없습니다.** "이 vCPU가 돌 수 있는 물리 CPU 후보 목록"일 뿐 우선순위가 아니라서, `31,29,27`과 `27,29,31`은 같은 설정입니다. 도구도 순서를 무시하고 비교합니다. 단 **개수는 봅니다** — `16,17`과 `16,17,17`은 다르게 판정합니다(중복 오기입을 조용히 넘기지 않기 위해).

**하이퍼스레딩(HT)** 이 켜져 있으면 물리 코어 1개가 논리 CPU 2개로 보입니다. 그래서 affinity 값을 자동 계산할 때 HT ON이면 `0,1` / `2,3` 식으로 2개씩, OFF면 1개씩 묶습니다. 이것이 `-ht on|off` 옵션의 정체입니다.

### Large Page (lpage) / HugePage

메모리는 보통 4KB 단위(페이지)로 관리되는데, 큰 메모리를 쓰는 워크로드에서는 이게 비효율적입니다. **2MB 단위(Large Page)** 로 관리하면 훨씬 빠릅니다.

문제는 **ESXi가 메모리 여유가 충분할 때만 Large Page를 유지**한다는 점입니다. 여유가 줄면 ESXi가 Large Page를 잘게 쪼개버려서 성능이 떨어집니다.

- ESXi는 총 메모리의 약 2%를 `minFree`로 잡고, 여유 메모리가 `minFree × 3` 이상이면 **High 상태**로 보고 Large Page를 유지합니다.
- 그래서 **VM에 메모리를 꽉 채워 할당하면 안 됩니다.** 버퍼를 남겨야 합니다.
- 이 버퍼를 계산해서 "ev02에 몇 GB까지 줘도 되나"를 알려주는 게 [`lpage_search`](./13_lpage_search.md)입니다.

관련 ExtraConfig 키들:

| 키 | 의미 |
|---|---|
| `sched.mem.lpage.enable1GPage` | 1GB 페이지 사용 여부 |
| `sched.mem.prealloc` | VM 메모리를 미리 통째로 확보 |
| `sched.mem.prealloc.pinnedMainMem` | 확보한 메모리를 물리 메모리에 고정(스왑 방지) |
| `sched.swap.vmxSwapEnabled` | vmx 프로세스 스왑 사용 여부 |

### Shares (공유값)

물리 자원이 부족할 때 **어느 VM에게 우선권을 줄지** 정하는 상대적 가중치입니다.

- `Normal` : vSphere가 알아서 계산 (기본값)
- `Custom` + ratio 숫자 (예: `4000`) : 직접 지정

도구 옵션 `-shares-ev01=4000`은 "ev01 그룹은 Custom ratio 4000이어야 한다"는 뜻이고, `-shares-ev01=normal`은 "Level이 normal이면 된다"는 뜻입니다. `4000,normal`처럼 쉼표로 여러 개 주면 **그 중 하나만 맞아도 통과**입니다.

### 호스트 전원 정책 (Power Policy)

ESXi 호스트 수준 설정입니다. 기본값은 "Balanced"(전력 절약)인데, 고성능 워크로드에서는 **High Performance**로 바꿔야 CPU 주파수가 떨어지지 않습니다. `vm-param-check`는 이걸 **점검만** 하고 자동 교정은 하지 않습니다. 교정은 `VM_setup/vm-param-fix/power_setting` 바이너리로만 가능합니다 ([17번 문서](./17_VM_setup_잔여도구.md)).

## 3. 네트워크 개념

### vSwitch와 포트그룹

```
[VM] ──(가상 NIC, vNIC)──> [포트그룹] ──> [vSwitch] ──> [물리 NIC, vmnic] ──> 실제 네트워크
```

- **vSwitch(가상 스위치)**: ESXi 호스트 안에 있는 가상 스위치. 기본 이름은 `vSwitch0`.
- **포트그룹(Port Group)**: vSwitch 위에 만드는 논리적 포트 묶음. VLAN ID를 지정할 수 있습니다. **VM은 포트그룹에 연결됩니다.**
- 포트그룹은 **ESXi 호스트마다 따로 만들어야 합니다.** 그래서 `vswitch_<user>.txt`의 첫 칼럼이 VM 이름이 아니라 **호스트 이름**입니다.

두 종류가 있습니다:

| 종류 | 설명 | 이 저장소 지원 |
|---|---|---|
| **표준 vSwitch (VSS)** | 호스트마다 개별 설정 | ✅ 지원 |
| 분산 스위치 (VDS/DVS) | vCenter가 여러 호스트에 걸쳐 한꺼번에 관리 | ❌ 포트그룹 생성 불가 |

### MAC 주소와 DHCP

VM을 새로 만들면 가상 NIC에 MAC 주소가 부여됩니다. 이 MAC을 DHCP 서버에 등록해두면 원하는 IP/OS 이미지가 자동으로 배포됩니다(Kickstart 프로비저닝).

여기서 사고가 납니다. **MAC을 잘못 등록하면 A 서버에 깔려야 할 OS가 B 서버에 깔립니다** — 이걸 **교차 설치(역설치)** 라고 부릅니다. OS 설치가 끝난 뒤 발견하면 재설치해야 하니, **파워온 전에** 잡아내야 합니다. 그 도구가 [`vm_verifier`](./12_vm_verifier.md)입니다.

## 4. 이 저장소가 쓰는 기술

### govmomi

VMware가 만든 **Go 언어용 vSphere API 라이브러리**입니다. 이 저장소의 Go 도구들은 전부 govmomi로 vCenter에 접속합니다.

- 버전: V2 VMsetup·망변경 포트그룹 단계 `v0.55.1`, vm-param-check·vm_verifier `v0.39.0`
- `V2/govendor/`, `.claude/공통/govendor/`, 각 프로젝트의 `vendor/`에 통째로 들어 있어서 인터넷 없이 빌드됩니다.

### Reconfigure Task

vCenter에서 VM 설정을 바꾸는 API 호출을 `ReconfigVM_Task`라고 합니다. **비동기**입니다 — 요청을 보내면 Task ID가 돌아오고, 완료를 따로 기다려야 합니다.

- 도구들은 "전송 → 완료 대기"를 워커 하나가 통째로 담당하는 **워커풀** 구조로 병렬 처리합니다.
- 동시 처리 개수를 `-concurrency`(기본 20~32)로 제한합니다. 너무 크게 잡으면 vCenter에 부하가 걸립니다.
- 좋은 도구는 VM 1대당 Reconfigure를 **정확히 한 번만** 호출합니다 (`vm-param-check -fix`가 그렇게 만들어져 있습니다).

### 전원 OFF 요구사항

**CPU 토폴로지(소켓/코어/NUMA)는 VM이 켜져 있으면 바꿀 수 없습니다.** 하드웨어 수준 설정이기 때문입니다. 그래서:

- `vm-param-check -fix`는 교정 대상 VM이 전부 꺼져 있는지 확인하고, 하나라도 켜져 있으면 **아무것도 바꾸지 않고 중단**합니다.
- `numa_preferht_setting`은 켜져 있는 VM을 건너뛰고 사유를 출력합니다.

## 5. 폐쇄망(Air-gapped) 환경

이 저장소가 유별나게 신경 쓰는 부분입니다.

**폐쇄망**이란 보안상 인터넷이 완전히 차단된 네트워크입니다. 실제 운영 서버들이 여기 있습니다. 그래서:

- `go build`가 인터넷에서 라이브러리를 받아오면 **빌드가 실패합니다.**
- 해결책: 각 프로젝트에 **`vendor/` 폴더**를 두고 의존성 소스를 통째로 커밋해 둡니다.
- 빌드할 때 `go build -mod=vendor`를 쓰면 인터넷을 보지 않습니다. `setup.sh`가 이 플래그를 항상 붙여줍니다.

**따라서 지켜야 할 규칙:**

1. 폴더를 옮길 때는 **통째로** 옮깁니다. `vendor/`를 빼면 빌드가 안 됩니다.
2. 코드 수정 시 새 외부 라이브러리를 추가하지 않습니다. 꼭 필요하면 인터넷 되는 PC에서 `go mod vendor`를 다시 돌려 `vendor/`를 갱신하고 함께 커밋해야 합니다.
3. `setup.sh`를 쓰세요. 직접 `go build`를 치면 `-mod=vendor`를 빼먹기 쉽습니다.
