# 30. 유지보수 — 수정 요청 방법

## 이 문서의 전제

이 저장소의 도구들은 AI로 만들어졌습니다. 유지보수도 Go를 깊이 아는 것보다 **"어느 폴더를, 어떤 문서를 읽고, 무엇을 바꿔라"를 정확히 전달하는 것**이 중요합니다. 이를 위해 도구별로 유지보수에 필요한 .md 문서만 모아 둔 **`유지보수` 공유 폴더**를 씁니다(인수인계 시 이 폴더도 함께 전달받습니다).

> 공유 폴더의 문서는 저장소 원본의 사본입니다. 어긋나면 **저장소의 원본이 기준**입니다.

---

## 1. 요청 방법 — 프로젝트 폴더 + 참조 문서

수정 요청에는 두 가지를 같이 적습니다.

1. **변경할 프로젝트 폴더** — 저장소 경로. 예: `.claude/VM/V2/VMsetup/`
2. **참조 문서** — 공유 폴더에서 해당 도구 그룹의 .md 파일

AI에게는 이렇게 전달합니다(대상 폴더와 참조 문서를 함께 첨부).

```
[변경할 프로젝트 폴더] .claude/VM/V2/VMsetup/
[참조 문서] 유지보수/1_VM_setup_및_설정체크/ 의 V2_공통/ARCHITECTURE.md, V2_공통/PR_CHECKLIST.md,
            VMsetup/CHANGELOG.md, VMsetup/tag_setting-source_README.md
[요청 내용] ...
[유지할 것] 요청하지 않은 파일·동작은 바꾸지 말 것. 오프라인(vendor) 빌드 유지.
[완료 기준] PR_CHECKLIST.md 항목 확인, CHANGELOG.md 추가, 옵션이 바뀌면 README 갱신
```

참조 문서를 먼저 읽게 하고, 범위가 커지면(다른 파일까지 건드려야 하면) 진행 전에 알려 달라고 덧붙이면 엉뚱한 파일을 건드리는 것을 막을 수 있습니다.

### 참조 문서 종류

| 문서 | 읽는 목적 |
|---|---|
| `ARCHITECTURE.md` | 구조·설계 결정·건드리면 안 되는 곳 파악 |
| `WORKFLOW.md` | 실행 흐름 확인 (흐름이 바뀌면 함께 수정) |
| `PR_CHECKLIST.md` | 수정 후 빌드·테스트·검증 절차 |
| `CHANGELOG.md` | 같은 수정을 반복하지 않도록 변경 이력 확인, 수정 후 항목 추가 |
| `README.md` | **옵션이 바뀌면 반드시 함께 수정**(옵션표·예시) |

> **옵션(플래그·환경변수·입력 파일 형식)이 추가·변경·삭제되면 해당 도구의 README도 요청 범위에 포함합니다.**

## 3. 수정이 끝난 뒤 갱신할 것

| 바뀐 것 | 갱신할 문서 |
|---|---|
| 모든 수정 | 도구 폴더의 `CHANGELOG.md`에 오늘 날짜로 항목 추가(맨 위) |
| 옵션·환경변수·입력 파일 형식 | 도구의 `README.md` 옵션표, 이 핸드북의 해당 도구 문서(10·11·12·13·14·15번)의 옵션표 |
| 실행 흐름·단계 순서 | `WORKFLOW.md`와 `workflow.svg`(`.mmd`가 있으면 원본부터), 핸드북의 흐름도 |
| 구조·설계 결정 | `ARCHITECTURE.md` |
| 위 문서를 고쳤을 때 | 공유 `유지보수` 폴더의 사본도 같은 파일로 교체 |

핸드북(HTML)은 인수인계 폴더의 `build_handbook.py`로 다시 만듭니다(오프라인 — 외부 CDN 없이 mermaid를 내장합니다).

```bash
python build_handbook.py
```

## 4. 확인

- 빌드·테스트는 요청한 도구의 `PR_CHECKLIST.md` 항목을 기준으로 합니다.
- 결과를 받으면 **요청한 파일만 바뀌었는지 diff**를 확인하고, 설정을 바꾸는 도구라면 무작위 VM·호스트 몇 대에서 실제 반영을 직접 확인합니다.
- 변경 후에도 폐쇄망에서 `vendor/` 기반 오프라인 빌드가 되는지는 반드시 확인하세요.
