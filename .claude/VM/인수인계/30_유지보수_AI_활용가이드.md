# 30. 유지보수 — AI로 코드를 수정하는 방법

## 이 문서의 전제

**이 저장소의 도구들은 전부 AI(이른바 "바이브 코딩")로 만들어졌습니다.** Go 언어를 깊이 알아야 유지보수할 수 있는 게 아니라, **무엇을 어떻게 바꿔야 하는지 정확히 설명할 수 있으면** 유지보수가 됩니다.

그래서 이 문서는 "Go 코드 고치는 법"이 아니라 **"AI에게 제대로 시키는 법"** 입니다.

핵심은 하나입니다.

> **정해진 양식으로 요청하면 결과 품질이 일정합니다.**
> 즉흥적으로 "이거 좀 고쳐줘"라고 하면 AI가 엉뚱한 파일을 건드리거나, 안전장치를 없애거나, 폐쇄망 빌드를 깨뜨립니다.

---

## 1. 전체 절차 (4단계)

```
1) 양식 작성        31_변경요청서_양식.md 을 복사해서 채운다
      ↓
2) AI에게 전달      양식 + "먼저 이 문서들부터 읽어라" 지시
      ↓
3) 결과 확인        빌드/테스트 통과 + 실제로 요청한 것만 바뀌었는지 diff 확인
      ↓
4) 기록            CHANGELOG.md 갱신 + 작업 기록 폴더에 계획서 저장 + 인수인계 문서 갱신
```

## 2. 1단계 — 변경 요청 양식 작성

[31_변경요청서_양식](./31_변경요청서_양식.md)을 복사해서 채웁니다. 다섯 칸입니다.

| 칸 | 왜 필요한가 | 안 쓰면 생기는 일 |
|---|---|---|
| **대상 저장소·경로** | AI가 어느 폴더를 고칠지 확정 | 비슷한 이름의 다른 폴더를 고침 (이 저장소엔 `vm-param-check`가 여러 벌 있습니다 — 현행은 `V2/` 아래) |
| **참고 문서** | 기존 구조와 컨벤션을 먼저 파악 | 기존 스타일과 다른 코드가 섞임 |
| **요청 내용** | 무엇을 바꿀지 | 범위가 무한정 커짐 |
| **제약 / 유지할 것** | **건드리면 안 되는 것** | 안전장치가 사라지거나 폐쇄망 빌드가 깨짐 |
| **완료 기준** | 언제 끝난 건지 | "다 됐다"고 하는데 빌드가 안 됨 |

### 가장 중요한 칸: "제약 / 유지할 것"

이 저장소에는 **없애면 사고가 나는 안전장치**들이 있습니다. AI는 요청하지 않은 것도 "개선"이라고 판단해 건드릴 수 있으므로, **반드시 명시**하세요.

| 안전장치 | 어느 도구 | 없애면 |
|---|---|---|
| `-fix`의 **게이트**(그룹 동질성 + 전원 OFF 확인) | vm-param-check | 켜져 있는 VM의 CPU 토폴로지를 바꾸려다 실패하거나, 스펙이 다른 VM에 잘못된 값이 들어감 |
| **`-yes`가 실제 변경 확인을 생략하지 않는 것** | vm-param-check | 무인 실행에서 설정이 통째로 바뀜 |
| **인시던트 자동 저장 + 역순 롤백**, 엔진 백업만 인덱싱(자체 백업 금지) | Network_Change_Integration_Script | 롤백이 원본으로 돌아가지 않음 |
| **포트그룹 대상 = `ip_ok` 목록** | Network_Change_Integration_Script | IP 실패 VM이 새 VLAN으로 옮겨져 고립 |
| **엔진 출력 파싱 계약** (`lib/stages.sh`의 awk 패턴) | Network_Change_Integration_Script | 성공/실패 집계가 틀어짐 |
| **Ctrl+C 5초 안에 3번** 종료 | 망변경 엔진, vm-ip-change | 실수 한 번에 작업이 끊김 |
| **실패 시 종료코드 1, 그 단계에서 멈춤** | V2 `vm_create`/`vswitch_setting`/`vm_setup.sh` | 실패를 모른 채 다음 단계 진행 |
| **affinity 파일 필수**(자동 계산 없음) | V2 `affinity_setting` | ev들이 같은 물리 CPU에 겹쳐 고정 |
| **전원 OFF 스킵** | V2 numa_preferht_setting | 켜진 VM에 적용 시도 → 실패 |
| **`power_setting` 바이너리 보존** | `VM_setup/vm-param-fix/` | 소스 없는 유일 사본 — 복구 불가 |
| **비밀번호를 환경변수로만 받는 것** | 전부 | 셸 히스토리/`ps`에 비밀번호 노출 |
| **`vendor/` 기반 오프라인 빌드** | 전부 | **폐쇄망에서 빌드 불가능** |
| **옵션 미지정 시 스킵** 동작 | vm-param-check | 안 준 옵션까지 체크되어 대량 FAIL |

### 완료 기준에 항상 넣을 것

```
- bash setup.sh (오프라인 빌드) / go vet 통과
- 대상 폴더 PR_CHECKLIST.md 의 항목 전부 확인
- 실 vCenter 에서 대상 2대로 최소 1개 시나리오 재현 확인
- CHANGELOG.md 에 오늘 날짜로 항목 추가
- README.md 및 인수인계 문서의 옵션표 갱신
```

## 3. 2단계 — AI에게 전달

### 반드시 앞에 붙일 지시

```
아래 변경 요청을 처리해줘.
시작하기 전에 대상 경로의 README.md → 계획서.md/PLAN.md(있으면) → CHANGELOG.md → ARCHITECTURE.md 를 이 순서로 읽고
기존 구조와 컨벤션을 파악한 뒤에 착수해.

변경 범위가 처음 합의한 것보다 커지면(다른 파일까지 건드려야 하면) 진행 전에 먼저 알려줘.
```

AI가 저장소를 직접 받아야 하면 알려줍니다.

```

```

## 4. 3단계 — 결과 확인 (사람이 반드시 할 일)

AI가 "완료했습니다"라고 해도 **그대로 믿지 마세요.** 아래를 직접 확인합니다.

### 확인 명령

```bash
cd <대상 폴더>

# 1) 빌드되는가 (폐쇄망 기준으로!)
bash setup.sh

# 2) 정적 분석 통과하는가
go vet -mod=vendor ./...

# 3) 대상 폴더의 PR_CHECKLIST.md 항목을 하나씩 확인

# 4) 요청한 것만 바뀌었는가 ← 가장 중요
git diff --stat
git diff
```

### `git diff`에서 봐야 할 것

| 확인 | 왜 |
|---|---|
| **`vendor/` 아래가 바뀌지 않았는가** | 바뀌었다면 새 의존성이 추가된 것 → 폐쇄망 빌드가 깨질 수 있음 |
| **요청과 무관한 파일이 바뀌지 않았는가** | AI가 "겸사겸사" 리팩터링한 것. 되돌리라고 요청 |
| **안전장치 코드(`gates.go`, 확인 프롬프트)가 그대로인가** | 없어졌으면 즉시 되돌릴 것 |
| **기존 옵션의 기본값이 바뀌지 않았는가** | 운영 스크립트가 기본값에 의존할 수 있음 |
| **에러 메시지/출력 형식이 바뀌지 않았는가** | 로그 파싱하는 자동화가 깨질 수 있음 |

### 실제 환경 검증

실 vCenter에서 확인할 때는 **대상 2대**로만, **예정만 보는 모드(`-n`, `--dry-run`, `-fix` 없이 점검) 먼저** 돌리세요.

## 5. 4단계 — 기록

### 5-1. CHANGELOG.md (필수)

각 도구 폴더의 `CHANGELOG.md`에 **최신이 위**로 추가합니다. 형식은 기존 항목을 그대로 따르세요.

```markdown
## YYYY-MM-DD — <한 줄 요약>

- **<영역>(`파일명`)**: 무엇을, 왜 바꿨는지
- **영향 범위**: 건드린 파일 목록과 각각 어떤 부분인지
- **확인**: 빌드/vet 결과, 재현한 시나리오와 결과
```

실제 예시(이 저장소에 있는 것):

```markdown
## 2026-08-23 — NUMA 노드당 코어수 체크가 Auto 모드를 무시하던 버그 수정

- **문제**: `autoCoresPerNumaNode=true`인 VM은 `coresPerNumaNode`에 지난 전원 켜짐 시점의
  값이 남아있을 뿐이라 무시해야 하는데, 체크가 이 값을 그대로 비교해서 우연히 값이 같으면
  OK로 잘못 판정하고 있었다.
- **조회(`vcenter/client.go`)**: `vm.Config.NumaInfo.AutoCoresPerNumaNode`를 함께 조회.
  `model.VMInfo`에 `NumaAutoCoresPerNode *bool` 필드 신설.
- **체크(`checker/topology.go`)**: true면 값 비교 없이 "설정없음"으로 처리하도록 분기 추가.
- **영향 범위**: vm-param-check 뿐 아니라 레거시 vm-param-setting-check 에도 동일 수정 적용.
- **확인**: 빌드/vet 통과.
```

### 5-2. 작업 기록 폴더 (사용자 고정 지침)

계획을 세우고 코드를 생성한 작업은 모두 다음 위치에 기록합니다.

```
https://github.com/qazx2675/myrepo/tree/master/.claude/<작업 이름을 한글로 딴 폴더>/
```

그 폴더 안에 이번 작업의 **계획서 / 요청 요약 / 변경 내용**을 markdown으로 남깁니다.

### 5-3. 문서 갱신 (빠뜨리기 쉬움)

| 바꾼 것 | 같이 갱신할 문서 |
|---|---|
| 옵션 추가/변경 | 도구 폴더 `README.md` 옵션표 + **인수인계 문서의 옵션표** |
| 동작 변경 | 도구 폴더 `README.md` + 인수인계 문서의 "주의사항과 한계" |
| 새 파일/폴더 추가 | 두 문서의 "파일 구조" + [40_폴더구조](./40_폴더구조.md) |
| 알려진 버그 해결 | 두 문서의 "알려진 한계" 항목을 해결됨으로 |

**문서를 고쳤으면 HTML을 재생성합니다.**

```bash
cd .claude/VM/인수인계
```

## 6. AI에게 요청할 때 자주 하는 실수

| 실수 | 결과 | 대신 이렇게 |
|---|---|---|
| "vm-param-check 고쳐줘"라고만 함 | 저장소에 같은 이름이 **여러 벌**(V2, V1, integrated, vm-param-setting-check) 있어 엉뚱한 걸 고침 | 전체 경로(`.claude/VM/V2/...`)를 정확히 적기 |
| 제약을 안 적음 | 안전장치가 사라지거나 vendor/가 갱신됨 | "제약/유지할 것"을 반드시 채우기 |
| 여러 요청을 한꺼번에 | 무엇이 무엇 때문에 깨졌는지 추적 불가 | **한 번에 하나씩** |
| 완료 기준을 안 적음 | 빌드도 안 되는 코드를 "완료"로 받음 | 빌드/테스트/문서 갱신을 명시 |
| diff를 안 봄 | 요청 외 변경이 섞여 들어감 | `git diff`는 반드시 사람이 확인 |
| 문서를 안 고침 | 다음 사람이 옛날 옵션표를 보고 헤맴 | 문서 갱신을 완료 기준에 포함 |

## 7. AI가 이 저장소에서 반드시 지켜야 할 규칙 (요약)

요청서에 매번 다 쓰기 번거로우면 **이 절을 통째로 복사해서 붙여넣으세요.**

```
[이 저장소 공통 규칙]
1. 새 외부 의존성을 추가하지 말 것. vendor/ 기반 오프라인 빌드가 반드시 유지되어야 함.
   불가피하면 먼저 알리고 승인받을 것.
2. 비밀번호는 환경변수로만 받는다. 플래그나 파일로 받도록 바꾸지 말 것.
3. 실제 설정을 바꾸기 직전의 확인 프롬프트를 제거하거나 우회 가능하게 만들지 말 것.
4. 안전 게이트(그룹 동질성, 전원 OFF 확인, 인시던트·롤백, Ctrl+C 3회)를 제거하지 말 것.
5. 기존 옵션의 이름·기본값·미지정 시 동작(스킵 등)을 바꾸지 말 것.
6. 종료 코드 규약을 바꾸지 말 것.
7. 요청한 파일 외에는 건드리지 말 것. 필요하면 먼저 알릴 것.
8. 작업 후 CHANGELOG.md 를 갱신하고, README.md 와 .claude/VM/인수인계/ 의
   해당 문서(옵션표·한계)를 함께 갱신할 것.
9. bash setup.sh(오프라인 빌드) / go vet 통과와 대상 폴더 PR_CHECKLIST.md 확인을 최소 기준으로 할 것.
10. 현행 VM 생성·점검 코드는 .claude/VM/V2/ 아래다. V1 폴더(VM_setup, vm-param-check-usability-improvement)를
    고치지 말 것 (power_setting 바이너리는 삭제·이동 금지).
```

## 8. 참고: 원 작성자 환경의 자동화 스킬

원 작성자는 AI 도구에 **스킬(Skill)** 두 개를 등록해서 이 절차를 자동화하고 있었습니다.

| 스킬 | 역할 |
|---|---|
| `maint-request-sk` | 수정 요청이 들어오면 자동으로 위 양식으로 구조화하고, 완료 후 CHANGELOG 기록까지 처리 |
| `git-upload-sk` | 폐쇄망에서 다운로드→빌드가 가능한 상태로 폴더를 구성하고 설명을 남기는 기준 |

인수받는 팀의 AI 환경에 이런 스킬이 없어도 됩니다 — **이 문서와 [31번 양식](./31_변경요청서_양식.md)이 같은 내용을 담고 있으므로, 양식을 복사해서 쓰면 동일한 결과가 나옵니다.**
