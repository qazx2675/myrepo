# 00. 시작하기 — 인수자가 첫날 알아야 할 것

## 1. 이 도구들은 왜 존재하나

회사에는 **수백 대 규모의 물리 서버(BM, Bare Metal)** 가 있고, 그 위에 VMware ESXi가 깔려 있으며, 각 물리 서버마다 가상 머신(VM)이 1~3대씩 올라가 있습니다. 이 VM들은 CAE(해석/시뮬레이션) 같은 고성능 작업을 돌리기 때문에, **성능에 직결되는 설정값들이 정확히 맞아야 합니다.**

문제는 이겁니다.

- 서버가 500대면 VM은 1,000~1,500대입니다. **vSphere Client(웹 UI)로 하나씩 확인·설정하는 건 현실적으로 불가능합니다.**
- 설정이 하나만 틀려도 성능이 크게 떨어지는데, 눈으로는 티가 안 납니다.
- 신규 서버 도입, 네트워크 이관, 라이선스 갱신 같은 작업이 주기적으로 생깁니다.

그래서 **"vCenter에 API로 접속해서 대량으로 조회하고 설정하는 CLI 도구들"** 을 Go 언어로 만들어 쓰고 있습니다. 그게 이 저장소입니다.

## 2. 전체 그림

```
   [작업자 PC / Rocky Linux 서버]
              │
              │  이 저장소의 Go 도구를 실행
              │  (vCenter API, HTTPS 443)
              ▼
        ┌───────────┐
        │  vCenter  │  ← 여러 ESXi 호스트를 한꺼번에 관리하는 관리 서버
        └───────────┘
              │
      ┌───────┼───────┐
      ▼       ▼       ▼
   [ESXi]  [ESXi]  [ESXi]     ← 물리 서버(BM) 한 대 = ESXi 한 대
     │        │       │
   ev01     ev01    ev01      ← 그 위에 올라간 VM들
   ev02     ev02    ev02
```

- **작업자는 vCenter에만 접속합니다.** 개별 ESXi나 VM에 SSH로 들어가지 않습니다 (예외: `esxi-log-check`는 ESXi에 직접 접속해 로그를 읽습니다).
- 도구들은 전부 **vCenter API(govmomi 라이브러리)** 를 씁니다.
- VM 이름 규칙은 `<물리서버이름>ev01`, `<물리서버이름>ev02` 입니다. 이 규칙을 도구들이 전제로 깔고 있습니다.

## 3. 도구를 성격별로 나누면

| 성격 | 도구 | 인프라를 바꾸나 |
|---|---|---|
| **점검** | `vm-param-check`(체크 모드), `vm_verifier`, `esxi-log-check`, `vm-param-setting-check` | 아니오 |
| **계산** | `lpage_search` | 아니오 (접속조차 안 함) |
| **설정 변경** | `vm-param-check -fix`, `VM_setup/*`, `vm-setting-go-lang/*`, `vm-network-migration` | **예** |
| **테스트 환경** | `vcenter-test-env-vcsim`, `integrated-vm-param-check-test-tool`, `gemini_vcsim-pipeline-test` | 아니오 (가짜 vCenter 위에서만) |
| **설치 지원** | `powershell` | 작업 PC만 |

> **가장 중요한 구분: 🔴 표시가 붙은 도구는 실제로 운영 중인 인프라의 설정을 바꿉니다.**
> 이 문서들에서 🔴를 보면, "실행 전에 dry-run으로 먼저 확인했는가"를 반드시 자문하세요.

## 4. 첫날에 할 일 (30분 코스)

실제 인프라를 전혀 건드리지 않고 감을 잡는 순서입니다.

```bash
# 1) 저장소 받기 (인터넷 되는 곳에서 딱 한 번)
git clone https://github.com/qazx2675/myrepo.git
cd myrepo/.claude/VM

# 2) 가장 간단한 도구를 빌드해본다 (외부 의존성 없음, 30초)
cd lpage_search
bash setup.sh
./lpage_search -h esxi01 -v1 240 -hm 512
#   → 계산 결과가 표로 나오면 Go 빌드 환경이 정상이라는 뜻

# 3) 주력 도구를 빌드하고, vCenter 없이 데모 모드로 돌려본다
cd ../vm-param-check-usability-improvement/vm-param-check
bash setup.sh
./vm-param-check -demo
#   → 가짜 VM 3대에 대한 점검 결과가 색깔로 출력됨. 아무것도 안 바뀜
```

여기까지 되면 **빌드 환경은 끝난 것**입니다. Go가 없다는 오류가 나면 [02_공통_실행환경](./02_공통_실행환경.md)의 "Go 설치"를 보세요.

## 5. 둘째 날 이후 (실제 vCenter 붙이기)

1. **읽기 전용 계정**으로 시작하세요. `vm-param-check`를 체크 모드(`-fix` 없이)로만 돌리면 조회 권한만 있으면 됩니다.
2. 대상 VM을 **2대만** 적은 목록 파일로 시작하세요. 전체 인벤토리를 대상으로 첫 실행하지 마세요.
3. 결과 CSV를 vSphere Client 화면과 직접 대조해보세요. 도구를 믿기 전에 도구가 맞는지 확인하는 과정입니다.
4. 그 다음에야 `-fix`(설정 변경)를 검토하세요.

## 6. 반드시 지켜야 할 것 3가지

### (1) 설정을 바꿨으면 눈으로 확인한다

모든 도구의 README에 같은 경고가 붙어 있습니다.

> 본 스크립트/툴은 100% 신뢰하기보다 **참고용(보조 도구)** 으로 사용하는 것을 권장합니다.
> 설정 변경 후에는 **랜덤한 서버 몇 대를 골라 vSphere Client에서 직접 확인**하는 절차가 반드시 필요합니다.

도구가 "성공"이라고 출력해도, 실제로 반영됐는지는 사람이 표본 확인해야 합니다.

### (2) 비밀번호는 절대 명령행에 쓰지 않는다

전부 **환경변수**로 넘깁니다. 명령행에 쓰면 셸 히스토리(`~/.bash_history`)와 프로세스 목록(`ps`)에 그대로 남습니다.

```bash
read -rsp 'vCenter 비밀번호: ' VC_PASSWORD; export VC_PASSWORD; echo
```

도구마다 환경변수 이름이 조금 다릅니다 — [02_공통_실행환경](./02_공통_실행환경.md)의 표를 참고하세요.

### (3) 폐쇄망 빌드 성질을 깨지 않는다

모든 Go 프로젝트는 `vendor/` 폴더에 의존성을 통째로 넣어두었습니다. 그래서 **인터넷이 없는 서버에서도 폴더만 복사하면 빌드가 됩니다.** 코드를 수정할 때 새 외부 라이브러리를 추가하면 이 성질이 깨집니다. 하지 마세요. (자세한 이유와 예외 처리는 [30_유지보수_AI_활용가이드](./30_유지보수_AI_활용가이드.md) 참고)
