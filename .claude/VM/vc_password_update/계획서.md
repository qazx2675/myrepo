# vc_password_update (vCenter 비밀번호 갱신 도구) 프로젝트 계획서

## 목표 및 범위

- vCenter 비밀번호는 만료일이 되면 반드시 값을 "변경"해야 하며, 만료일 자체를 늘리는 기능은 없다. 그런데 실제 비밀번호 값을 바꾸고 싶지 않은 경우(외부 연동 시스템, 자동화 스크립트가 그 계정을 참조하는 경우 등)가 있어, **기존과 동일한 비밀번호로 "재설정"해서 만료 타이머만 리셋**하는 것이 목표다.
- 대상은 여러 개의 vCenter(사내 여러 랩/사이트) 각각에 존재하는 동일한 이름의 계정(기본값 `lscsystems@vsphere.local`)이다.
- 로그인은 각 vCenter의 **`Administrator@vsphere.local` 계정으로만** 한다(확정). 이 admin 계정 자신은 비밀번호를 변경하지 않고, admin 권한으로 대상 계정(`lscsystems@vsphere.local`)의 비밀번호를 old password 없이 강제 재설정한다.
- **범위 포함**: Go CLI 바이너리(`vc_password_update`), 여러 vCenter 순회 처리, 실행 결과 요약 출력, crontab 등록 가이드, **폐쇄망에서도 통째로 다운로드해 빌드 가능한 상태로 git 업로드**.
- **범위 제외**: 비밀번호 값 자체를 생성/변경하는 기능(이건 기존 `passwd_update.sh`가 담당), 비밀번호 정책/복잡도 검증, GUI.

## 확정된 설계

1. **로그인 계정**: `Administrator@vsphere.local` 고정. 비밀번호는 암호화 파일이 아니라 **환경변수 `ADMIN_PASSWORD`**로 입력받는다.
   - crontab에 등록할 때는 크론 환경엔 대화형 셸의 환경변수가 없으므로, `cron_wrapper.sh`가 `admin_password.secret` 파일(권한 600)에서 읽어 export 한다 — crontab 라인 자체에 비밀번호를 적지 않는다.
2. **`-dir`의 의미**: `secret_lib.sh`가 쓰는 `secret/` 폴더 전체(= `key` 파일 + `vcenter_<계정>.enc` 파일들)를 가리킨다.
   - `-dir "secret_lib.sh 로 만든 secret/ 폴더 경로"` 를 그대로 넘긴다. 예: 기존 `passwd_update.sh` 로 `lscsystems@vsphere.local` 비밀번호를 저장해 둔 그 `secret/` 폴더(예: `/home/V2/secret`)를 `-dir` 값으로 지정.
   - Go 쪽은 `secret_lib.sh`의 `secret_file()` 규칙을 그대로 따라, `-id`(기본값 `lscsystems@vsphere.local`)를 받아 파일 경로를 `<dir>/vcenter_<id의 '/'를 '_'로 치환>.enc` 로 계산하고, `<dir>/key` 로 복호화한다.
   - 실행 예시: `./vc_password_update -dir /home/V2/secret -vc /home/V2/vcenter.txt` (환경변수 `ADMIN_PASSWORD` 는 실행 전에 export 하거나 crontab 라인에 포함).
   - **admin 계정(`Administrator@vsphere.local`) 비밀번호는 이 `secret/` 폴더에 저장하지 않는다** — 로그인용으로만 쓰이므로 `.enc` 파일로 보관하지 않고 환경변수로만 받는다.

## 주요 기능

1. **admin 로그인**: `Administrator@vsphere.local` + 환경변수 `ADMIN_PASSWORD` 로 각 vCenter에 govmomi 세션 로그인
2. **대상 계정 암호 복호화**: `-dir` 폴더에서 `secret_lib.sh`와 같은 방식(`openssl aes-256-cbc -md sha256 -a`, `key` 파일)으로 대상 계정(`-id`)의 현재 비밀번호를 복호화
3. **vCenter 목록 순회**: `-vc`로 지정된 `vcenter.txt`(한 줄에 vCenter IP 하나, `#` 주석 지원)의 각 vCenter를 순회
4. **admin 권한 비밀번호 재설정**: 각 vCenter에서 대상 계정의 비밀번호를 복호화한 값과 동일하게 admin 권한으로 강제 재설정 (`govmomi/ssoadmin` 의 `ResetPersonPassword`)
5. **결과 요약 출력**: vCenter별 성공/실패를 한눈에 볼 수 있게 출력
6. **crontab 등록**: 85일 주기 실행 등록 가이드 + `cron_wrapper.sh`
7. **실행 로그 기록**: 크론 실행 결과를 나중에 확인 가능하게 파일로 남김

## 단계별 마일스톤 (진행 결과)

1. **ssoadmin 재설정 방식 PoC** — ✅ 완료. 랩 vCenter(192.168.0.50)에서 `Administrator@vsphere.local` 로그인 → `ResetPersonPassword` 로 대상 계정 비밀번호를 old password 없이 강제 재설정 → **같은 값으로 연속 두 번 재설정해도 둘 다 성공**함을 확인(비밀번호 이력 정책 `ProhibitedPreviousPasswordsCount=5` 우회됨). 핵심 가정이 유효함을 실측으로 검증.
2. **govmomi ssoadmin 패키지 vendoring** — ✅ 완료. `.claude/공통/govendor/govmomi-0.55.1-vc-password-update` 신규 생성(`ssoadmin`/`sts` 패키지 포함, 다른 프로젝트의 govmomi vendor 사본과 분리 관리).
3. **`vc_password_update` CLI 완성** — ✅ 완료. `-dir`, `-vc`, `-id`, `-adminId`, `-timeout` 플래그, 여러 vCenter 순회(한 vCenter 실패해도 계속 진행), per-host 타임아웃(응답 없는 vCenter가 전체를 막지 않음), 결과 요약.
4. **crontab 등록 + wrapper 스크립트 + 로그 정착** — ✅ 완료. `cron_wrapper.sh`가 85일 경과를 직접 계산(`.last_success` 스탬프 파일)해서 cron의 day-of-month 한계를 우회, admin 비밀번호는 `admin_password.secret` 파일에서 비대화형으로 로딩.
5. **폐쇄망 오프라인 빌드/배포 패키징** — ✅ 완료. `setup.sh`가 공유 govendor를 `vendor/`로 심볼릭 링크해 `GOPROXY=off` 빌드, README에 빌드/사용/옵션/문서 순서로 전 과정 기술, CI(`ci.yml`)가 같은 방식으로 빌드 확인.

## 기술 스택 / 아키텍처

- **언어**: Go — 기존 V2 도구들과 동일한 패턴, 공유 `govendor/`를 vendor로 링크해서 오프라인 빌드.
- **vCenter 연동**: `govmomi` 세션 로그인은 기존 도구들과 동일, 비밀번호 강제 재설정은 `govmomi/ssoadmin` 패키지의 `ResetPersonPassword` 사용 — SSO Admin API 는 STS 토큰(`govmomi/sts`) 기반 별도 로그인이 필요(vim25 세션 쿠키로는 인증 안 됨, govmomi `cli/sso` 참고해서 구현).
- **admin 비밀번호 입력**: 환경변수 `ADMIN_PASSWORD` (필수, 없으면 즉시 에러 종료).
- **대상 계정 비밀번호 저장/복호화**: Go에서 `openssl` 을 shell-out 으로 호출해 `secret_lib.sh`와 완전히 같은 파라미터(`-aes-256-cbc -md sha256 -a`, `key` 파일)로 복호화. `-dir`은 `secret/` 폴더 전체를 가리키고, 파일명은 `secret_file()` 규칙을 그대로 따른다.
- **vCenter 목록**: `vcenter.txt`, 기존 `vcenter.txt.example` 포맷(IP 한 줄, `#` 주석) 그대로 재사용.
- **동시성**: 순차 처리(vCenter 개수가 많지 않을 것으로 예상). 대신 per-host `-timeout`으로 개별 vCenter가 전체를 막지 않게 함.
- **크론 등록**: cron 표현식으로는 "정확히 85일마다"를 표현할 수 없어, 매일 실행 + `.last_success` 스탬프 파일 비교 방식(`cron_wrapper.sh`)으로 구현. 일부 vCenter만 실패하면 기준일을 갱신하지 않아 다음날 재시도.
- **폐쇄망 빌드/git 업로드**: 기존 저장소 컨벤션([[feedback_git_upload_docs_standard]] 메모 기준)을 그대로 따름 — vendor 커밋, `setup.sh` 오프라인 빌드, README 빌드→사용→옵션→문서 순서, disclaimer, CI, `ARCHITECTURE.md`/`PR_CHECKLIST.md`/`CHANGELOG.md`/`WORKFLOW.md`+`workflow.svg`.

## 리스크 및 제약사항 (검증 결과 반영)

- **"동일 비밀번호로 재설정 = 만료일 리셋" 가정** — ✅ 검증 완료. admin 강제 재설정은 비밀번호 이력 정책을 우회하므로 같은 값으로도 성공한다.
- **crontab의 `*/85` 필드 한계** — 해결: 매일 실행 + `.last_success` 스탬프 파일 비교(`cron_wrapper.sh`).
- **`ADMIN_PASSWORD`가 crontab 라인에 평문으로 노출** — 해결: `admin_password.secret` 파일(600, root 소유)에서 읽도록 분리, crontab 라인에는 경로만 남음.
- **ssoadmin API 미vendoring 및 OS6 빌드 호환성** — vendoring은 완료(랩의 Rocky 8, go1.26.5 환경에서 빌드/실행 검증 완료). **OS6 빌드 호환성은 아직 검증하지 못했다** — 필요 시 `build_os6.sh` 패턴을 참고해 별도 검증 필요(이번 범위에서는 요구되지 않아 보류).
- **여러 vCenter 중 일부 실패 시 처리** — 구현: 한 vCenter 실패해도 나머지는 계속 처리, 실패 목록은 표준 출력/로그에 남음. 이메일 등 알림 연동은 이번 범위에 포함하지 않음(README "알려진 한계"에 확장 여지로 기록).
- **(신규 발견) STS 토큰은 시계에 민감함** — 랩 검증 중 vCenter 시계가 실제보다 약 44분 느려 `MessageExpired` 오류가 발생했다. 이 도구를 실행하는 서버와 각 vCenter의 NTP 동기화 여부를 운영 전 확인해야 한다(README "알려진 한계"/PR_CHECKLIST 에 반영).
