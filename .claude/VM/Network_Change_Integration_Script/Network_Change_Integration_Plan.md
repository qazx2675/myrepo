# 통합 VM 네트워크 및 HPC 망변경 스크립트 구축 계획서 (v2)

> v1(`Network_Change_Integration_Plan.md`) 을 기존 3개 프로젝트 코드와 대조 검토한 뒤,
> 확인된 사항을 반영해 다시 쓴 것입니다. **구현은 이 문서를 기준으로 합니다.**
>
> v1 대비 바뀐 곳은 각 절 머리에 `[v1 수정]` / `[신규]` 로 표시했습니다.

## 1. 프로젝트 개요 및 통합 목적

기존 개별 운영되던 3개 프로젝트를 단일 스크립트로 통합하여 VM 망변경 프로세스를
자동화하고 안정성을 확보합니다.

### 1.1 통합 대상 프로젝트

| # | 프로젝트 | 경로 | 검증 상태 |
|---|---|---|---|
| 1 | `ip_change` | `.claude/HPC/ip_change` | **미검증** |
| 2 | `ldap_setting` | `.claude/HPC/ldap_setting` | 검증 완료 |
| 3 | `vm-network-migration` | `.claude/VM/vm-network-migration` | 검증 완료 |

### 1.2 핵심 통합 원칙 `[v1 수정]`

- **독립성 유지**: 기존 개별 프로젝트에는 원칙적으로 영향이 없어야 하며, 수정이
  필요한 사항은 통합 프로젝트 내에서 독립적으로 수정·적용합니다.
- **독립성 원칙의 예외**: 아래 한 가지는 **원본 `HPC/ldap_setting` 에도 함께
  반영**합니다. 통합본과 원본의 자산현황 조회 동작이 갈리면 두 코드가 서로
  다른 대상을 고르게 되어 추적이 불가능해지기 때문입니다.
  - 자산현황 중복 처리 · `default_site` · `ev01~03` 접미사 fallback (→ §11)
- **프로세스 단일화**: 망변경 절차를 한 번의 스크립트 실행으로 순차 처리합니다.

## 2. 저장소 구조 및 환경 설정 관리

### 2.1 디렉터리

```
VM/Network_Change_Integration_Script/
├── change.sh                  # 사용자 진입점 (bash 래퍼)
├── integration.conf           # 중앙 설정 (단일 편집 지점)
├── conf/
│   └── *.sample
├── bin/                       # 빌드 산출물
├── logs/                      # 실행 로그
├── incidents/                 # 인시던트별 상태·백업 인덱스
└── work/                      # 전처리 결과 등 중간 산출물
```

### 2.2 conf 중앙화 방식 `[v1 확정]`

**중앙 `integration.conf` → 실행 직전 각 프로젝트의 `conf/*.conf` 로 렌더링**합니다.
운영자는 `integration.conf` 한 파일만 편집하며, 원본 프로젝트 코드는 한 줄도
고치지 않습니다.

추가되는 주요 키:

| 키 | 설명 |
|---|---|
| `bm_domain` | BM 호스트에 붙일 도메인. **기본값 `seccae.com`** |
| `result_dir` | 결과 목록 파일 출력 경로 (→ §6) |
| `default_site` | 자산현황에서 못 찾은 호스트에 적용할 site (→ §11) |
| `os6_hostgroup` | 6버전용 빌드로 실행해야 하는 **관리서버** hostname 목록(쉼표구분). 이 서버가 해당되면 실행 전체가 os6 경로 (→ §8.1) |
| `os6_bin_dir` / `os6_gossh` | OS 6 전용 바이너리 디렉토리·gossh 경로 |
| `bin_dir` / `gossh` | 일반 바이너리·gossh 경로 |

### 2.3 `user선택` 함수

`change.sh` 안에 함수 틀만 만들고 내부는 비워 둡니다 (사용자가 직접 작성).
**통합 스크립트 한 곳에서만 선택하고**, 결과를 `{user}` 변수로 하위 단계에
전달합니다. 각 프로젝트 래퍼의 빈 선택 함수는 호출하지 않습니다.

## 3. 입력 파일 양식 및 데이터 규격

### 3.1 파일별 규격 `[v1 확정]`

| 파일 | 내용 | 1열의 실체 |
|---|---|---|
| `{user}.txt` | `VM이름 변경될_IP` | **VM 이름. 도메인 없음** |
| `vswitch_${user}.txt` | `BM호스트 포트그룹명 VLAN` | **BM 호스트. 도메인 필수** |

### 3.2 이름 규약 (확정)

- `{user}.txt` 의 1열은 **도메인 없는 VM 이름**이며, 이것이 곧
  - vCenter 인벤토리의 VM 표시이름이고,
  - `ip_change` / `ldap_setting` 이 gossh 로 SSH 접속하는 대상입니다.
  - → **DNS 가 짧은 이름을 해석해야 한다**는 전제가 성립해야 합니다.
- `vswitch_${user}.txt` 의 1열 BM 호스트는 **항상 `.seccae.com` 이 붙습니다.**

### 3.3 반드시 고쳐야 할 것 `[신규 — v1 누락]`

`vm-network-migration` 의 `internal/config.LoadVMList` 는 **줄 전체를 VM 이름으로
사용**합니다 (`strings.Fields(line)[0]` 이 아님).

`{user}.txt` 가 `VM이름 변경될_IP` 2열이므로, **지금 그대로 통합하면 포트그룹
대상이 전부 실패**합니다. 통합 프로젝트의 사본에서 **1열만 취하도록** 수정합니다.

### 3.4 인코딩

- UTF-8 BOM 은 `vm-network-migration` 의 `LoadLines` 에 **이미 처리되어 있습니다.**
  통합에서 새로 만들지 않습니다.
- CSV(쉼표 구분) 입력은 전처리 단계에서 공백 구분으로 변환합니다.

## 4. 전처리(Pre-processing) 데이터 변환 로직

`change.sh` 실행 시 가장 먼저 `vswitch_${user}.txt` 를 검증·표준화합니다.
**출력은 `vm-network-migration` 의 `LoadWorklist` 가 요구하는 정확히 3열**이어야 합니다.

### 4.1 케이스별 변환 규칙 `[v1 수정]`

`BM호스트.domain` 이 이미 포함된 줄은 변환하지 않고 그대로 둡니다(멱등).

**1번 케이스 — 4열 `BM호스트 폴더명 IP VLAN`**
```
변환:  BM호스트.seccae.com  폴더명-<문자열>-<IP 앞3옥텟을 '-' 로 연결>-0  VLAN
예시:  hostname asdf 3.1.3.12 12
  →    hostname.seccae.com  asdf-cae-3-1-3-0  12
```
- `<문자열>` 은 실행 시 사용자 입력값, **기본값 `cae`**
- **`-0` 은 4번째 옥텟 자리이며 항상 `0` 으로 고정**합니다
  (v1 의 "3옥텟-0" 표현이 모호했던 부분 — 예시가 정답)

**2번 케이스 — 3열 `BM호스트 IP VLAN`**
- 폴더명을 사용자에게 **추가 입력**받은 뒤 1번과 동일하게 변환

**3번 케이스 — 그 외**
- 변환하지 않고 원본 유지
- **판정 기준을 명시할 것**: 열 개수가 3·4가 아니거나, 3열인데 2번째 필드가
  IP 형식이 아니면 3번 케이스로 본다.

## 5. 작업 수행 워크플로우 및 인시던트 관리

### 5.1 실행 절차

1. **사전 준비** — `{user}.txt`, `vswitch_${user}.txt` 작성 후 `bash change.sh`
2. **전처리** — `vswitch_${user}.txt` 양식 검증·표준화 (§4)
3. **1차 작업** — `{user}.txt` 대상 VM 에 IP 변경 → LDAP 변경 순차 실행
4. **결과 리다이렉션** — 성공/실패 목록 기록 (§6)
5. **2차 작업 질의** — Portgroup 작업 진행 여부 확인

### 5.2 작업 순서에 대한 전제 `[신규 — 반드시 명시]`

IP 변경 직후 대상 VM 은 **"새 IP 설정 + 옛 VLAN"** 상태가 됩니다. 이는 **의도된
설계**이며 다음 전제 위에서만 안전합니다.

> `ip_change` 는 네트워크 서비스를 재시작하지 않으므로(원본 ARCHITECTURE 규칙 4)
> **리부팅 전까지 옛 IP 로 통신이 유지**되고, 포트그룹 변경 후 리부팅/재적용
> 시점에 새 IP 가 활성화된다.

이 전제가 깨지면(누군가 중간에 네트워크를 재시작하거나 VM 을 리부팅하면)
해당 VM 은 콘솔 외 접근이 불가능해집니다. 운영 안내에 반드시 포함하십시오.

### 5.3 인시던트 관리 및 재개

- **보류(`N`/`n`)**: 인시던트 이름을 입력받아 진행 상태·이력을 `incidents/` 에 저장
- **재개**: 다음 실행 시 이력이 있으면 이어서 진행할지 질의
- **독립 실행**: `bash change.sh port` — 인시던트 이름을 직접 입력해 2차 작업만 수행
- **재개 시 접속 IP**: 상태 파일에 "이 VM 에 접속할 때 쓸 IP(옛/새)" 를 반드시
  기록합니다. 기록이 없으면 재개 시 어느 IP 로 붙어야 할지 알 수 없습니다.

### 5.4 서브커맨드 체계

```
change.sh                    전체 흐름 (전처리 → IP/LDAP → 질의 → 포트그룹)
change.sh port               2차(포트그룹)만, 인시던트 지정
change.sh rollback <name>    인시던트 역순 원복 (§7)
change.sh --retry ip         IP 실패 목록만 재시도
change.sh --retry ldap       LDAP 실패 목록만 재시도
```

## 6. 결과 리다이렉션 `[신규]`

IP·LDAP 변경 후, 결과를 `integration.conf` 의 `result_dir` 에 목록 파일로 남깁니다.

| 파일 | 내용 | 용도 |
|---|---|---|
| `on_off_${user}.txt` | **IP·LDAP 둘 다 성공**한 VM 이름 | **별도 전원 on/off 작업 스크립트의 입력** |
| `ip_ok_${user}.txt` | IP 변경 성공 | 단계별 추적 |
| `ldap_ok_${user}.txt` | LDAP 변경 성공 | 단계별 추적 |
| `on_off_${user}.failed.txt` | 실패 VM 이름만 | 재시도 입력 |
| `failed_${user}.txt` | `VM이름 <에러코드>` | 진단 (복사 불가 환경 대응) |

**규칙**
- 기존 파일이 있으면 `.bak.<시점>` 으로 백업한 뒤 새로 씁니다.
  → 내용이 항상 "직전 실행 기준"으로 명확해집니다.
- `on_off_${user}.txt` 는 **포트그룹(2차) 작업의 입력이 아닙니다.** 전원 작업
  스크립트가 있는 곳에서 쓰기 위한 별도 산출물입니다.
- 부분 실패(IP·LDAP 중 하나만 실패)는 `--retry ip` / `--retry ldap` 으로
  해당 단계만 재시작할 수 있어야 합니다.

> **확인 필요**: `on_off_${user}.txt` 를 "둘 다 성공" 기준으로 정의했습니다.
> 전원 작업은 IP·LDAP 이 모두 끝난 대상에만 하는 것이 안전하다는 판단입니다.
> 다른 기준이 필요하면 알려주십시오.

## 7. 백업 및 롤백 `[v1 보강]`

### 7.1 백업 — 새로 만들지 않습니다

세 프로젝트가 **이미 각자의 백업 메커니즘을 갖고 있습니다.**

| 프로젝트 | 백업 형태 |
|---|---|
| `ip_change` | `ifcfg` 파일의 `.bak.<STAMP>` |
| `ldap_setting` | 설정 파일별 `.bak.<STAMP>` + 전용 `rollback` 서브커맨드 |
| `vm-network-migration` | `state_{user}.json` + `nm-rollback` |

통합 스크립트는 **자체 백업을 만들지 않고**, 세 백업의 위치·시점을
인시던트 디렉터리에 **인덱싱만** 합니다.

> ⚠️ `ldap_setting` 은 *"백업은 한 실행에서 파일당 한 번만"* 이 전제입니다
> (원본 ARCHITECTURE 규칙 7). 통합이 추가로 백업을 뜨면 백업이 "이미 일부
> 수정된 상태"가 되어 **롤백해도 원본으로 돌아가지 않습니다.** 실제 버그 이력이 있습니다.

### 7.2 롤백

```
change.sh rollback <incident>
```
인시던트에 기록된 백업 인덱스를 읽어 **역순**(포트그룹 → LDAP → IP)으로
각 프로젝트의 롤백 명령을 호출합니다. 세 단계 모두 자동입니다:

- 포트그룹 — `nm run.sh --rollback`
- LDAP — `ldap-config-engine -rollback`
- IP — `ip-change-engine -rollback` (각 노드의 최근 `<ifcfg>.bak.<STAMP>` 복원)
  `[2026-09-11 추가]` 이전엔 수동 안내만 했으나 ip_change 에 `-rollback` 을 추가해 자동화.
  엔진 실행 실패 시에만 대상 목록 출력 + 수동 복원 안내.

## 8. OS 분기 및 지연 VM 처리

### 8.1 OS 6 바이너리 분기 `[2026-09-11 재정의]`

판정 기준은 **작업 대상 VM 이 아니라, 이 `change.sh` 를 실행하는 관리서버의 OS**
입니다. 대상 노드에는 Go 바이너리가 올라가지 않고(base64 bash 주입) gossh·엔진은
관리서버에서만 돕니다. 관리서버가 RHEL 6/8 두 대이고, RHEL 6 에서 실행할 때만
커널/glibc 제약으로 6버전용 빌드가 필요합니다.

- `conf` 의 `os6_hostgroup` = **쉼표구분 관리서버 hostname 목록 문자열** (파일 아님)
- 이 서버의 hostname(short/FQDN)이 목록에 있으면 **이번 실행 전체**가
  `os6_gossh` / `os6_bin_dir`(기본 `./bin_os6` 사전빌드) 사용
- 없으면 일반 경로 (RHEL 8 관리서버 = 기존 동작 그대로)
- per-target 분할·gossh 2회 호출은 폐기 (한 실행은 항상 한 관리서버에서 돎)
- `[2026-09-11 추가]` 포트그룹(E 단계)도 대상: `bin_os6/nm-*` 를 `projects/
  vm-network-migration/build_os6.sh` 로 빌드해 커밋. `run.sh` 는 `NM_BIN_DIR`
  환경변수로 바이너리 경로를 바꿀 수 있고, `_nm_bin_dir` 이 관리서버가 os6 일 때
  자동으로 넘겨줌. vendor 한 govmomi 가 Go 1.21+ 표준 라이브러리를 써서
  go.mod 만 낮추는 걸론 부족 — vendor 안 3곳만 Go 1.20 호환 코드로 치환한 임시
  사본에서 빌드(원본 vendor/ 는 그대로).

### 8.2 지연·고부하 VM 타임아웃 `[v1 수정]`

**문제 배경**: 1개 VM 이 CPU/메모리를 과점유하면 다른 VM 작업이 심각하게 지연됩니다.
장애조치(Failover) 후 진행하는 방식이 아니므로, Ping 은 되는데 응답만 느린 VM 은
시간이 걸리더라도 끝까지 완수되어야 합니다.

**단, `gossh -t` 는 전역 타임아웃입니다.** 이 값을 크게 두면 *진짜 죽은 노드*에서도
같은 시간만큼 매답립니다. 따라서 **2패스**로 처리합니다.

1. **1차** — 표준 타임아웃으로 전체 실행
2. 타임아웃/실패한 호스트에 대해 **ping 선검사**
3. **2차** — `ping OK` 인 호스트만 추려 **긴 타임아웃**으로 재실행
4. `ping` 도 안 되는 호스트는 즉시 실패로 확정 (대기하지 않음)

## 9. vCenter 상위폴더 다중 대응 `[신규]`

### 9.1 증상

상위폴더가 2개 이상인 환경에서 작업 대상 VM 을 제대로 찾지 못하는 경우가 있었습니다.
(동명 VM 중복은 아니었음이 확인됨)

### 9.2 원인 분석

`internal/vsphere/session.go` 의 `CreateContainerView(root, ..., true)` 는 **재귀
조회**이므로 **폴더 깊이 자체는 원인이 아닙니다.** 색인은 전부 됩니다.

"찾을 수 없음" 경로는 5개이며, 어느 것이었는지에 따라 원인이 다릅니다.

| 코드 | 메시지 | 위치 | 원인 |
|---|---|---|---|
| E1 | `VM %q 를 어느 vCenter 에서도 찾을 수 없습니다` | `session.go` | `{user}.txt` VM 이름 불일치 |
| E2 | `여러 개 있습니다(이름으로 특정 불가)` | `session.go` | 동명 VM — **해당 없음** |
| E3 | `ESXi 호스트 %q 를 어느 vCenter 에서도 찾을 수 없습니다` | `cmd/pgcreate` | vswitch 1열 ≠ vCenter 등록 이름 |
| E4 | `VM 이 올라가 있는 ESXi 호스트를 찾을 수 없습니다` | `cmd/backup`, `cmd/verify` | `HostByRef` 실패 |
| **E5** | `BM 호스트 %q 에 대한 항목이 worklist 에 없습니다` | `internal/config` | **`host.Name` ≠ vswitch 1열 표기** |

**E5(또는 E3)가 가장 유력합니다.** `cmd/backup/main.go` 는
`TargetForHost(worklist, host.Name)` 으로 **vCenter 가 보고한 호스트 이름**과
vswitch 1열을 문자열 비교합니다. BM 은 항상 `.seccae.com` 이 붙는데, 한쪽 폴더의
ESXi 가 short name 으로 등록돼 있으면 **그 호스트에 올라간 VM 만 골라서 실패**합니다
— "상위폴더가 2개일 때 일부만 실패"라는 증상과 정확히 일치합니다.

### 9.3 대응 (원인이 무엇이든 유효)

1. **폴더 경로 색인** — 같은 `ContainerView` 에서 `Folder` 타입도 **함께** 조회해
   부모 체인을 메모리에서 조립합니다.
   → **vCenter 왕복 추가 0회**, 기존 `ConnectFleet` 병렬 구조 그대로 유지
   → **요구사항인 "이 부분은 무조건 병렬" 을 충족**합니다
2. **이름 정규화** — 호스트·VM 이름을 **FQDN / short 양쪽으로 색인**해
   `esxi01` 과 `esxi01.seccae.com` 이 같은 항목을 가리키게 합니다
3. **에러 메시지 보강** — 실패 시 **인벤토리 실제 경로 + 등록된 이름**을 함께 출력
4. **진단 모드** — `change.sh --debug-inventory` 로 vCenter 가 보고하는
   호스트/VM 이름과 폴더 경로를 덤프

> 3·4번은 원인 확정 전에 먼저 넣습니다. 다음에 재현되면 원인이 화면에 바로 뜹니다.

| 문자 | 단계 | 예 |

## 11. `ldap_setting` 자산현황 조회 변경 `[신규 · 원본에도 반영]`

**배경**: 자산현황에는 물리 호스트(BM)만 등재되어 있어 VM 이름으로는 조회되지
않을 수 있습니다. site 는 VM 이 올라간 BM 기준으로 판정하면 되므로, 조회 실패 시
가상화 인스턴스 접미사를 떼고 한 번 더 찾습니다.

### 11.1 조회 fallback 체인

```
1. VM 이름 정확 일치           (svr001ev01)
2. ev 접미사 제거 후 재검색     (svr001ev01 → svr001)
3. default_site 적용           (화면 경고 + -d1 로그에 목록)
4. 여전히 실패 → 실패 기록(D1)
```

### 11.2 확정 규칙

| 항목 | 확정값 |
|---|---|
| ev 위치 | **접미사, 구분자 없음** (`svr001ev01`) |
| ev 범위 | **`ev01` · `ev02` · `ev03` 3개 고정** |
| 다대일 매칭 | 여러 VM 이 같은 BM 항목을 참조해도 정상. **SSH 대상은 원래 VM 이름 유지** |
| 기본 site | `integration.conf` / `ldap_config.conf` 의 `default_site` 키 |

> ⚠️ **`Entry.Host` 는 반드시 원래 VM 이름(`svr001ev01`)으로 유지**해야 합니다.
> site 만 BM 항목에서 가져옵니다. 축약된 이름으로 SSH 하면 엉뚱한 장비에 붙습니다.

### 11.3 자산현황 중복 처리 — 동작 변경

현재 `internal/asset/asset.go` 는 같은 hostname 이 2번 나오면 **전체 실행을 에러로
중단**합니다. 이를 **마지막 줄 우선 + 경고 출력**으로 바꿉니다.
(자산현황은 사람이 이어 붙여 쓰는 파일이라 나중 줄이 최신 정보)

**함께 고쳐야 할 것**
- `internal/asset/asset_test.go` 의 `TestDuplicateHostRejected` — 마지막 줄 우선을
  검증하는 테스트로 교체
- `internal/config/config.go` — `default_site` 키 파싱 추가
- `conf/ldap_config.conf.sample` — `default_site` 설명 추가
- `CHANGELOG.md` — 항목 추가

### 11.4 `default_site` 검증 (필수)

`default_site` 는 자산현황에 없는 호스트에 **조용히** 적용되므로, 값이 틀렸으면
**한 대도 건드리기 전에** 멈춰야 합니다. 인프라 선택 직후 해당 infra 에 그 site
블록이 있는지 확인하고, 없으면 즉시 에러로 중단합니다.

> 원본 ARCHITECTURE 규칙 5 는 *"`-infra` 에 기본값을 두지 말라"* 입니다.
> `site` 는 `infra` 와 다른 축이라 직접 위반은 아니지만 **같은 종류의 위험**입니다.
> 기본값이 적용된 호스트는 화면에 크게 경고하고 `-d1` 로그에 목록을 남기십시오.

> **2026-09 갱신**: `-infra` 자체도 처음엔 `integration.conf` 의 `ldap_infra`
> 값을 조용히 재사용하도록 통합했었는데, 이는 규칙 5를 직접 위반하는 것이었다
> (이전 작업의 인프라가 그대로 남아 다음 실행에 조용히 적용될 수 있음).
> `change.sh --infra <이름>` (미지정 시 `ldap_config.conf` 의 infra 목록을
> 보여주는 대화형 선택, 비대화형은 오류)으로 교체하고 `ldap_infra` 를
> `integration.conf` 에서 제거했다. 선택된 인프라는 인시던트 메타(`meta` 의
> `ldap_infra`)에 저장해 롤백이 항상 원래 적용된 인프라로 정확히 되돌아가게
> 했다 (§11.5 의 `site` 누락 문제와 같은 종류의 함정을 피하기 위함).

### 11.5 롤백 경로 누락 주의

`runRollback` 은 `Entry.Host` 만 쓰고 `Site` 는 쓰지 않습니다. 그런데 롤백은
설정 파일을 읽지 않으므로 `default_site` 를 알 수 없습니다.

→ **`default_site` 로만 대상에 포함되던 호스트가 롤백에서만 빠지는 구멍**이
생깁니다. 롤백 모드에서는 자산현황에 없는 호스트도 목록에 그대로 남기십시오
(site 가 필요 없으므로 안전합니다).

## 11.6 타 부서 단독 이관을 위한 소스 자체 보관(vendoring) `[2026-09-10 추가]`

전체를 `projects/` 아래에 스냅샷 복사**해 자체 보관하도록 전환:

- `projects/ip_change`, `projects/ldap_setting`, `projects/vm-network-migration`

- `setup.sh` 의 `IP_DIR`/`LDAP_DIR`/`NM_DIR` 을 `../../HPC/...`, `../vm-network-migration`
  에서 `./projects/...` 로 변경.
- `integration.conf.sample` 의 `nm_dir` 기본값을 `../vm-network-migration`
  → `./projects/vm-network-migration` 로 변경. (`ldap_conf`/`ldap_assets`
  자체 보관은 §1.2/CHANGELOG 2026-09-10 항목에서 먼저 처리됨.)
- `change.sh`, `lib/incident.sh` 의 `conf_get nm_dir <기본값>` 도 동일하게 변경.

**트레이드오프(운영자가 알아야 할 것)**: `projects/` 는 원본의 **스냅샷**이라

## 12. `base64` / gossh 위험키워드 — 이미 해결됨

`gossh` 는 명령 문자열에 `reboot`/`poweroff`/`shutdown`/`halt`/`ddc` 같은 위험
키워드가 섞여 있으면(대소문자 무시, 부분일치) 실행을 거부합니다. base64 는 사실상
무작위 문자열이라 스크립트가 길어질수록 이런 조각이 우연히 섞일 확률이 올라갑니다.

**이 문제는 `ip_change` · `ldap_setting` 양쪽에 `spaceOut` 으로 이미 해결되어
있습니다.** base64 를 두 글자마다 공백으로 끊어 3글자 이상 이어진 조각 자체를
없애고, 원격에서 `tr -d ' '` 로 지웁니다.

> ✅ **통합 스크립트가 gossh 를 직접 호출하지 않고 항상 기존 Go 바이너리를
> 경유하면 이 문제를 새로 만들 일이 없습니다.**
> 통합 레벨에서 자체 gossh 호출이 생긴다면 **반드시 동일한 `spaceOut` 규칙을
> 복제**하십시오. 이 규칙을 어겨 두 번 연달아 재발한 이력이 있습니다.

또한 gossh 에 넘기는 명령줄에는 **따옴표를 절대 넣지 마십시오.** 대상 계정의
로그인 셸이 bash/csh/tcsh 중 무엇인지 알 수 없습니다. 항상 base64 로 감싸
`echo <b64> | tr -d ' ' | base64 -d | bash` 형태로 보냅니다.
