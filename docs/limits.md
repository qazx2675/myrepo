# AWX variables 크기 한도와 E2E 측정

대상: AWX v24.6.1, http://192.168.0.58:30080, 인벤토리 ID 5.
측정일: 2026-11-17. 업로더는 VM(RHEL, go 1.25 빌드), 다운로더는 윈도우 11에서 실행했다.

## 1. 인증 후 PATCH 한도 (실측)

`./awx_copy --measure-limits --measure-max-mib 8` 결과. 크기는 variables 값의 문자 수(base64)다.
측정 후 variables 는 원본(0자)으로 복원됐다.

| 128 KiB | 131,072 | 200 | 0.19 | 성공 |

| 512 KiB | 524,288 | 200 | 0.30 | 성공 |
| 1 MiB | 1,048,576 | 200 | 0.42 | 성공 |
| 2 MiB | 2,097,152 | 200 | 0.68 | 성공 |

- 한도는 nginx `client_max_body_size 5m` 이다. 요청 본문 전체(JSON 포장 포함)가 5 MiB 를 넘으면 413 이다.
  값 자체는 4.94 MiB 까지 들어간다.
- Django 쪽 한도(`DATA_UPLOAD_MAX_MEMORY_SIZE`)에는 걸리지 않았다.
- timeout 은 없었다. 가장 느린 PATCH 가 1.64초다.
- 저장 후 GET 값은 보낸 값과 같다. 단, AWX 는 저장할 때 variables 끝의 공백/줄바꿈을 제거한다. 내용과 탭은 그대로다.
  측정 코드(`measure.go`)는 이 끝 공백을 비교에서 제외하도록 고쳤다.

이전에 무인증 PATCH 로 잰 nginx 한도(5,242,880 bytes 까지 통과, 그 이상 413)와 같은 결과다.

## 2. chunk_size 기본값

- 기본값: **1,048,576 (1 MiB, base64 문자)**. 최대 성공 4.94 MiB 의 약 0.2배다.
- PATCH 본문 = 조각 + backup_b64(시작 전 variables 의 base64) + 약 1 KB.
  시작 전 variables 가 크면 chunk_size 를 줄인다. 본문 예상치가 5 MiB 를 넘으면 업로더가 경고한다.
- 1 MiB 조각 PATCH 는 0.42초다.

## 3. 실제 AWX E2E 결과

업로더: VM `bin/awx_copy_new`(최신 소스 빌드). 다운로더: 윈도우 `dist\awx_fetch.exe`. 두 쪽을 동시에 실행했다.
`test/e2e_send.sh` + `test/e2e_fetch.ps1` + `test/compare.ps1`. chunk_size 1,048,576.

| 파일 | 크기(bytes) | 조각 | 업로더 시간(초) | 다운로더 시간(초) | SHA-256 / 바이트 | 종료 후 variables |
|---|---:|---:|---:|---:|---|---|
| t00_empty.txt | 0 | 1 | 1.36 | 0.18 | PASS | 시작 전과 같음 |
| t01_one_byte.txt | 1 | 1 | 2.36 | 0.16 | PASS | 같음 |
| t02_edge_minus1.bin (조각-1) | 786,431 | 1 | 1.22 | 0.24 | PASS | 같음 |

| t04_edge_plus1.bin (조각+1) | 786,433 | 2 | 2.19 | 0.88 | PASS | 같음 |
| t05_chunk_x3.bin (조각x3) | 2,359,296 | 3 | 5.45 | 2.79 | PASS | 같음 |

11개 모두 SHA-256 과 바이트가 원본과 같았다. 종료 코드는 전부 0이다.
조각 경계 파일의 조각 수는 계산과 같다 (-1, 정확히 = 1개, +1 = 2개).

속도 (실측):

| 파일 | 시간 | 처리량 |
|---|---:|---:|
| 1 MiB (조각 2개) | 업로더 3.86초 / 다운로더 1.44초 | 약 0.3 MiB/s (업로더 기준) |
| 10 MiB (조각 14개) | 업로더 19.31초 / 다운로더 16.72초 | 약 0.5 MiB/s |

업로더 시간에는 시작 전 확인, 백업, 폴링 대기, 원복이 들어 있다. 파일이 작으면 이 고정 시간이 대부분이다.
10 MiB 는 조각마다 PATCH(약 0.4초) + ack 폴링 + 다운로더 처리가 끼므로 조각당 약 1.4초다.

주의: 파일 이름의 `:` 는 윈도우에서 `_` 로 바뀐다 (`t08_special_ #-'{}[] 한글.txt`). 내용은 같다.
`test/compare.ps1` 는 이 규칙을 알고 있다. 원본 폴더를 윈도우로 복사할 때도 `:` 를 `_` 로 바꿔야 한다.

## 4. 원본 variables 가 비어 있지 않을 때

variables 에 `foo: bar\nlist:\n  - x\nlast: end` (30자)를 넣고 다시 시험했다. 끝에 인벤토리를 빈 값으로 되돌렸다.

| 시험 | 결과 |
|---|---|
| t09_data.csv, t10_crlf_tabs.txt 전송·수신 | SHA-256 같음, 종료 후 variables 30자 원문 그대로 |
| 업로더 실행 중 Ctrl+C (SIGINT) | 업로더가 원복, 같음 |
| 업로더 `kill -9` 후 `./awx_copy --restore` | 블록의 backup_b64 에서 30자 복원, 같음 |

빈 variables(0자)에서도 같은 SIGINT, kill -9 + `--restore` 시험을 했고 통과했다.
`--restore` 를 블록이 없을 때 다시 실행하면 "복원할 것이 없습니다" 로 종료 코드 0 이다.

## 5. 안전성

테스트 전 `./awx_copy --snapshot > /tmp/before.txt`, 후 `/tmp/after.txt` 를 만들어 `diff` 했다.
결과는 빈 출력이다. 작업 템플릿 5개와 인벤토리 소스 1개의 modified 값이 변하지 않았다.
작업 템플릿 실행과 인벤토리 소스 동기화는 하지 않았다. 변경한 것은 인벤토리 5의 variables 뿐이다.

## 6. 남은 한계

- 4.94 MiB(문자) 를 넘는 조각은 보낼 수 없다. chunk_size 는 이보다 충분히 작게 둔다.
- AWX 가 variables 끝의 공백/줄바꿈을 제거하므로, 원본 variables 가 공백으로 끝나면 복원 후 그 공백이 없다.
  (시작 전 값도 이미 AWX 가 저장한 값이므로 보통 문제가 없다.)
- variables 는 YAML/JSON 이어야 저장된다. 탭이 들어간 비 YAML 원문은 AWX 가 400 으로 거부한다.
  업로더는 값을 모두 큰따옴표 문자열로 보내므로 파일 내용의 영향을 받지 않는다.
- Windows 전송 속도는 AWX 응답 시간에 묶인다. 1 MiB 당 약 2초 안팎이다.
