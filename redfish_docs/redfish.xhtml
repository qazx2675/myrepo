대상 프로젝트: redfish (biostool — v0.1.0)

원본 저장소 경로 (origin/master): .claude/HPC/redfish

대상 브랜치: confluence (redfish_docs/)

커밋된 사전 빌드 바이너리: bin/biostool (RHEL8 / kernel >= 3), bin/biostool_os6 (RHEL6 / kernel 2.6.32용 — 실제 RHEL6 미검증)

[중요 — v0.1.0 실장비 미연결 경고] 현재 redfish(biostool v0.1.0)는 실제 물리 BMC 하드웨어에 단 한 번도 연결·테스트된 적이 없습니다. 모든 동작 검증은 합성 testdata/ 기반 모의 서버(mockbmc.sh / Farm) 및 -from-dump 로컬 덤프에서만 수행되었습니다.

실제 BMC에 최초 연결하기 전에 반드시 저장소 루트의 FIRST_RUN.md를 정독하고, FIRST_RUN.md §B에 정리된 17개 미확인 항목과 9단계 1대 시범 절차를 먼저 검증하십시오. 또한 bin/biostool_os6는 CentOS 6 유저랜드 + kernel 4.18 환경에서만 확인되었으며 실제 RHEL6(kernel 2.6.32) 실기 검증은 완료되지 않았습니다.

안전 설계 원칙: biostool은 어떤 경우에도 서버를 자동 재부팅(Reset)하거나 즉시(Immediate) 적용하지 않고 Pending Settings만 예약하며, profiles/*.tsv에서 특정 모델 행에 verified=Y가 명시된 항목(Dell, HPE, Lenovo 한정)에만 쓰기를 허용합니다. 와일드카드(*) 행에 verified=Y를 설정하면 프로필 로드 자체가 차단됩니다.

1. 개요 및 변경 대상 (실제 조회/수정하는 Redfish 리소스 및 API)

redfish(biostool)는 데이터센터 다수 서버의 BMC(Out-of-Band) Redfish REST API를 통해 BIOS 설정 일괄 점검 및 표준 프로필 기반 Pending 설정 적용(check), 참조 서버 대비 전체 BIOS 속성 비교(allcheck), Redfish 트리 백업 덤프(dump), 비밀번호 암호화(encrypt)를 수행하는 Go 표준 라이브러리 기반 도구입니다.

안전장치를 위해 쓰기 동작은 엄격히 제한되며, 자동 재부팅(Reset)은 절대 수행하지 않고 Pending Settings만 예약합니다.

1.1 벤더별 지원 범위 및 실제 API 변경 대상

기능 / 벤더 대상 모델 / 조건 실제 호출·변경 범위 및 안전장치
BIOS 점검 (읽기 전용) Dell, HPE, Lenovo, Cisco, Supermicro (5개 벤더) Redfish GET으로 시스템·모델·현재 BIOS 속성·Pending Settings 조회 (ModeReadOnly). 프록시 우회, 리다이렉트 차단, BMC당 요청 간격 100ms, 호스트당 로그인 세션 1개(auth=session, 실패 시 Basic 폴백)
BIOS Pending 설정 적용 (쓰기) Dell, HPE, Lenovo만 쓰기 지원 (Cisco, Supermicro는 읽기 전용) profiles/<profile>.tsv에서 특정 모델 행의 verified=Y가 확인된 항목만 Pending Settings PATCH 및 설정 Job 생성(ModeSet). 와일드카드(*) 행에 verified=Y가 있으면 프로필 로드 자체가 에러로 차단됨
위험 경로·속성 차단 모든 Redfish 요청 (checkAllowed) 화이트리스트 checkAllowed가 LogServices, ClearLog, Reset, Immediate 등 시스템 재기동/로그 삭제/즉시 반영 경로 호출을 차단
로컬 결과·덤프 생성 관리서버 로컬 디스크 results/<YYYYMMDD_HHMMSS>/ 하위에 0600 권한으로 결과 파일 저장, dumps/ 하위에 xml.sh(dump) JSON 트리 저장

2. 사전준비 / 빌드 · 입력파일 · 계정/암호화

2.1 사전 빌드 바이너리 및 폐쇄망 빌드/업데이트

Go 표준 라이브러리만 사용(go.mod go 1.20, 외부 모듈/vendor/ 불필요)하며, 저장소 bin/에 커밋된 정적 바이너리를 래퍼(lib.sh)가 uname -r 주 버전에 따라 자동 선택합니다.

  • bin/biostool: RHEL8 이상 (kernel >= 3, Go 1.25 정적 빌드)
  • bin/biostool_os6: RHEL6용 (kernel < 3 / 2.6.32 타깃, Go 1.20.x 정적 빌드 — 단, 실제 RHEL6 2.6.32 미검증, CentOS 6 유저랜드 + kernel 4.18에서만 확인됨)
  • 랩 재빌드 및 배포 업데이트: bash setup.sh 또는 bash build.sh(os8 전용), bash build_os6.sh(admin, /opt/go1.20/bin 필요). 사내 표준 경로 배포 시 update.sh가 고정 경로 TARGET=/root/server_vm_python/redhfish/V2를 업데이트하며, 기존본을 /root/server_vm_python/redhfish/backup/V2_<일시>.tgz로 백업하고 설정·암호화 키·결과·덤프를 보존하며 profiles/*.tsv가 로컬에서 수정된 경우 *.new로 병합합니다.
bash

2.2 입력 파일 및 계정/암호화 (AES-256-GCM)

bios.conf에 평문 비밀번호 키(pass, password, passwd, pw)가 하나라도 존재하면 보안 오류로 즉시 실패합니다. 반드시 encrypt.sh로 암호화해야 합니다.

  • bios.conf: user= 필수 지정, 비밀번호는 pass_file=pass.enc 및 key_file=key.bin으로 참조.
  • encrypt.sh: 대화형으로 비밀번호를 2회(에코 없음) 입력받아 표준입력(stdin)으로 biostool encrypt에 전달하고 AES-256-GCM 암호화 파일(pass.enc, key.bin)을 0600 권한(.gitignore 대상)으로 생성합니다.
  • user.txt / /etc/hosts: 대상 호스트 목록(기본 user.txt)과 BMC IP/호스트명 매핑(/etc/hosts 또는 -hosts 지정 파일).
  • profiles/*.tsv: 탭 구분 프로필 테이블(컬럼: vendor, model, std_name, attribute, value, verified). 4개 표준 속성(system_profile, hyper_threading, llc_prefetch, sub_numa_cluster)은 프로필에 정의가 없더라도 항상 점검 대상에 포함되며(행이 없으면 MAPPING_MISSING으로 보고), value는 A|B 형식, 검증 여부는 Y/N으로 관리합니다.
bash

실제 BMC 연결 전 필수 확인: 아래 3.1절의 모의 BMC 사전 연습과 3.2절의 FIRST_RUN.md 9단계 실장비 최초 검증 절차를 거치지 않고 대량 서버에 bios_check.sh를 실행하지 마십시오. 특히 auth_fail_stop(기본 3)을 0으로 끄면 BMC 계정 잠금(lockout) 위험이 있습니다.

3.2 FIRST_RUN.md 기반 실 BMC 최초 검증 9단계 및 표준 적용 절차

  1. 1단계 (인증 사전 확인): bios.conf의 user와 encrypt.sh로 생성한 pass.enc/key.bin이 1대 테스트 BMC 인증에 정상 동작하는지 확인합니다. (웜업 직렬 인증 체크 후 병렬 진입, 연속 인증 실패 auth_fail_stop=3 도달 시 SKIPPED_AUTH_STOP으로 즉시 중단)
  2. 2단계 (1대 GET 덤프 채집): bash xml.sh로 실제 테스트 서버 1대의 Redfish 트리를 읽기 전용 GET으로 덤프합니다. (주의: xml.sh는 항상 현재 디렉터리의 ./bios.conf를 읽으며 -conf 등의 옵션을 거부함)
  3. 3단계 (실제 트리/스펙 대조 기록): 덤프 결과에서 실제 Model명, BIOS 버전, 인증 방식(Session/Basic), Settings 경로, 4개 표준 속성(system_profile, hyper_threading, llc_prefetch, sub_numa_cluster), Pending 경로, Attribute Registry 및 FIRST_RUN.md §B의 17개 미확인 항목을 직접 대조·기록합니다.
  4. 4단계 (프로필 미검증 등록): profiles/<프로필>.tsv(예: profiles/VM.tsv)에 해당 특정 모델 행을 추가하되 초기에는 반드시 verified=N으로 둡니다. (읽기 점검만 가능, 쓰기 차단 상태)
  5. 5단계 (-dry-run 미리보기): bash bios_check.sh --profile VM -dry-run을 실행해 생성될 PATCH 대상과 Job 동작을 육안으로 검증합니다.
  6. 6단계 (수동 BMC 변경 교차검증): 테스트 서버 BMC 웹 UI/CLI에서 해당 설정을 수동으로 적용·재부팅한 뒤, -no-prompt 읽기 전용 검증이 OK로 판정하는지 및 실제 BIOS 화면 값을 대조 확인합니다.
  7. 7단계 (특정 모델 verified=Y 승격): 검증이 끝난 해당 특정 모델 행만 verified=Y로 승격합니다. (와일드카드 * 행은 절대 Y로 두지 마십시오.)
  8. 8단계 (단일 서버 툴 실적용 및 재부팅 후 재확인): 1대 대상 bash bios_check.sh --profile <프로필> 실행 → APPLIED 확인 → 수동 재부팅 → 재점검 실행해 OK 판정 및 BMC/BIOS 실제 화면 수동 확인을 완료합니다. (참고: 비TTY 환경에서 -stdin-ok 없이 실행 시 Y/N 확인은 기본 N으로 안전 취소됨)
  9. 9단계 (점진적 대수 확대 및 사후 비교): 소수 카나리 그룹부터 대수를 단계적으로 늘려 적용하며, all_bios_check.sh로 기준(REFERENCE) 서버 대비 전 서버 일관성(SAME vs DIFF)을 최종 검증합니다.

5. 백업 및 롤백 방법

  • 작업 전 Redfish 트리 백업(필수): BIOS Pending 설정을 적용하기 전에 반드시 bash xml.sh [targets...]로 대상 BMC의 현재 Redfish 설정 트리를 dumps/에 저장해 두십시오.
  • Pending 설정 취소(재부팅 전 롤백): biostool은 자동 재부팅을 하지 않으므로 APPLIED 직후(재부팅 전)에 잘못된 변경이 발견되면 해당 서버 BMC 웹 콘솔이나 벤더 CLI(iDRAC/iLO/XCC)에서 Pending BIOS Settings / BIOS Job Queue를 수동 삭제해 반영을 막을 수 있습니다.
  • 재부팅 후 BIOS 값 원복: 이미 재부팅되어 BIOS 값이 실제 반영된 경우, 사전에 채집한 dumps/ JSON 스냅샷을 대조하여 profiles/<원복프로필>.tsv를 구성해 재적용하거나 BMC 콘솔에서 수동 원복 후 재부팅하십시오.
  • 배포본 롤백(update.sh 백업 활용): update.sh 실행 시 /root/server_vm_python/redhfish/backup/V2_<일시>.tgz가 생성되므로 툴 자체 버전 장애 시 해당 아카이브로 복원할 수 있습니다.

특히 v0.1.0은 실제 BMC 실장비 테스트 없이 모의 환경에서만 검증되었으므로, biostool이 APPLIED 또는 재부팅 후 OK / SAME을 보고하더라도 벤더 펌웨어별 Pending 반영 지연, Job 미생성, 속성 의존성(DEPENDS_ON_PROFILE) 등으로 실제 하드웨어 BIOS가 달라질 수 있습니다. 작업 완료 후 반드시 벤더·모델별 랜덤 1~3대 서버의 실제 BMC 콘솔/웹 UI 및 OS 쉘에 직접 접속하여 아래를 교차검증하십시오.

  • 실제 BMC BIOS 화면에서 system_profile, hyper_threading, llc_prefetch, sub_numa_cluster 적용 값과 Job Queue 잔여 상태 육안 확인
  • FIRST_RUN.md 및 dumps/ 기준의 원복 가능 상태 및 정상 POST/OS 부팅 여부 확인
  • RHEL6 환경에서 bin/biostool_os6 사용 시 실제 2.6.32 커널 환경에서의 TLS·세션·결과 저장 정상 동작 재확인
