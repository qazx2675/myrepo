실제 BMC 미검증 + 사후 확인 필수. 이 도구는 실제 BMC 하드웨어에서 검증된 적이 없으므로 100% 신뢰하지 말고 참고용(보조 도구)으로 사용하십시오. 설정 변경·계정 생성·비밀번호 변경을 한 뒤에는 벤더·모델별 랜덤 1~3대 서버에 직접 접속해 실제로 반영되었는지 확인해야 합니다. 모델을 처음 만나면 1대부터 진행합니다.

안전 설계 원칙

  • 재부팅(Reset)·즉시(Immediate) 적용을 하지 않습니다. 로그 조회·ClearLog·Reset 경로는 전송 전에 코드가 차단합니다.
  • 서버 고유값·부팅·보안·RAID·PXE·NIC 속성(IQN, IP, ServerName, BootMode, SecureBoot 등)은 어떤 경우에도 설정하지 않습니다 (설정 파일로 해제 불가).
  • TUI 의 수정 단계는 미리보기 → 확인(y) → 적용 순서이며, n·Esc·Ctrl+X 면 아무것도 쓰지 않습니다. -plain·-auto 는 읽기 전용입니다.
  • 같은 BMC 에 인증을 반복하면 계정이 잠길 수 있어 인증 실패(AUTH_FAIL)는 자동 재시도하지 않고, 연속 실패가 3회(auth_fail_stop)에 이르면 나머지 호스트 접속을 멈춥니다.

3. 비밀번호 암호화와 벤더 암호화 키는 어떻게 만드나?

모든 BMC 비밀번호는 bash bios.sh encrypt 로 암호화합니다. 비밀번호는 명령행 인자로 받지 않고 화면에 표시하지 않으므로 ps·쉘 히스토리에 남지 않습니다. 세 암호화 파일은 하나의 key.bin(AES-256 키)을 공유합니다.

명령 만드는 파일 어떤 비밀번호인가 입력 방식
bash bios.sh encryptpass.enc (+ key.bin)1순위 공용 BMC 계정(bios.conf 의 user) 비밀번호. 점검·설정 접속에 사용숨김 입력 2회, 같을 때만 저장
bash bios.sh encrypt 2pass2.enc두 번째 공용 계정(user2) 비밀번호. 계정 생성에서만 사용숨김 입력 2회
bash bios.sh encrypt rf / bash bios.sh encrypt rf <벤더>rf.enc (벤더별 한 줄)벤더 admin(2순위) 계정 비밀번호. 1순위 계정이 BMC 에 없을 때 접속·계정 생성에 사용글자마다 * 표시, 붙여넣기 거부, 터미널에서 직접 입력 2회

3.1 벤더 암호화 키(rf.enc)를 만드는 절차

벤더 값: dell hpe lenovo supermicro cisco cray. 계정명은 /etc/rf_tool/rf.conf 에 적고, 비밀번호는 rf.enc 에 벤더별로 암호화합니다.

  1. /etc/rf_tool/rf.conf 에 <벤더>_user=계정명 을 적고 권한을 600 으로 합니다 (비밀번호는 적지 않음).
  2. bash bios.sh encrypt rf 를 실행하면 rf.conf 에 계정명이 있는 벤더를 차례로 묻고 비밀번호를 받습니다. 한 벤더만 만들거나 갱신하려면 bash bios.sh encrypt rf dell 처럼 벤더를 줍니다 (rf.enc 의 다른 벤더 항목은 그대로 남음).
  3. key.bin 이 없으면 이때 AES-256 키가 새로 만들어지고, 있으면 그 키를 그대로 씁니다.
  4. rf.enc·key.bin 권한이 600 인지 확인합니다 (아니면 도구가 600 으로 보정하고 안내).
  5. rf.conf 에 예전 형식의 평문 <벤더>_pass= 줄이 있으면 경고가 나옵니다. rf.enc 가 우선하지만 평문 줄은 지웁니다.
bash
  • key.bin 과 pass.enc/pass2.enc/rf.enc 는 짝입니다. key.bin 을 지우거나 바꾸면 기존 암호화 파일을 풀 수 없어(키 불일치 오류) 모두 다시 만들어야 합니다.
  • 둘이 함께 유출되면 비밀번호가 풀립니다. 권한 600 을 유지하고 저장소·백업·티켓·메신저에 올리지 마십시오. 벤더별 예비 비밀번호는 서로 다르게 두고, 예비 계정은 권한이 낮은 계정(BIOS 설정만 가능)으로 만드십시오.
  • 2순위(벤더 admin) 계정은 1순위 로그인이 401 인증 실패일 때만 호스트당 1회 시도합니다. 벤더는 인증 전 ServiceRoot 응답으로 식별하므로 신뢰하는 관리망에서만 쓰십시오.

4.2 TUI 는 어떤 순서로 진행되나?

  1. 대상 입력: 대상 파일을 지정하거나 hostname / hostname-m / IP 를 붙여넣습니다 (한 줄에 hostname 또는 hostname 태그, Ctrl+D 완료, Ctrl+X 취소). -user 를 주면 묻지 않습니다.
  2. 프로파일 선택: profiles/*.tsv 중에서 고릅니다 (-profile 로 지정하면 생략).
  3. 접속·조회: 호스트당 로그인 1회로 BIOS 전체 속성을 읽어 프로파일 판정과 전체비교에 함께 씁니다. Ctrl+X 로 중단할 수 있습니다.
  4. [프로파일 점검] 화면: 프로파일 항목 결과를 색상 줄로 보여 줍니다. Tab 으로 [전체 설정 비교] 화면과 오갑니다.
  5. [전체 설정 비교] 화면: 처음 Tab 을 누르면 비교 기준을 고릅니다 (4.4 참고). 같은 모델끼리만 비교합니다.
  6. 수정: e 키로 들어가 수정 방법을 고르고, 미리보기 → 확인(y) 후 BMC Pending 까지만 설정합니다. 설정을 보낸 호스트는 자동 재점검해 화면에 반영합니다.
  7. 요약: q 를 두 번 눌러 종료하면 OK / difference / N/A / 오류 건수, 결과 폴더, CSV 목록을 출력합니다.
  8. 계정 생성 질문: 1순위 계정이 거부되어 2순위(rf.conf)로 점검한 호스트가 있으면 계정을 만들까요? [Y/n] 을 묻습니다 (빈 입력 = Y).

4.4 전체비교의 기준 서버는 어떻게 정하나?

[전체 설정 비교] 화면에서 기준 메뉴가 아래 순서로 나옵니다. -ref·-ref-json·-diff 옵션을 주면 메뉴를 건너뜁니다 (셋 중 하나만 가능).

메뉴 번호 기준 설명
1대표서버 자동 지정 (태그·모델별 1대)읽기에 성공한 호스트를 태그+모델(태그가 없으면 모델) 묶음으로 나누고, 묶음마다 가장 흔한 값들과 가장 많이 일치하는 서버(다수결)를 대표로 고릅니다. 동점이면 다수 BIOS 버전 → 프로파일 OK → 입력 순서. 추가 접속은 하지 않습니다. 대표·대수·선정 사유는 결과 폴더의 compare_refs.tsv. 대표가 마음에 들지 않으면 c 키로 묶음별로 다시 고릅니다.
2비교서버 hostname 입력직접 지정 (-ref <hostname> 와 같음). 대상 목록에 없으면 그 서버만 추가 조회
3 이후refs/ 폴더의 JSONbash bios.sh export 로 뽑은 속성 JSON (-ref-json <파일>)
마지막diff.txt (모델별 기준)모델별 기준 호스트 목록 (-diff <파일>)
  • 같은 모델끼리만 비교합니다. 비교서버와 BIOS 버전이 다른 호스트의 차이는 비교서버 값으로 설정하지 않고 수정제외로 표시합니다.
  • 고유값은 항상 비교에서 제외합니다. 서비스태그·시리얼·MAC·IP/게이트웨이/DNS·iSCSI/NVMe-oF 식별자·서버 이름 등은 ignore_attrs.txt 가 있어도 제외되고, 값이 MAC·UUID·IP·iqn./nqn. 모양이어도 제외됩니다. 더 빼려면 ignore_attrs.txt 나 bios.conf 의 exclude_attrs 에 적습니다.
  • 결과 태그 3종: [OK](초록), [difference](노랑), [N/A](회색 — 판정할 수 없다는 뜻이며 “문제 없음”이 아님. 접속 실패도 N/A 로 나오므로 비고의 원래 상태명을 확인).

4.5 BIOS 값을 수정하려면? (e 키, 3가지 방법)

text 변경값 목록) → "위 수정대상을 적용할까요?" [y/N] → (수정제외 항목이 있으면) "수정제외 항목을 확인했습니다. 진행할까요?" [y/N] → (남의 Pending 이 있으면) 포함 여부 질문 → BMC Pending 까지만 설정 (재부팅 없음) → 설정 보낸 호스트 자동 재점검]]>
수정 방법 동작
1. 대표서버 기준으로 맞추기[전체 설정 비교] 의 묶음(태그·모델)마다 대표서버와 값이 다른 속성만 체크 목록으로 보여 줍니다 (처음에는 모두 해제). 체크한 속성만 확인 질문을 거쳐 적용합니다. 한쪽에만 있는 속성(대표에만 있고 대상에 없는 경우 또는 반대)은 Redfish 로 BIOS 속성을 새로 만들거나 지울 수 없으므로 사유와 함께 자동 제외됩니다. 보호 속성·고유값은 고를 수 없고, BIOS 버전이 다른 호스트는 별도 경고 행으로 표시됩니다. allcheck_set 설정과 상관없이 동작하며, 적용 후에는 r 키로 다시 비교합니다.
2. 점검 결과 기준 수정프로파일 점검에서 FAIL 이면서 verified=Y 인 항목을 호스트별로 보여 주고 확인 후 적용합니다. bios.conf 의 allcheck_set=on 이면 전체비교 difference 도 대상에 포함합니다 (기본 off).
3. BIOS 값 직접 입력<Redfish 속성 이름><공백 또는 탭><설정값> 을 한 줄에 하나씩 붙여넣고 Ctrl+D 로 끝냅니다. 이미 같은 값·없는 속성·보호 속성·맞지 않는 값은 건너뛰고 나머지를 미리보기 → 확인 후 설정합니다 (허용값·ReadOnly 는 적용 때 BMC 속성 레지스트리로 다시 확인).

한 번 적용한 뒤에는 같은 세션에서 같은 호스트를 다시 설정할 수 없습니다 (화면 값이 적용 전 값이므로). 재부팅 후 다시 점검합니다.

4.6 프로파일에 설정 행을 추가하려면? (profile add, TUI p 키)

프로파일 파일을 편집기로 고치지 않고 태그·모델별 설정 행을 추가합니다. 태그를 주면 그 태그가 붙은 서버들이 보고한 모델마다 같은 행이 만들어지고, 모델을 주면 그 모델 1종에만 추가됩니다.

bash
  • 행은 프로파일의 # [redfish] 구역 끝에 추가되며, 쓰기 전에 <이름>.tsv.bak.<일시> 로 백업합니다.
  • verified 는 항상 N 입니다. 쓰기 허가(Y)는 사람이 실제 장비에서 확인한 뒤 프로파일 파일을 직접 고쳐 올립니다.
  • 보호 속성은 거절하고, 해당 모델에 없는 속성은 그 모델만 건너뜁니다. 같은 행이 다른 값으로 이미 있으면 -force 없이는 아무것도 쓰지 않고 종료코드 1 로 끝납니다.

4.7 자동화에서 쓰는 비대화형 실행 (-auto, -auto-check)

  • 묻지 않고 점검만 합니다 (설정 없음). 프로파일은 -profile 또는 bios.conf 의 auto_profile 입니다.
  • targets.txt 와 결과 파일 check.res_<user>(-auto 는 check.res_<user>_postapply 도)는 호출한 폴더 기준입니다.
  • 점검을 끝냈으면 FAIL 이 있어도 종료코드 0 입니다. conf 오류·대상 없음·프로파일 없음 같은 치명적 오류만 0 이 아닙니다.

4.8 Cisco 장비는 어떻게 점검하나?

hostname 이 bios.conf 의 xml_host_prefix(기본 c)로 시작하는 대상과 -user-xml 목록은 Cisco UCSM/CIMC XML API(읽기 전용) 로 점검하고 나머지는 Redfish 로 점검합니다. Cisco 는 프로파일 점검만 하고 전체비교·설정에서는 빠집니다. 기대값은 프로파일의 # [xml] 구역입니다.

5. BMC 계정은 어떻게 만들고 비밀번호는 어떻게 바꾸나?

5.1 계정 생성 — bash bios.sh account

1순위 계정(bios.conf 의 user + pass.enc)이 일부 BMC 에 없을 때, 벤더 admin(2순위, rf.enc)으로 접속해 같은 id/pw 의 관리자 계정을 만듭니다. bios.conf 에 user2 가 있으면 권한이 다른 두 번째 계정도 같은 호스트에 만듭니다. 권한은 user2_role 또는 user2_role_<벤더> (Administrator / Operator / ReadOnly)이고, 둘 다 없으면 생성 직전에 고르라고 묻습니다.

bash
  • bash bios.sh(TUI·-plain)도 점검 끝에 같은 질문을 합니다. 만든 뒤에는 1순위 계정을 만든 호스트만 자동 재점검해 결과를 합쳐 보여 줍니다.
  • 같은 id 가 이미 있으면 덮어쓰지 않습니다 (SKIP_EXISTS). 만든 뒤 새 계정으로 로그인 1회 검증하고, 인증 거부면 이번 실행이 만든 계정만 롤백합니다 (VERIFY_FAIL_ROLLED_BACK). 통신 오류로 확인하지 못하면 롤백하지 않고 VERIFY_UNKNOWN(수동 확인), 롤백도 실패하면 ROLLBACK_FAILED(수동 조치)입니다.
  • 결과는 results/<일시>/account_result.tsv(권한 0600, 비밀번호 없음), 생성 대상은 account_targets.txt, 만들 수 없는 호스트는 account_unfixable.txt 에 남습니다.

5.2 비밀번호 변경 — bash bios.sh passwd

BMC 공용 계정(bios.conf 의 user)의 비밀번호를 바꾸는 명령입니다. 1순위 계정으로 로그인되는 호스트에서만 바꿉니다 (admin 세션으로 남의 계정 비밀번호를 바꾸지 않음).

bash
  1. 새 비밀번호 입력: 터미널에서만 받습니다 (파이프·파일 거부). 글자마다 * 로 보이며 붙여넣기는 거부되므로 키보드로 직접 입력합니다. @ ! # $ < & " 같은 특수문자도 그대로 전송합니다.
  2. 확인: 기본이 N 이므로 명시적으로 y 를 입력해야 변경됩니다.
  3. 검증·롤백: 새 비밀번호로 1회 로그인하고, 인증 거부면 열려 있는 세션으로 이전 비밀번호를 되돌립니다 (VERIFY_FAIL_ROLLED_BACK). 되돌리기도 실패하면 ROLLBACK_FAILED.
  4. pass.enc 는 자동으로 바뀌지 않습니다. 모든 호스트가 성공한 것을 확인한 뒤 bash bios.sh encrypt 로 새 비밀번호를 다시 암호화합니다. 일부 호스트가 변경되지 않았다면 그 호스트는 이전 비밀번호가 유지되므로, 모두 성공한 뒤에 pass.enc 를 바꾸는 것이 안전합니다.

이 명령은 BMC 계정 비밀번호만 다룹니다. 서버 OS(SSH root) 비밀번호 변경은 별도의 비밀번호 변경 스크립트(pwreset)가 담당하며 이 도구와 무관합니다. 변경 후에는 bash bios.sh -plain -profile VM -user user.txt 로 1~2대를 점검해 새 비밀번호로 로그인되는지 확인합니다.

6. 실제 장비에 처음 적용할 때는 어떤 순서로 하나? (표준 안전 절차)

처음 만나는 모델은 대량 서버에 바로 실행하지 말고 아래 9단계로 1대부터 확인합니다. auth_fail_stop 을 0 으로 끄면 BMC 계정 잠금 위험이 있습니다. 계정(비밀번호)이 틀린 채 같은 서버에 반복 접속하지 마십시오.
  1. 인증 확인: user.txt 에 1대만 넣고 bash bios.sh -plain -profile VM -user user.txt 로 읽기 전용 점검을 합니다. AUTH_FAIL 이면 중단하고 계정·비밀번호부터 확인합니다.
  2. 1대 GET 덤프: bash bios.sh dump <BMC 주소 또는 hostname-m>. GET 만 보내며 dumps/ 에 저장하고 요약(Vendor/Model/BIOS 버전, 인증 방식, Settings 경로, 표준 4항목 후보 속성·허용값·ReadOnly, Pending, 속성 레지스트리)을 출력합니다.
  3. 실제 응답 대조: 요약의 실제 모델명·속성 이름·허용값·Settings 경로·Pending 상태를 기록합니다 (프로젝트 폴더의 FIRST_RUN.md “확인 필요” 항목 참고).
  4. 프로파일에 미검증 행 추가: 확인한 실제 속성 이름·허용값 그대로 추가합니다. bash bios.sh profile add -profile VM -model "벤더/모델" -set "속성=값" (verified 는 항상 N). 이 상태에서는 읽기 점검만 되고 쓰기는 차단됩니다.
  5. 미리보기: bash bios.sh -profile VM -user user.txt 로 TUI 를 열어 e → 수정 전 확인 화면의 현재값 -> 변경값 을 확인하고 n 으로 취소합니다 (쓰기 없음). Pending PATCH 본문·Job 까지 보려면 bash bios.sh check -profile VM -dry-run 을 사용합니다.
  6. 수동 변경 교차검증: 테스트 서버 BMC 웹 UI 에서 같은 값을 수동 적용·재부팅한 뒤, 읽기 점검이 OK 로 판정하는지와 실제 BIOS 화면 값이 같은지 확인합니다.
  7. verified=Y 승격: 검증이 끝난 그 모델 행만 사람이 프로파일 파일에서 verified=Y 로 바꿉니다 (* 와일드카드 행은 Y 불가).
  8. 같은 모델 1대 실적용: bash bios.sh -profile VM -user user.txt → e → 확인 y → Pending 설정(APPLIED) → 수동 재부팅 → 재점검 OK → BMC/BIOS 화면 직접 확인. Dell 은 iDRAC Job Queue 에 BIOS 설정 Job 이 있었는지도 봅니다.
  9. 점진적 확대·전체 비교: 1대 → 소수 대 → 수십 대 → 전체로 늘리며 단계마다 랜덤 서버를 직접 확인합니다. 이후 [전체 설정 비교] 의 1번 대표서버 자동 지정으로 묶음 안의 일관성을 확인합니다.

중단 기준: AUTH_FAIL(계정부터 확인), 예상 밖의 REJECTED/SET_ERROR/APPLY_UNCONFIRMED, PENDING_EXISTS 다수 (남의 Pending 을 건드리지 않고 멈춘 것이므로 원인 확인), 한 모델에서 MAPPING_MISSING.

8. 문제가 생기면? (진단·백업·롤백)

8.1 BMC 에 접속이 안 될 때

bash # 403·로그인 실패 등 BMC 접속 장애 진단 (읽기 전용) bash bios.sh trs-cisco -targets # Cisco UNSUPPORTED·XML 실패 원인 진단]]>

결과 화면은 포트 닫힘·응답 없음은 [접속불가], 계정 거부는 [계정 오류 AUTH_FAIL] 로 구분해 보여 주므로 계정 문제처럼 보이지만 실제로는 네트워크 문제인 경우를 가릴 수 있습니다.

8.2 잘못 설정했을 때 되돌리는 방법

상황 되돌리는 방법
Pending 을 보냈고 아직 재부팅 전도구는 재부팅하지 않으므로 해당 서버 BMC 웹 콘솔·벤더 CLI(iDRAC/iLO/XCC)에서 Pending BIOS Settings / BIOS Job Queue 를 수동 삭제하면 반영되지 않습니다.
이미 재부팅되어 BIOS 에 반영됨설정 전에 bash bios.sh dump <대상> 으로 저장해 둔 덤프를 대조해 되돌릴 값을 정하고, bash bios.sh 의 e → “BIOS 값 직접 입력”으로 다시 Pending 설정하거나 BMC 콘솔에서 수동 원복한 뒤 재부팅합니다.
프로파일을 잘못 고쳤을 때profile add 가 쓰기 전에 만든 profiles/<이름>.tsv.bak.<일시> 로 되돌립니다.
계정 생성·비밀번호 변경 실패도구가 검증에 실패한 서버에서 자동 롤백합니다. ROLLBACK_FAILED 는 account_result.tsv 의 detail 안내대로 수동 조치합니다.

설정을 되돌린 뒤에도, 계정을 만들거나 비밀번호를 바꾼 뒤에도 랜덤 1~3대에 직접 접속해 실제 값(BIOS 화면·BMC 로그인)을 확인합니다. 점검·설정 결과(results/)와 pass.enc·pass2.enc·rf.enc·key.bin 은 커밋·공유하지 않습니다. 같은 서버를 다른 표기(host 와 host-m)로 중복 입력하지 마십시오 (DUPLICATE_TARGET).

9. 자주 묻는 질문 (FAQ)

Q. BIOS 점검은 어떤 명령으로 실행하나요?
A. bash bios.sh 하나로 실행합니다. 화면 없이 읽기 전용으로 하려면 bash bios.sh -plain -profile VM -user user.txt 입니다.

Q. BIOS 설정을 바꾸면 서버가 재부팅되나요?
A. 아니요. BMC 의 Pending(예약)까지만 설정하고 재부팅은 하지 않습니다. 다음 재부팅 때 반영됩니다. 재부팅 전에는 PENDING_OK 로 보입니다.

Q. BMC 계정 비밀번호를 바꾸려면?
A. bash bios.sh passwd -dry-run 으로 대상을 확인한 뒤 bash bios.sh passwd 를 실행하고 새 비밀번호를 키보드로 직접 2회 입력(붙여넣기 불가)합니다. 모든 호스트 변경이 성공한 것을 확인한 뒤 bash bios.sh encrypt 로 pass.enc 를 새 비밀번호로 다시 만듭니다.

Q. 벤더(2순위) 계정 비밀번호를 암호화하려면?
A. /etc/rf_tool/rf.conf 에 <벤더>_user=계정명 을 적고 bash bios.sh encrypt rf (또는 bash bios.sh encrypt rf dell)를 실행합니다. 결과는 rf.enc 이고 key.bin 을 pass.enc 와 공유합니다.

Q. 1순위 계정이 없는 BMC 는 어떻게 하나요?
A. 벤더 admin(rf.enc)으로 접속해 점검되고, 점검 끝에 계정을 만들까요? [Y/n] 질문이 나옵니다. 직접 하려면 bash bios.sh account -dry-run 후 bash bios.sh account 를 실행합니다.

Q. 대표서버 기준으로 BIOS 를 똑같이 맞추려면?
A. bash bios.sh 로 점검 → Tab 으로 [전체 설정 비교] → 기준 메뉴 1번(대표서버 자동 지정) → e → “1. 대표서버 기준으로 맞추기” 에서 맞출 속성만 체크하고 확인합니다. 한쪽에만 있는 속성은 자동 제외됩니다.

Q. 서버마다 다른 값(시리얼·MAC·IP)도 비교되나요?
A. 아니요. 서비스태그·시리얼·MAC·IP·iSCSI 식별자 등 고유값은 항상 비교에서 제외되고 설정도 막혀 있습니다.

Q. 특정 태그·모델에 대한 표준 설정을 프로파일에 추가하려면?
A. bash bios.sh profile add -profile VM -tag gold -set "속성=값" (태그의 모델별 행 생성) 또는 -model "DELL/R660" 입니다. verified 는 항상 N 으로 들어가며, 실제 장비 확인 후 사람이 Y 로 바꿉니다.

Q. APPLIED 이면 BIOS 에 반영된 건가요?
A. 아니요. BMC 의 Pending 에 기대값이 들어간 것을 재조회로 확인했다는 뜻입니다. 재부팅 후 재점검(OK)과 BMC/BIOS 화면 직접 확인이 필요합니다.

Q. AUTH_FAIL 이 나오면?
A. 계정·비밀번호를 먼저 확인합니다. 자동 재시도하지 않으며, 연속 3회(auth_fail_stop)면 나머지 호스트 접속을 멈춰 계정 잠금을 막습니다. 접속 자체가 안 되는 것인지는 bash bios.sh trs -targets <BMC IP> 로 진단합니다.

Q. 실패한 호스트만 다시 하려면?
A. bash bios.sh check -retry-from results/<일시> 를 실행합니다 (결과 폴더의 retry.txt 사용).

Q. 쓰기는 어떤 벤더에서 되나요?
A. Dell, HPE, Lenovo 만, 프로파일에서 모델을 지정한 verified=Y 행에 한해 됩니다. Cisco·Supermicro 는 점검만 합니다.

Q. 이 도구 결과를 그대로 믿어도 되나요?
A. 아니요. 실제 BMC 에서 검증되지 않았고 참고용 보조 도구입니다. 설정 변경·계정 생성·비밀번호 변경 뒤에는 랜덤 서버 몇 대를 직접 확인하십시오.
