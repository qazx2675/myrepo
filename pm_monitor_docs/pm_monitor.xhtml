2. 처음 사용하기 전에 무엇을 준비하나?

  1. root 로 로그인합니다.
  2. pm_monitor 폴더로 이동합니다. 실행 권한이 없으면 chmod +x install_mn.sh install_mn_os8 을 실행합니다. 빌드는 필요 없습니다.
  3. 설정 파일을 만듭니다: cp pm_monitor.conf.sample pm_monitor.conf. 필요한 줄의 # 을 지우고 고칩니다. 설정 파일이 없으면 기본값으로 실행하고 경고 1줄을 보여 줍니다.
  4. 호스트파일을 만듭니다 (2.1절).
  5. (선택) 기준표 oklist.txt 를 만듭니다 (6.2절).

2.1 호스트파일 형식

  • 한 줄에 hostname [yum] 을 씁니다.
  • 두 번째 칸이 yum(대소문자 무시)이면 yum 모드입니다. 비어 있거나 다른 값이면 OS 설치 감시입니다.
  • 세 번째 칸부터는 무시합니다. 빈 줄과 # 줄도 무시합니다.
  • 같은 hostname 이 두 번 나오면 첫 줄만 씁니다.
  • OS 설치 서버와 yum 서버를 한 파일에 섞어도 됩니다.

2.2 결과 파일은 어디에 생기나?

상태 기록 <호스트파일>.pm_state.json 과 설정 결과표 <호스트파일>.res 는 실행한 폴더에 생깁니다. 호스트파일이 있는 폴더가 아닙니다. 다시 실행하면 상태 기록을 이어서 씁니다.

6. 서버 설정 조사(l), 기준표(oklist), res 파일은 어떻게 쓰나? (v0.5.0)

6.1 무엇을 조사하나?

서버마다 gossh 로 원격 명령을 한 번 실행합니다. csh/tcsh 에서도 동작합니다.

값출처
OS커널uname -r
appl/etc/auto.appl 의 /appl 줄 마운트 위치 (예: nas01:/export/appl). /wappl 은 보지 않습니다.
dns/etc/resolv.conf 의 nameserver IP. 적힌 순서대로 공백으로 잇습니다.
ldap_URI/etc/openldap/ldap.conf 의 URI 줄에서 호스트 이름만 순서대로 잇습니다. 예: URI ldap://server1/ ldap://server2/ → server1 server2
binddn/etc/openldap/ldap.conf 의 binddn 값
h/tlscpu 의 Thread(s) per core. 2 이상 ON, 1 OFF
ldap_check결과ldap_check_sh 로 지정한 ldap_check.sh 의 출력. 비교에는 쓰지 않습니다. 설정이 없으면 ldap_check_sh 미설정

bindpw(비밀번호)는 읽지도, 저장하지도, 보여 주지도 않습니다.

언제대상과 동작
자동 조사아직 조사하지 않은 서버를 회차마다 최대 100대 조사합니다. 성공한 서버는 자동으로 다시 조사하지 않습니다. 대상: yum 서버는 yum_update/접속가능 일 때만, OS 서버는 ping 이 닿는 동안
l 키대상 전체를 다시 조사합니다. 응답 없는 서버는 이전 값을 그대로 두고 비고에 실패 이유를 남깁니다. 대상: yum 서버는 yum_update/접속가능 만, OS 서버는 상태와 관계없이 전부

서버가 많을 때는 l 을 자주 누르지 마십시오. 누를 때마다 전체를 다시 조사하므로 관리 서버 부하가 커집니다. 8000대는 자동 조사로 모두 채우는 데 80회차(약 80분) 이상 걸립니다.

6.2 기준표 oklist.txt 형식

엑셀에서 복사해 붙여 넣은 탭 구분 7칸입니다: hostname, OS커널, appl, dns, ldap_URI, binddn, h/t

  • 빈 줄, # 줄, 첫 칸이 hostname 인 머리줄은 무시합니다.
  • 칸이 7개보다 적은 줄, hostname 이 없는 줄, 중복 hostname 줄은 무시하고 경고로 셉니다.
  • oklist 에 없는 서버는 비교하지 않습니다.
  • oklist 를 읽을 수 없으면 시작 전에 오류를 내고 종료 코드 1 로 끝납니다.
  • 비교 규칙: 여섯 값을 대소문자와 순서까지 구분해 비교합니다. ldap01 ldap02 와 ldap02 ldap01 은 다릅니다.
  • 다른 칸은 l 표에서 빨간색으로 보입니다. 조사 값이 비었는데 기준에 값이 있으면 (없음) 을 빨간색으로 보여 줍니다.

6.3 res 파일 <호스트파일>.res

탭 구분, UTF-8 입니다. 머리줄 9칸 뒤에 모든 서버를 호스트파일 순서로 씁니다. 내용이 바뀔 때마다 갱신합니다.

열내용
hostname · OS커널 · appl · dns · ldap_URI · binddn · h/t마지막으로 성공한 조사 값
설치/yumupdate여부O: 한 번이라도 설치완료(OS) 또는 yum_update/접속가능(yum)이었습니다. 한 번 켜지면 꺼지지 않습니다. 재부팅만 한 yum 서버는 X 입니다.
설정동일여부oklist 가 있고 그 서버가 oklist 에 있고 조사 결과가 있을 때만 O(여섯 값 모두 같음) / X. 그 밖에는 빈칸

엑셀에 붙여 넣으려면 cat hosts.txt.res 출력을 복사합니다. 터미널에서 보려면 column -t -s$'\t' hosts.txt.res | less -S 를 씁니다.

7. yum update 모드는 어떻게 쓰나? (v0.4.0)

yum 모드는 OS 가 이미 설치된 서버에서 yum update 와 재부팅 뒤 커널이 바뀌었는지 감시합니다. pm_monitor 는 yum update 를 실행하지 않습니다. 사람이 따로 실행합니다.

  1. 호스트파일에서 서버 이름 뒤에 yum 을 붙입니다.
  2. yum update 를 실행하기 전에 bash install_mn.sh hosts.txt 를 시작합니다. SSH 가 처음 성공한 회차에 기준 커널(uname -r)과 부팅 시각(uptime -s)을 한 번만 기록하기 때문입니다.
  3. 서버에서 yum update 와 재부팅을 합니다.
  4. 상태가 yum_update/접속가능 이 되면 완료입니다.
상태 (필터 번호)뜻 (yum 서버)
확인전아직 SSH 로 커널을 읽지 못했습니다.
ping X (5)기준 커널을 기록하기 전에 ping 응답이 없습니다.
접속가능 (8)기준 커널을 기록했고, 커널이 같고, 재부팅 흔적이 없습니다. 진행 중입니다.
재부팅됨 (6)ping 이 끊겼거나 부팅 시각이 60초 넘게 바뀌었는데 커널은 같습니다. 진행 중입니다. 매 회차 다시 확인합니다.
yum_update/접속가능 (9)SSH 가 되고 현재 커널이 기준 커널과 다릅니다. 완료입니다.
완료후꺼짐 (7)yum_update/접속가능 서버를 c 로 확인했을 때 ping 응답이 없습니다. 다시 켜지면 yum_update/접속가능 으로 돌아갑니다.
  • yum 지연: 기준 커널을 기록한 뒤 yum_delay_min(기본 60분)이 지나도 완료가 아니면 yum 지연입니다. 상태 이름은 바뀌지 않고 r·c·y 에만 나타납니다.
  • r 의 yum 블록: A) 재부팅이 확인되지 않음(접속가능) B) 재부팅했으나 커널이 바뀌지 않음(재부팅됨, 커널 동일) C) 재부팅 뒤 접속되지 않음
  • 집계: 설치완료 집계는 OS 서버만 셉니다. yum 서버는 yum update N대 중 M대 커널 변경 완료 로 따로 셉니다.

9. 문제가 생기면?

  • 사용법만 나오고 끝난다(종료 코드 2): 호스트파일 인자가 없거나 파일이 없습니다.
  • oklist 오류로 끝난다(종료 코드 1): oklist 파일을 읽을 수 없습니다. 경로를 확인하십시오.
  • 수집이 시작되지 않는다: /run/install_mn/<id>.log 를 보십시오. root 로 실행했는지 확인하십시오.
  • yum 서버가 계속 접속가능 이다: yum update 와 재부팅이 끝난 뒤에 감시를 시작했을 수 있습니다. 이 경우 변화가 없어서 완료가 되지 않습니다. 커널을 직접 확인하십시오.
  • yum 서버가 재부팅됨 에 머문다: 재부팅했지만 기본 부팅 커널이 옛 커널입니다. 서버의 기본 부팅 커널을 확인하십시오.
  • "호스트파일·설정이 바뀌어 수집을 다시 시작했습니다" 가 나온다: 호스트파일·설정·oklist·프로그램 버전 중 하나가 바뀌었습니다. 상태 기록은 유지합니다.
  • d 에 "dhcp_server 미설정" 이 나온다: pm_monitor.conf 에 dhcp_server 를 쓰십시오.

10. 자주 묻는 질문 (FAQ)

Q. pm_monitor 는 무엇을 하는 도구인가요?
A. PM 서버의 OS 설치 진행, yum update 후 커널 변경, 서버 설정을 1분마다 감시해 화면으로 보여 주는 도구입니다. 실행 명령은 bash install_mn.sh <호스트파일> 입니다.

Q. OS 설치가 오래 걸리는 서버를 찾으려면?
A. 화면에서 2 를 눌러 지연 서버만 봅니다. r 을 누르면 벤더별 점검요청 코멘트를 만듭니다.

Q. 설치현황을 보고하려면?
A. 화면에서 c 를 누릅니다. "N대 중 M대 설치완료" 같은 코멘트를 만듭니다.

Q. 화면을 닫으면 감시가 멈추나요?
A. 아니요. 수집은 백그라운드에서 계속합니다. 같은 명령으로 다시 붙습니다. 시작 12시간 뒤에는 스스로 끝납니다.

Q. yum update 후 커널이 바뀌었는지 확인하려면?
A. 호스트파일에서 서버 이름 뒤에 yum 을 붙이고, yum update 전에 감시를 시작합니다. 상태가 yum_update/접속가능 이면 완료입니다. y 키로 커널 표를 봅니다.

Q. 서버 설정이 기준과 같은지 비교하려면?
A. 기준표 oklist.txt 를 만들고 bash install_mn.sh hosts.txt oklist.txt 로 실행합니다. l 을 누르면 다른 칸이 빨간색입니다. m 을 누르면 다른 서버만 봅니다.

Q. 설정 결과를 엑셀로 받으려면?
A. 실행한 폴더의 <호스트파일>.res 내용을 복사해 엑셀에 붙여 넣습니다.

Q. pm_monitor 와 setup_check 는 무엇이 다른가요?
A. pm_monitor 는 설치 진행을 계속 감시하는 화면입니다. setup_check 는 한 번 판정하고, -run 으로 설정수정·부하테스트까지 진행합니다.
